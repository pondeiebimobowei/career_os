# ADR-048 — Browser Extension Version Compatibility Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** None

---

# Context

Unlike the Web Application, the Browser Extension cannot be updated instantly.

Extension releases are distributed through browser stores such as:

- Chrome Web Store
- Microsoft Edge Add-ons
- Mozilla Add-ons (future)

Users update extensions at different times.

As a result, production will always have multiple extension versions running simultaneously.

For example:

```text
Backend API

v1.8.0

↓

Connected Extensions

1.5.0

1.5.1

1.6.0

1.7.2

1.8.0
```

The backend must therefore support multiple extension versions during transition periods.

Failure to do so can result in:

- failed synchronization
- rejected requests
- parser incompatibilities
- broken user experiences
- forced upgrades
- data loss

CareerOS requires a formal compatibility strategy to ensure reliable operation across rolling extension upgrades.

---

# Decision

CareerOS adopts a **Backward-Compatible API Strategy** for Browser Extension communication.

The backend must remain compatible with supported extension versions for a defined support window.

Breaking protocol changes require staged migration rather than immediate replacement.

Backward compatibility is preferred over forced upgrades.

---

# Design Goals

The strategy should provide:

- reliable synchronization
- gradual extension adoption
- zero-downtime upgrades
- predictable compatibility
- graceful deprecation
- safe protocol evolution

---

# Compatibility Model

```text
Browser Extension

↓

Synchronization API

↓

Compatibility Layer

↓

Backend Services
```

Compatibility is managed by the backend.

Extensions remain lightweight clients.

---

# Version Identification

Every Browser Extension request includes:

```text
Extension Version

Parser Version

Protocol Version

Application Version
```

Example:

```http
X-Extension-Version: 1.6.0

X-Protocol-Version: 2

X-Parser-Version: linkedin-2.3.1
```

Version metadata enables compatibility decisions.

---

# Supported Version Window

The backend supports multiple extension versions simultaneously.

Example:

| Backend | Supported Extension Versions |
|---------|------------------------------|
| 1.8.0 | 1.6.x – 1.8.x |

Older unsupported versions receive upgrade guidance.

---

# Compatibility Policy

Supported versions receive:

- synchronization
- authentication
- parser support
- API stability
- bug fixes where practical

Unsupported versions may lose compatibility after the defined support window.

---

# API Evolution

Public synchronization endpoints should evolve conservatively.

Preferred sequence:

```text
Introduce

↓

Support Both Versions

↓

Deprecate

↓

Remove Old Version
```

Immediate breaking replacements are prohibited.

---

# Synchronization Protocol

Synchronization payloads include an explicit protocol version.

Example:

```json
{
  "protocolVersion": 2
}
```

Protocol versions are independent of application versions.

---

# Compatibility Layer

The backend includes a compatibility layer responsible for:

- request transformation
- payload normalization
- legacy field mapping
- protocol adaptation

Business logic should not contain version-specific branching.

---

# Deprecation Process

Breaking changes follow a staged process.

```text
Announce

↓

Introduce New API

↓

Support Old + New

↓

Monitor Adoption

↓

Deprecate

↓

Remove Legacy
```

Users should receive adequate notice before removal.

---

# Unsupported Versions

When an unsupported extension connects:

The backend should:

- reject unsupported operations gracefully
- return structured error responses
- indicate minimum supported version
- direct users to update

Example response:

```json
{
  "error": "UnsupportedExtensionVersion",
  "minimumVersion": "1.8.0"
}
```

Unexpected failures should be avoided.

---

# Feature Negotiation

Features should not be inferred solely from version numbers.

Preferred approach:

```text
Extension

↓

Capabilities

↓

Backend

↓

Supported Features
```

Capabilities provide greater flexibility than version comparisons.

---

# Capability Model

Example capabilities:

```text
resume-library

analytics-v2

bulk-import

sync-v2

parser-metadata
```

The backend enables behavior based on declared capabilities.

---

# Feature Flags

Feature flags may further control compatibility.

Example:

```text
New Sync Engine

↓

Enabled

↓

Supported Extension Versions Only
```

Feature flags complement—not replace—compatibility management.

---

# Parser Compatibility

Parser behavior evolves independently.

Each synchronization request includes:

- parser name
- parser version

This improves diagnostics and troubleshooting.

---

# Request Validation

Compatibility validation occurs before business logic.

Validation includes:

- protocol version
- extension version
- authentication
- schema version

Invalid requests fail early.

---

# Analytics

Track:

- extension version distribution
- protocol adoption
- unsupported version usage
- synchronization failures by version

Analytics guide deprecation timing.

---

# Rollout Strategy

Compatibility changes follow gradual rollout.

Example:

```text
Backend Supports V1 + V2

↓

Extension V2 Released

↓

80% Adoption

↓

Deprecation Notice

↓

Backend Removes V1
```

Compatibility removal is driven by adoption metrics.

---

# Browser Store Delays

The architecture assumes delayed updates.

Factors include:

- store approval
- user update behavior
- enterprise-managed browsers

The backend should tolerate delayed adoption.

---

# Offline Clients

Offline Browser Extensions may reconnect after long periods.

The backend should:

- detect compatibility
- request updates where necessary
- preserve synchronization safety

Unexpected data corruption must be avoided.

---

# Error Responses

Compatibility-related errors should be structured.

Example:

```json
{
  "code": "VERSION_NOT_SUPPORTED",
  "message": "Please update your Browser Extension.",
  "minimumVersion": "1.8.0"
}
```

Responses should support localization in the future.

---

# Testing Strategy

Compatibility requires:

## Unit Tests

- version comparison
- protocol negotiation
- capability evaluation

---

## Integration Tests

- legacy extension communication
- new protocol support
- compatibility layer

---

## End-to-End Tests

Verify:

- supported versions
- deprecated versions
- unsupported versions
- staged migrations
- rollback scenarios

Compatibility testing is part of release validation.

---

# Documentation

Compatibility documentation should include:

- supported extension versions
- protocol versions
- deprecated features
- migration guidance

Documentation should remain synchronized with releases.

---

# Security

Older extension versions remain subject to:

- authentication
- authorization
- rate limiting
- validation

Compatibility must never weaken security controls.

---

# AI Assistant Rules

AI-assisted development must:

- preserve backward compatibility
- avoid unnecessary breaking changes
- update compatibility tests
- document protocol evolution
- maintain capability negotiation
- avoid version-specific business logic outside the compatibility layer

Breaking compatibility requires an ADR and migration plan.

---

# Future Enhancements

Potential future improvements include:

- automatic compatibility negotiation
- protocol adapters
- server-driven capabilities
- multi-channel extension releases
- staged protocol upgrades
- compatibility dashboards

These enhancements should build upon the compatibility architecture.

---

# Consequences

## Positive

- Reliable Browser Extension upgrades
- Reduced synchronization failures
- Safer backend deployments
- Better operational visibility
- Improved user experience
- Predictable protocol evolution

## Negative

- Additional compatibility code
- Longer support windows
- Increased testing effort
- Operational monitoring requirements

---

# Compliance

All Browser Extension releases, synchronization endpoints, backend services, protocol changes, and parser integrations must comply with this compatibility strategy.

Breaking compatibility requires an approved Architecture Decision Record (ADR), a documented migration path, and a staged deprecation process.
