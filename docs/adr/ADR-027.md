# ADR-027: Engineering Playbook

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is developed using a repository-first, AI-assisted engineering workflow.

Unlike many projects where engineering practices are informal, CareerOS requires a standardized operating model because:

- planning is defined in YAML,
- GitHub is an execution platform,
- AI assistants participate in implementation,
- multiple automation tools interact with the repository,
- architectural consistency must be maintained over time.

Without a shared engineering playbook:

- development practices drift,
- code quality becomes inconsistent,
- reviews become subjective,
- automation becomes unreliable,
- AI-generated code varies in quality,
- onboarding becomes difficult.

CareerOS therefore requires a single engineering playbook that defines how engineering work is performed.

---

# Decision

CareerOS adopts a repository-wide **Engineering Playbook**.

The playbook defines the engineering standards, workflows, and operating principles used throughout the project.

Every contributor—human or AI—is expected to follow these standards.

---

# Goals

The Engineering Playbook should:

- Standardize engineering practices.
- Improve code quality.
- Reduce decision fatigue.
- Support AI-assisted development.
- Improve maintainability.
- Encourage continuous improvement.
- Provide a repeatable engineering workflow.

---

# Guiding Principles

Engineering decisions should prioritize:

- Simplicity
- Maintainability
- Readability
- Testability
- Scalability
- Reliability
- Automation
- Determinism

Every engineering decision should optimize for long-term maintainability over short-term convenience.

---

# Repository-First Development

All planning begins in the repository.

Workflow:

```text
CBS

↓

Backlog YAML

↓

GitHub Issue

↓

Branch

↓

Implementation

↓

Pull Request

↓

Merge
```

Planning does not originate in GitHub.

---

# Architecture First

Implementation follows documented architecture.

Developers should:

- consult ADRs,
- understand domain boundaries,
- avoid architectural shortcuts,
- update documentation when architecture evolves.

Code should conform to existing architectural decisions.

---

# Single Source of Truth

CareerOS maintains explicit ownership boundaries.

Examples:

| Concern | Source of Truth |
|---------|-----------------|
| Planning | YAML Backlog |
| Workflow | GitHub Projects |
| Code | Repository |
| Domain Model | ADR-010 |
| Analytics | ADR-018 |
| Resume Data | ADR-017 |

Duplicate sources of truth are prohibited.

---

# Engineering Workflow

Every feature follows:

```text
Select Issue

↓

Generate Branch

↓

Implement

↓

Test

↓

Commit

↓

Open PR

↓

Review

↓

Merge
```

The workflow remains consistent across all domains.

---

# Backlog First

Engineering begins with a backlog issue.

Developers should never implement undocumented features.

New work should be represented in the backlog before implementation begins.

---

# Short-Lived Branches

All implementation occurs on temporary branches.

Characteristics:

- Small
- Focused
- Reviewable
- Quickly merged

Long-lived branches are discouraged.

---

# Pull Requests

Every code change enters the repository through a pull request.

PRs should:

- solve one logical problem,
- reference one primary backlog issue,
- include tests,
- satisfy acceptance criteria,
- pass CI.

---

# Code Review

Reviews evaluate:

- correctness,
- readability,
- maintainability,
- architecture,
- testing,
- performance,
- security.

Reviews should focus on improving the software rather than personal coding preferences.

---

# Coding Standards

Code should be:

- readable,
- explicit,
- predictable,
- well-structured,
- strongly typed where applicable.

Prefer clarity over cleverness.

---

# SOLID Principles

CareerOS follows SOLID where appropriate.

Developers should strive for:

- Single Responsibility
- Open/Closed
- Liskov Substitution
- Interface Segregation
- Dependency Inversion

These principles guide maintainable software design rather than rigid rules.

---

# DRY

Avoid unnecessary duplication.

Shared behavior should be extracted when:

- duplication is meaningful,
- abstraction improves maintainability,
- complexity is not increased unnecessarily.

Over-abstraction is discouraged.

---

# KISS

Prefer the simplest solution that satisfies requirements.

Complexity requires justification.

---

# YAGNI

Features should not be implemented until required.

Avoid speculative abstractions.

Avoid premature optimization.

---

# Domain-Driven Thinking

Business rules belong in domain logic rather than infrastructure.

The domain model should express business concepts clearly.

Technical implementation should support the domain—not define it.

---

# Layered Architecture

Responsibilities remain separated.

Typical layers include:

```text
Presentation

↓

Application

↓

Domain

↓

Infrastructure
```

Cross-layer coupling should be minimized.

---

# Feature Organization

Projects are organized by feature rather than technical type whenever practical.

Each feature owns:

- UI
- Business logic
- Tests
- Supporting infrastructure

This improves cohesion.

---

# Testing Philosophy

Testing is mandatory.

Priority:

1. Unit tests
2. Integration tests
3. End-to-end tests

Critical business logic should never rely solely on manual testing.

---

# Continuous Integration

Every pull request executes:

- Type checking
- Linting
- Unit tests
- Integration tests
- Build verification
- Backlog validation

Failing checks block merging.

---

# Documentation

Documentation evolves alongside implementation.

Documentation updates are required when changes affect:

- architecture,
- APIs,
- workflows,
- engineering practices,
- product behavior.

Documentation is part of the feature—not an afterthought.

---

# AI-Assisted Development

AI assistants are engineering collaborators rather than autonomous decision makers.

AI may:

- generate code,
- explain code,
- suggest improvements,
- draft tests,
- draft documentation.

Humans remain responsible for:

- correctness,
- architecture,
- security,
- reviews,
- final approval.

---

# Security

Security is considered throughout development.

Developers should:

- validate input,
- enforce authorization,
- avoid exposing secrets,
- minimize privileges,
- follow secure defaults.

Security reviews are part of normal engineering work.

---

# Performance

Optimize based on measurement rather than assumption.

Performance improvements should:

- target real bottlenecks,
- preserve readability,
- include benchmarks when appropriate.

Premature optimization is discouraged.

---

# Error Handling

Errors should:

- be explicit,
- provide actionable context,
- avoid silent failures,
- preserve system consistency.

Unexpected errors should be observable and logged appropriately.

---

# Observability

Applications should expose sufficient telemetry for:

- debugging,
- monitoring,
- performance analysis,
- operational support.

Observability is considered during implementation rather than added later.

---

# Technical Debt

Technical debt should be:

- visible,
- documented,
- intentional,
- prioritized.

Hidden technical debt is unacceptable.

---

# Dependency Management

Dependencies should be:

- necessary,
- actively maintained,
- well understood,
- periodically reviewed.

Avoid unnecessary libraries.

---

# Refactoring

Refactoring is encouraged when it:

- improves maintainability,
- reduces complexity,
- improves readability,
- preserves behavior.

Refactoring should remain incremental.

---

# Release Readiness

Features are considered complete only when:

- acceptance criteria pass,
- tests pass,
- documentation is updated,
- CI succeeds,
- review is approved.

Implementation alone does not define completion.

---

# Continuous Improvement

Engineering practices evolve through:

- retrospectives,
- architectural discussions,
- ADRs,
- measurable outcomes.

Significant process changes require documented architectural decisions.

---

# Alternatives Considered

## Informal Engineering Practices

Rejected because:

- inconsistent quality,
- weak onboarding,
- subjective reviews,
- poor automation.

---

## Team-Specific Rules

Rejected because:

- fragmented standards,
- duplicated knowledge,
- inconsistent implementation.

---

# Consequences

## Positive

- Consistent engineering practices.
- Improved maintainability.
- Better onboarding.
- Reliable automation.
- Higher code quality.
- Strong AI collaboration.

---

## Negative

- Requires discipline.
- Documentation maintenance.
- Periodic review of engineering standards.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Engineering begins with an approved backlog issue.
- Architectural decisions documented in ADRs are followed.
- Repository-first planning is maintained.
- Every change is reviewed through a pull request.
- Continuous integration must pass before merge.
- Code adheres to established design principles.
- Documentation evolves alongside implementation.
- AI-generated code follows the same standards as human-written code.

Changes to the Engineering Playbook require a new ADR.

# Decision Summary

CareerOS adopts a comprehensive **Engineering Playbook** that standardizes how software is planned, designed, implemented, tested, reviewed, and released. The playbook establishes repository-first planning, architecture-driven development, AI-assisted engineering, mandatory testing, continuous integration, disciplined code review, and consistent design principles. It serves as the operational foundation for every contributor and ensures that engineering practices remain deterministic, maintainable, scalable, and aligned with the project's long-term architectural vision.
