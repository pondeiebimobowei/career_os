# ADR-001: Monorepo Architecture

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is not a single application.

It consists of multiple applications, shared libraries, developer tooling, browser extensions, infrastructure configuration, and planning artifacts that evolve together.

Current and planned applications include:

- Web Application
- Browser Extension
- Backend API
- Documentation Site (future)
- Admin Portal (future)
- Shared Packages
- Backlog CLI
- Internal Developer Tooling

All of these systems share common concerns including:

- TypeScript types
- Validation schemas
- API contracts
- UI components
- Design tokens
- Authentication models
- Business rules
- Configuration
- Engineering standards

Managing these repositories independently would introduce duplicated code, version drift, inconsistent tooling, and complex release coordination.

A monorepo allows all related software to evolve together while maintaining clear package boundaries.

---

# Decision

CareerOS will adopt a **Monorepo Architecture** managed using **Turborepo** and **pnpm Workspaces**.

The repository will contain all applications, shared packages, engineering tooling, documentation, backlog definitions, and infrastructure code.

The repository is the single source of truth for the CareerOS platform.

---

# Goals

The monorepo should:

- Minimize duplication
- Encourage code reuse
- Maintain strong package boundaries
- Simplify dependency management
- Enable shared tooling
- Improve developer experience
- Support incremental scaling
- Allow independent deployment of applications
- Centralize documentation
- Enable AI-assisted development with complete project context

# Workspace Organization

The repository is divided into four primary areas.

## Applications

Applications represent independently deployable software.

Examples:

- Web Application
- Backend API
- Browser Extension
- Documentation Site

Applications may depend on shared packages but never on other applications.

---

## Shared Packages

Packages contain reusable logic.

Examples include:

- UI Components
- Design Tokens
- Shared Types
- Validation Schemas
- Utilities
- API Client
- Configuration
- Backlog CLI

Packages should remain application-agnostic whenever possible.

---

## Documentation

Documentation lives inside the repository and evolves alongside the code.

Documentation includes:

- Product Requirements
- Architecture
- ADRs
- Engineering Guides
- API Specifications
- YAML Backlog
- Security Documentation
- Testing Documentation

Documentation is version-controlled and reviewed like code.

---

## Infrastructure

Infrastructure contains deployment and operational assets.

Examples include:

- Docker
- CI/CD
- Infrastructure configuration
- Environment templates
- Deployment scripts

---

# Package Dependency Rules

Dependencies must flow in one direction.

```text
Applications
        │
        ▼
Shared Packages
        │
        ▼
External Libraries
```

Applications must never import code directly from another application.

For example:

✅ Allowed

```text
apps/web
      │
      ▼
packages/ui
```

❌ Not Allowed

```text
apps/web
      │
      ▼
apps/api
```

---

# Shared Package Principles

Shared packages should:

- Have a single responsibility
- Expose stable public APIs
- Minimize external dependencies
- Be independently testable
- Be reusable across applications

Packages should avoid knowledge of application-specific implementation details.

# Build System

CareerOS uses:

- Turborepo
- pnpm Workspaces
- TypeScript Project References

- Incremental builds
- Cached builds
- Parallel execution
- Dependency-aware task execution

# Dependency Management

The workspace uses:

- pnpm

Reasons include:

- Fast installation
- Efficient disk usage
- Strict dependency isolation
- Excellent monorepo support

---

# Code Sharing

Shared functionality belongs in packages.

Examples include:

- Authentication types
- API contracts
- UI components
- Utility functions
- Zod schemas
- Error models

Business logic should not be duplicated across applications.

---

# Testing

Each application owns its own tests.

Shared packages own package-level tests.

The repository also supports:

- Integration tests
- End-to-end tests
- Browser Extension tests

Testing should execute through Turborepo task pipelines.

---

# CI/CD

Continuous Integration operates at the repository level.

Typical pipeline:

```text
Install
    ↓
Type Check
    ↓
Lint
    ↓
Unit Tests
    ↓
Integration Tests
    ↓
Build
    ↓
Backlog Validation
```

Only affected workspaces should rebuild whenever possible.

---

# Versioning

Applications may be deployed independently.

Shared packages follow Semantic Versioning.

Repository history remains unified.

---

# Documentation Strategy

Documentation is treated as code.

Every significant architectural decision is documented through:

- ADRs
- Product Documentation
- Engineering Guides
- YAML Backlog

Documentation changes undergo the same review process as source code.

# AI Development

The monorepo provides complete project context for AI assistants.

Benefits include:

- Repository-wide search
- Cross-package understanding
- Shared type awareness
- Documentation access
- Architecture awareness
- Backlog integration

AI tooling must respect package boundaries and repository conventions.

# Alternatives Considered

## Multiple Repositories

Advantages

- Smaller repositories
- Independent permissions

Disadvantages

- Duplicate tooling
- Version drift
- Harder refactoring
- Complex dependency management
- Fragmented documentation

Rejected.

---

## Polyrepo with Git Submodules

Advantages

- Code sharing

Disadvantages

- Operational complexity
- Difficult onboarding
- Poor developer experience

Rejected.

---

## Monorepo Without Shared Packages

Advantages

- Simpler initially

Disadvantages

- Code duplication
- Inconsistent implementations
- Harder maintenance

Rejected.

---

# Consequences

## Positive

- Single source of truth
- Shared architecture
- Better code reuse
- Consistent tooling
- Easier refactoring
- Unified documentation
- Improved AI assistance
- Simplified dependency management
- Faster onboarding

---

## Negative

- Larger repository
- More sophisticated build tooling
- Initial Turborepo configuration complexity
- Developers must understand workspace boundaries

These trade-offs are acceptable given the long-term benefits.

---

# Compliance

The following repository rules are mandatory.

- Applications must not depend on other applications.
- Shared code belongs in packages.
- Documentation resides in the repository.
- Every package has a clear responsibility.
- New reusable code should be extracted into shared packages.
- Workspace boundaries must not be violated.
- All build and test tasks execute through Turborepo.

# Decision Summary

CareerOS will use a **Turborepo-based monorepo** with **pnpm Workspaces** as the foundation of the platform. All applications, shared packages, documentation, backlog definitions, developer tooling, and infrastructure will live in a single repository with strict dependency boundaries, centralized documentation, and shared engineering standards.
