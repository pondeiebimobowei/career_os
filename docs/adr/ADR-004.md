# ADR-004: Feature-Based Project Structure

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is expected to grow into a large software platform with numerous product domains, including:

- Authentication
- Dashboard
- Companies
- Jobs
- Applications
- Application Pipeline
- Tasks
- Notes
- Resume Library
- Browser Extension
- Analytics
- Notifications
- Settings
- Billing
- Administration

Organizing the codebase by technical type (for example `components/`, `pages/`, `services/`, `hooks/`) causes related code to become scattered across the repository.

As the project grows, this leads to:

- Difficult navigation
- Tight coupling
- Poor ownership
- Harder refactoring
- Large merge conflicts
- Reduced developer productivity

The project structure should instead reflect the **business domains** of CareerOS.

---

# Decision

CareerOS will organize applications using a **Feature-Based Project Structure**.

Every business capability is implemented as a self-contained feature.

A feature owns everything required to implement that capability.

Examples include:

- UI
- Application services
- Domain logic
- Validation
- API calls
- Hooks
- Tests
- Feature documentation

---

# Goals

The project structure should:

- Mirror the product domain
- Keep related code together
- Reduce coupling
- Improve discoverability
- Encourage modular development
- Enable independent evolution
- Support AI-assisted engineering
- Improve onboarding

---

# Architecture Relationship

Feature-Based Organization complements the Layered Architecture defined in ADR-003.

Each feature internally follows the same layered principles.

```text
Feature
    │
    ├── Presentation
    ├── Application
    ├── Domain
    └── Infrastructure
```

Features organize **what** the code belongs to.

Layers organize **how** the code is structured.

# Internal Feature Structure

Each feature follows a predictable structure.

```text
applications/

├── components/
│
├── pages/
│
├── hooks/
│
├── services/
│
├── domain/
│
├── api/
│
├── validation/
│
├── types/
│
├── utils/
│
├── tests/
│
├── index.ts
│
└── README.md
```

Not every feature requires every folder.

Only create folders when needed.

---

# Responsibilities

Each feature owns:

- UI Components
- Pages
- Business Workflows
- Validation
- Feature Types
- Feature Tests
- Feature Hooks
- API Integration
- Domain Models
- Utilities

The feature should be as self-contained as possible.

---

# Public API

Each feature exposes a public interface.

Example:

```text
applications/

index.ts
```

Other features import only from the public entry point.

Never import internal implementation files directly.

Example:

✅ Allowed

```typescript
import { CreateApplicationForm } from "@/features/applications";
```

❌ Not Allowed

```typescript
import { CreateApplicationForm } from "@/features/applications/components/forms/create/CreateApplicationForm";
```

---

# Cross-Feature Communication

Features should communicate through:

- Public APIs
- Shared packages
- Application services
- Events
- Explicit interfaces

Features should avoid direct knowledge of internal implementation details.

---

# Shared Code

Not all code belongs inside a feature.

Reusable code should move into shared packages.

Examples include:

- UI components
- Design tokens
- Shared validation
- Shared utilities
- Shared types
- API client
- Configuration

The rule is:

> If multiple features need it, consider extracting it into a shared package.

---

# Feature Independence

Each feature should be independently understandable.

A developer should be able to open a feature directory and immediately find:

- Components
- Services
- Domain logic
- Tests
- Validation
- Types

without searching the rest of the project.

---

# Browser Extension

The Browser Extension follows the same philosophy.

Example:

```text
apps/extension/src/

features/

├── authentication/
├── capture/
├── parser/
├── sync/
├── settings/
└── telemetry/
```

Each extension feature owns its implementation.

---

# Backend API

The backend follows feature organization as well.

Example:

```text
apps/api/src/

features/

├── authentication/
├── companies/
├── jobs/
├── applications/
├── tasks/
├── notes/
└── analytics/
```

Each feature contains:

- Routes
- Controllers
- Services
- Domain
- Repositories
- Validation
- Tests

---

# Dependency Rules

Features may depend on:

- Shared packages
- Public APIs of other features (when necessary)

Features must **not** depend on internal implementation details of another feature.

---

# Folder Naming

Folder names should:

- Represent business domains
- Use lowercase
- Use kebab-case
- Avoid framework terminology

Good examples:

```text
application-pipeline
resume-library
browser-extension
user-profile
```

Avoid:

```text
components2
newComponents
misc
helpers
commonStuff
```

---

# Testing

Each feature owns its own tests.

Examples:

```text
applications/tests/

companies/tests/

dashboard/tests/
```

Feature tests should remain close to the code they validate.

---

# Documentation

Each major feature may include:

```text
README.md
```

Containing:

- Feature overview
- Responsibilities
- Dependencies
- Public API
- Important implementation notes

---

# Benefits

Feature organization provides:

- Better navigation
- Reduced coupling
- Easier refactoring
- Smaller pull requests
- Clear ownership
- Better scalability
- Better onboarding
- Easier AI reasoning
- Higher cohesion

---

# Alternatives Considered

## Technical Folder Structure

Example:

```text
components/
pages/
hooks/
services/
utils/
```

Rejected because:

- Related code becomes scattered.
- Difficult to understand business capabilities.
- Large cross-cutting changes.
- Poor scalability.

---

## MVC Organization

Rejected because:

- Controllers become large.
- Business logic becomes fragmented.
- Less suitable for modern frontend architecture.

---

## Flat Folder Structure

Rejected because:

- Does not scale.
- Difficult navigation.
- Poor discoverability.

---

# Consequences

## Positive

- Code mirrors the product.
- Easier onboarding.
- Smaller merge conflicts.
- Better modularity.
- Easier testing.
- Improved maintainability.
- Better AI context.
- Independent feature evolution.

---

## Negative

- More directories.
- Slight duplication between small features.
- Requires discipline to avoid unnecessary coupling.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every business capability is implemented as a feature.
- Features own their implementation.
- Shared logic belongs in shared packages.
- Cross-feature imports use public APIs only.
- Tests remain within their feature.
- Internal implementation must not be imported directly.
- Feature names represent business domains.

Violations require architectural review.

# Decision Summary

CareerOS will organize all applications using a **Feature-Based Project Structure**, where each business capability owns its UI, application services, domain logic, validation, API integration, tests, and documentation. Features internally follow the Layered Architecture defined in ADR-003, exposing only a stable public API while keeping implementation details encapsulated. This approach aligns the codebase with the product domain, improving modularity, maintainability, scalability, and developer productivity.
