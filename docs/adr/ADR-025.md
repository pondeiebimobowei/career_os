# ADR-025: Conventional Commits

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS follows a repository-first engineering workflow built around:

- CBS v1.0 Backlog
- GitHub Issues generated from YAML
- AI-assisted development
- Protected branches
- Automated releases
- Pull request conventions
- Semantic versioning

Git commit messages form the permanent history of the project.

Poor commit messages make it difficult to:

- Understand project history.
- Generate changelogs.
- Audit changes.
- Identify regressions.
- Automate releases.
- Correlate commits with backlog issues.

To support automation and maintain a high-quality repository history, CareerOS requires a standardized commit message format.

---

# Decision

CareerOS adopts the **Conventional Commits Specification** as the mandatory commit message format.

Every commit must use a structured format that communicates:

- the type of change,
- the affected scope,
- a concise description,
- and, where applicable, the associated CBS issue.

---

# Goals

The commit convention should:

- Produce a readable Git history.
- Support semantic versioning.
- Enable automated changelog generation.
- Improve traceability.
- Support AI-assisted development.
- Simplify debugging.
- Integrate with release automation.

---

# Commit Lifecycle

Development follows:

```text
Backlog Issue

↓

Feature Branch

↓

Commits

↓

Pull Request

↓

Merge

↓

Release
```

Commits document implementation progress within a feature branch.

---

# Commit Format

CareerOS adopts the Conventional Commits format:

```text
<type>(<scope>): <description>
```

Examples:

```text
feat(api): add application creation endpoint
```

```text
fix(parser): handle missing LinkedIn company names
```

```text
docs(adr): add analytics model decision
```

The header should be concise and written in the imperative mood.

---

# Commit Types

Approved commit types include:

```text
feat
fix
refactor
perf
test
docs
style
build
ci
chore
revert
```

No additional commit types should be introduced without team agreement.

---

# Type Definitions

## feat

Introduces new functionality.

Example:

```text
feat(app): add application status history
```

---

## fix

Corrects incorrect behavior.

Example:

```text
fix(sync): prevent duplicate application creation
```

---

## refactor

Improves internal structure without changing external behavior.

Example:

```text
refactor(core): simplify dependency resolver
```

---

## perf

Improves performance.

Example:

```text
perf(api): reduce dashboard query time
```

---

## docs

Documentation changes.

Example:

```text
docs(adr): add resume library architecture
```

---

## test

Adds or updates automated tests.

Example:

```text
test(parser): add normalization test cases
```

---

## style

Formatting-only changes that do not affect behavior.

Examples include:

- whitespace
- formatting
- lint fixes

---

## build

Changes to build tooling.

Example:

```text
build(turbo): update pipeline configuration
```

---

## ci

Changes to continuous integration.

Example:

```text
ci(github): add backlog validation workflow
```

---

## chore

Repository maintenance.

Examples:

- dependency upgrades
- tooling
- housekeeping

---

## revert

Reverts a previous commit.

Example:

```text
revert(api): remove experimental parser endpoint
```

---

# Scope

The scope identifies the primary subsystem affected.

Recommended scopes include:

```text
api
web
mobile
extension
parser
sync
database
auth
dashboard
analytics
core
backlog
docs
ci
```

Scopes should remain short and meaningful.

---

# Description

Descriptions should:

- use lowercase,
- use the imperative mood,
- describe intent,
- avoid trailing periods.

Good:

```text
add resume versioning
```

Avoid:

```text
Added resume versioning.
```

---

# Breaking Changes

Breaking changes are explicitly identified.

Header example:

```text
feat(api)!: redesign authentication endpoints
```

Additional details belong in the commit body.

Breaking changes trigger a major version increment.

---

# Commit Body

A body is optional but encouraged for complex changes.

The body explains:

- motivation,
- implementation decisions,
- important context.

Example:

```text
Refactors dependency resolution to support
cross-domain feature references while
maintaining deterministic ordering.
```

---

# Footer

Footers may reference issues.

Examples:

```text
Refs: APP-001
```

```text
Closes: APP-014
```

or

```text
Fixes #123
```

The canonical planning reference remains the CBS issue identifier.

---

# Commit Size

Commits should be:

- focused,
- atomic,
- reviewable.

One logical change per commit.

Avoid combining unrelated modifications.

---

# Relationship to Pull Requests

Multiple commits may exist within a feature branch.

After review, the branch is merged using:

```text
Squash and Merge
```

The resulting commit becomes the permanent record on `main`.

---

# AI-Assisted Development

AI-generated commits must follow the same convention.

AI tools should generate compliant commit messages rather than generic summaries.

Human developers remain responsible for verifying commit quality.

---

# Automation

Conventional Commits enable:

- semantic versioning,
- release automation,
- changelog generation,
- commit validation,
- repository analytics.

Automation relies on consistent formatting.

---

# Commit Validation

Commit messages should be validated automatically.

Recommended mechanisms include:

- commit-msg Git hooks,
- Husky,
- Commitlint,
- CI enforcement.

Invalid commit messages should be rejected before merge.

---

# Examples

Feature:

```text
feat(extension): add greenhouse parser
```

Bug fix:

```text
fix(database): prevent duplicate resume records
```

Documentation:

```text
docs(architecture): document layered architecture
```

Testing:

```text
test(sync): add retry integration tests
```

CI:

```text
ci(actions): cache pnpm dependencies
```

---

# Merge Commits

Merge commits are avoided by using:

```text
Squash and Merge
```

This keeps the `main` branch history linear and easy to read.

---

# Release Integration

Release tooling derives changelog entries from commit types.

Examples:

```text
feat → Features

fix → Bug Fixes

perf → Performance

docs → Documentation
```

Consistent commits improve release notes automatically.

---

# Testing Strategy

Validation includes:

## Local Validation

Commit hooks.

---

## CI Validation

Commitlint.

---

## Regression Tests

Ensure release tooling correctly interprets commit messages.

---

# Alternatives Considered

## Free-Form Commit Messages

Rejected because:

- inconsistent history,
- poor automation,
- weak release support.

---

## Ticket Number Only

Example:

```text
APP-001
```

Rejected because:

- lacks context,
- poor readability,
- weak changelog generation.

---

## Long Narrative Messages

Rejected because:

- inconsistent,
- difficult to scan,
- unsuitable for automation.

---

# Consequences

## Positive

- Consistent Git history.
- Better release automation.
- Improved debugging.
- Strong AI compatibility.
- Reliable changelog generation.
- Easier repository navigation.

---

## Negative

- Slight learning curve.
- Commit validation tooling required.
- Developers must follow formatting rules.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every commit follows the Conventional Commits format.
- Approved commit types are used consistently.
- Commit descriptions use the imperative mood.
- Breaking changes are explicitly identified.
- Commit messages are validated automatically where possible.
- Commits remain focused and atomic.
- Squash merge is the default strategy for `main`.

Changes to the commit message convention require a new ADR.

# Decision Summary

CareerOS adopts the **Conventional Commits Specification** for all Git commit messages. Every commit follows the `<type>(<scope>): <description>` format, enabling a consistent repository history, automated changelog generation, semantic versioning, AI-assisted development, and reliable release automation. Commit messages are validated through tooling wherever possible, and all changes merged into `main` must comply with this convention.
