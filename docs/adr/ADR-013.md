# ADR-013: Browser Extension Architecture

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

A defining capability of CareerOS is allowing users to capture job opportunities directly from supported recruitment websites without manually recreating them inside the application.

Unlike the web application, a browser extension operates inside an untrusted environment:

- Third-party websites
- Multiple browser tabs
- Different browser APIs
- Dynamic HTML
- Frequent DOM changes
- Permission restrictions
- Cross-origin communication

The extension must therefore have a dedicated architecture that:

- Isolated browser-specific logic
- Separates parsing from synchronization
- Shares business models with the platform
- Supports multiple job boards
- Remains maintainable as external websites evolve

---

# Decision

CareerOS will implement the browser extension as a **standalone application** within the monorepo using **Manifest V3** and a layered, modular architecture.

The extension will:

- Share platform contracts through shared packages.
- Use parser adapters for each supported ATS.
- Communicate exclusively through the CareerOS API.
- Keep browser-specific logic isolated from business logic.

---

# Goals

The browser extension should:

- Capture jobs with minimal user interaction.
- Support multiple recruitment platforms.
- Remain resilient to DOM changes.
- Minimize browser permissions.
- Share validation and API contracts.
- Be independently testable.
- Scale as new parsers are added.

# Core Components

The extension consists of four primary runtime components:

## Content Scripts

Responsible for:

- Reading page content.
- Detecting supported pages.
- Extracting raw DOM information.
- Sending parsed data to the extension runtime.

Content scripts never communicate directly with the backend.

---

## Background Service Worker

Responsible for:

- Authentication
- Synchronization
- Browser events
- Messaging
- Storage
- Network communication

The background worker is the integration hub of the extension.

---

## Popup UI

Responsible for:

- User interaction
- Capture confirmation
- Manual editing
- Authentication
- Settings
- Error display

Business logic should not reside inside UI components.

---

## Shared Services

Reusable services include:

- Authentication
- API Client
- Storage
- Parser Registry
- Sync Queue
- Telemetry

These services isolate infrastructure concerns.

---

# Layered Architecture

The extension follows the same layered architecture as the rest of CareerOS.

```text
Presentation

↓

Application

↓

Domain

↓

Infrastructure
```

Browser APIs belong exclusively to the infrastructure layer.

---

# Parser Layer

Parsing is isolated behind a common interface.

```text
Parser Interface

↓

LinkedIn

Greenhouse

Lever

Workday

Ashby (future)

Workable (future)
```

Each parser converts platform-specific HTML into a shared domain model.

---

# Canonical Job Model

Every parser outputs the same canonical object.

Example:

```text
Captured Job

Title

Company

Location

Employment Type

Description

Source URL

External ID
```

The rest of the extension is unaware of the originating platform.

---

# Parser Independence

Each parser is self-contained.

Responsibilities include:

- DOM selection
- Data extraction
- Validation
- Normalization

Parsers must not depend on one another.

---

# Authentication

Authentication uses the platform identity provider.

Flow:

```text
User

↓

Firebase Authentication

↓

ID Token

↓

CareerOS API
```

The extension never implements a separate authentication system.

---

# Synchronization

Captured jobs are synchronized through the backend API.

Workflow:

```text
Capture

↓

Validate

↓

Queue

↓

API

↓

Database

↓

Response
```

All synchronization passes through the backend.

---

# Duplicate Detection

Duplicate detection occurs in two stages.

Local:

- Recently captured items.
- Current synchronization queue.

Backend:

- Existing applications.
- Existing jobs.
- Existing captured URLs.

The backend remains the source of truth.

---

# Offline Support

Temporary offline behavior includes:

- Local queue
- Retry mechanism
- Status indicators

Permanent offline operation is outside MVP scope.

---

# Storage

The extension stores only lightweight operational data.

Examples:

- Authentication state
- Queue state
- User preferences
- Temporary captures

Persistent business data belongs in PostgreSQL.

---

# Browser Permissions

The extension follows the principle of least privilege.

Only required permissions are requested.

Examples:

- Storage
- Active Tab
- Scripting
- Supported host permissions

Broad permissions are avoided whenever possible.

---

# Error Handling

Failures are categorized.

Examples:

- Parser failure
- Authentication failure
- API failure
- Synchronization failure
- Network failure

Users receive actionable feedback.

---

# Telemetry

Operational events include:

- Capture attempted
- Capture succeeded
- Capture failed
- Parser selected
- Sync completed
- Sync failed

Telemetry excludes sensitive user data.

---

# Security

Security principles include:

- Secure token handling
- Minimal permissions
- HTTPS-only communication
- Input validation
- No secrets in source code

Browser storage should never contain long-lived secrets unnecessarily.

# Versioning

The extension follows Semantic Versioning.

Browser releases remain compatible with supported backend API versions.

Breaking protocol changes require coordinated releases.

---

# Extensibility

New ATS integrations require:

1. New parser implementation.
2. Registration in parser registry.
3. Test fixtures.
4. Parser tests.

No other architectural changes should be required.

---

# Alternatives Considered

## Monolithic Extension

Advantages:

- Fewer files.

Rejected because:

- Difficult maintenance.
- Tight coupling.
- Poor scalability.

---

## Parser Logic Inside UI

Rejected because:

- Violates separation of concerns.
- Difficult testing.
- Poor reuse.

---

## Direct Database Access

Rejected because:

- Security risk.
- Bypasses business validation.
- Breaks platform architecture.

---

## Separate Backend for Extension

Rejected because:

- Duplicated business logic.
- Increased maintenance.
- Inconsistent APIs.

---

# Consequences

## Positive

- Clean separation of concerns.
- Independent parser development.
- Shared platform contracts.
- Easier maintenance.
- Better testing.
- Future-proof architecture.

---

## Negative

- More architectural components.
- Additional messaging complexity.
- Ongoing parser maintenance as websites evolve.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Browser APIs remain in the infrastructure layer.
- Every supported platform implements the parser interface.
- Synchronization occurs only through the CareerOS API.
- Shared packages provide common models and validation.
- Content scripts never access the database directly.
- Business logic remains outside UI components.
- Extension permissions follow least privilege.
- Every parser includes dedicated tests.

Architectural changes require a new ADR.

# Decision Summary

CareerOS adopts a modular **Browser Extension Architecture** based on Manifest V3, layered design, and parser adapters. Browser-specific concerns are isolated from business logic, all synchronization flows through the CareerOS API, and shared packages provide common contracts and validation. This architecture supports maintainability, scalability, and reliable job capture across multiple recruitment platforms.
