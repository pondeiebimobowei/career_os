# ADR-005: Backend API Style

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS consists of multiple clients that communicate with a shared backend API.

Current clients include:

- Web Application
- Browser Extension
- Backlog CLI (future integrations)
- Internal Administration Tools (future)
- Mobile Application (future)

These clients require a stable, predictable, versioned API that is easy to consume, document, test, and maintain.

The API should:

- Be simple to understand
- Be easy to document
- Be strongly typed
- Support long-term evolution
- Minimize breaking changes
- Integrate well with TypeScript
- Support future client applications

---

# Decision

CareerOS will adopt a **RESTful API architecture** using **resource-oriented design**.

The API will be:

- Versioned
- JSON-based
- Stateless
- Type-safe
- Consistently structured
- Fully documented using OpenAPI

---

# Goals

The API should provide:

- Predictable resource naming
- Consistent request/response formats
- Clear error handling
- Strong validation
- Stable contracts
- Easy client integration
- Excellent developer experience

---

# API Style

The API follows REST principles.

Resources are represented by nouns.

Examples:

```text
/users

/companies

/jobs

/applications

/tasks

/resumes
```

Actions are represented by HTTP methods rather than verbs in URLs.

---

# URL Structure

The API follows this convention:

```text
/api/v1/{resource}
```

Examples:

```text
/api/v1/companies

/api/v1/jobs

/api/v1/applications

/api/v1/tasks
```

Future versions will increment the version segment.

```text
/api/v2/
```

---

# HTTP Methods

Standard HTTP methods are used consistently.

| Method | Purpose |
|----------|----------|
| GET | Retrieve resource(s) |
| POST | Create resource |
| PUT | Replace resource |
| PATCH | Partial update |
| DELETE | Remove resource |

---

# Resource Naming

Resources use plural nouns.

Examples:

```text
/users

/jobs

/tasks

/companies
```

Avoid:

```text
/getJobs

/createApplication

/deleteCompany
```

---

# Nested Resources

Nested resources are used only when ownership is explicit.

Example:

```text
GET

/companies/{companyId}/jobs
```

Avoid deep nesting.

Maximum recommended depth:

```text
/resource/id/resource
```

---

# Request Format

Requests use JSON.

Example:

```json
{
  "title": "Frontend Engineer",
  "location": "Remote",
  "employmentType": "Full-time"
}
```

All requests use UTF-8 encoding.

---

# Response Format

Successful responses return JSON.

Example:

```json
{
  "data": {
    "id": "job_123",
    "title": "Frontend Engineer"
  }
}
```

Collections return:

```json
{
  "data": [],
  "pagination": {}
}
```

---

# Standard Response Envelope

All successful responses follow a consistent envelope.

```json
{
  "data": {},
  "meta": {}
}
```

Optional metadata may include:

- Pagination
- Request ID
- Processing time

---

# Error Response Format

Errors use a consistent structure.

```json
{
  "error": {
    "code": "APPLICATION_NOT_FOUND",
    "message": "Application could not be found.",
    "details": []
  }
}
```

Error responses must never expose:

- Stack traces
- Database errors
- Internal implementation details
- Sensitive information

---

# HTTP Status Codes

Standard status codes are used.

| Status | Meaning |
|----------|----------|
| 200 | Success |
| 201 | Created |
| 204 | No Content |
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not Found |
| 409 | Conflict |
| 422 | Validation Error |
| 429 | Rate Limited |
| 500 | Internal Server Error |

---

# Validation

Every incoming request is validated before reaching business logic.

Validation includes:

- Required fields
- Data types
- Length constraints
- Enumerations
- Formats
- Business rules

Validation uses shared Zod schemas where possible.

---

Authentication uses **NestJS JWT & Social OAuth2 Authentication** (Google/Gmail, GitHub) issued directly by the CareerOS API.

Workflow:

```text
Client (Web / Extension)
        │
        ├── Local Credentials ──► POST /api/v1/auth/login
        │
        └── OAuth2 Provider ────► GET /api/v1/auth/google (or /github)
                                         │
                                         ▼
                        NestJS AuthService (verify OAuth profile / password)
                                         │
                                         ▼
                        Find or Create User (link googleId / githubId)
                                         │
                                         ▼
                        Issue NestJS JWT Access Token (+ Refresh Token)
                                         │
                                         ▼
                        API Authorization Header (Bearer <jwt_token>)
                                         │
                                         ▼
                        NestJS JwtAuthGuard (Passport JWT strategy)
                                         │
                                         ▼
                        Authenticated Request
```

The backend verifies incoming JWT Access Tokens via `JwtAuthGuard` before executing protected route controllers.

---

# Authorization

Authentication identifies the user.

Authorization determines what the user is allowed to access.

Authorization occurs inside the Application Layer.

Every protected endpoint performs authorization checks.

---

# Pagination

Collection endpoints support pagination.

Example:

```text
GET

/jobs?page=2&pageSize=20
```

Response:

```json
{
  "data": [],
  "pagination": {
    "page": 2,
    "pageSize": 20,
    "totalItems": 143,
    "totalPages": 8
  }
}
```

---

# Filtering

Filtering uses query parameters.

Example:

```text
/jobs?status=OPEN
```

Multiple filters:

```text
/jobs?status=OPEN&location=Remote
```

---

# Sorting

Sorting uses query parameters.

Example:

```text
/jobs?sort=createdAt
```

Descending:

```text
/jobs?sort=-createdAt
```

---

# Searching

Search uses query parameters.

Example:

```text
/jobs?search=frontend
```

Search behavior is documented per endpoint.

---

# Idempotency

Safe operations should be idempotent.

Examples:

- GET
- PUT
- DELETE

POST endpoints may support idempotency keys where duplicate submissions are possible.

---

# API Versioning

Breaking changes require a new API version.

Examples:

```text
/api/v1/

/api/v2/
```

Minor, backward-compatible changes may be introduced without version changes.

---

# Documentation

Every endpoint is documented using OpenAPI.

Documentation includes:

- Summary
- Description
- Parameters
- Request schema
- Response schema
- Error responses
- Authentication requirements
- Examples

---

# Rate Limiting

Protected endpoints may enforce rate limits.

Examples:

- Authentication
- Search
- Browser Extension synchronization

Rate limiting protects the platform from abuse.

---

# Logging

Every request records:

- Request ID
- User ID (when authenticated)
- Endpoint
- Method
- Response status
- Duration

Sensitive request data must not be logged.

---

# API Contracts

All request and response models are strongly typed.

Shared contracts should be reused by:

- Backend
- Frontend
- Browser Extension

Type duplication should be avoided.

---

# File Uploads

File uploads use multipart requests.

Example:

```text
POST

/resumes
```

Validation includes:

- MIME type
- File size
- Virus scanning (future)
- File extension

---

# Browser Extension API

The Browser Extension consumes the same REST API as the Web Application.

No extension-specific API should exist unless strictly necessary.

This ensures:

- Consistent behavior
- Reduced maintenance
- Shared authorization
- Shared validation

---

# Alternatives Considered

## GraphQL

Advantages:

- Flexible querying
- Reduced over-fetching

Rejected because:

- Increased complexity
- More difficult caching
- Higher learning curve
- REST sufficiently satisfies current product requirements

---

## RPC-style APIs

Example:

```text
/createApplication
```

Rejected because:

- Less resource-oriented
- Harder to evolve
- Less predictable

---

## Mixed API Styles

Rejected because:

- Inconsistent developer experience
- More difficult documentation
- Greater maintenance burden

---

# Consequences

## Positive

- Predictable endpoints
- Easy documentation
- Strong tooling support
- Better testing
- Stable contracts
- Easy frontend integration
- Easy Browser Extension integration
- Simpler AI reasoning

---

## Negative

- Some endpoints may return more data than necessary.
- Deeply customized queries may require additional endpoints.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- APIs are RESTful.
- Resources use plural nouns.
- JSON is the standard data format.
- APIs are versioned.
- OpenAPI documentation is required.
- Request validation is mandatory.
- Authentication uses NestJS JWT Bearer tokens.
- Error responses follow the standard error format.
- Response envelopes remain consistent.
- Business logic never resides in controllers.

Violations require architectural review.

# Decision Summary

CareerOS adopts a **RESTful, JSON-based, versioned API** using **resource-oriented design**. The API is stateless, documented with OpenAPI, validated using shared schemas, authenticated via NestJS JWT Bearer tokens, and follows consistent conventions for URLs, responses, errors, pagination, filtering, and versioning. This provides a stable, predictable contract for all current and future CareerOS clients.
