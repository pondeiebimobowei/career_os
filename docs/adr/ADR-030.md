# ADR-030: SOLID Principles and Clean Architecture

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is intended to be a long-lived software platform comprising multiple products, shared packages, backend services, browser extensions, and AI-assisted tooling.

As the codebase grows, uncontrolled coupling and inconsistent design can lead to:

- fragile code,
- difficult testing,
- duplicated business logic,
- tight framework coupling,
- poor maintainability,
- slow feature delivery.

CareerOS already adopts:

- Layered Architecture
- Feature-Based Organization
- Shared Packages
- Repository-First Planning

To ensure these architectural decisions remain maintainable over time, the project requires clear software design principles that govern implementation inside those architectural boundaries.

---

# Decision

CareerOS adopts **SOLID Principles** together with **Clean Architecture** as the primary design philosophy for application development.

These principles guide implementation decisions across all applications, services, packages, and libraries.

They are design guidelines—not rigid rules—and should be applied with engineering judgment.

---

# Goals

The architecture should:

- maximize maintainability,
- minimize coupling,
- improve testability,
- encourage modularity,
- isolate business rules,
- simplify refactoring,
- reduce framework dependence,
- support long-term scalability.

---

# Architectural Philosophy

CareerOS separates:

```text
Business Rules

↓

Application Logic

↓

Infrastructure

↓

Frameworks
```

Business rules remain the most stable part of the system.

External technologies are implementation details.

---

# Dependency Rule

Dependencies always point inward.

```text
Frameworks

↓

Infrastructure

↓

Application

↓

Domain
```

The domain layer depends on nothing outside itself.

Outer layers depend on inner layers.

Inner layers never depend on outer layers.

---

# Layer Responsibilities

## Domain

Contains:

- entities,
- value objects,
- business rules,
- domain services,
- domain events,
- repository contracts.

The domain layer contains no framework-specific code.

---

## Application

Coordinates use cases.

Responsibilities include:

- orchestration,
- validation,
- transaction boundaries,
- application services,
- command handlers,
- query handlers.

Application code depends on domain abstractions.

---

## Infrastructure

Implements technical concerns.

Examples:

- database repositories,
- file storage,
- HTTP clients,
- authentication providers,
- queues,
- logging.

Infrastructure implements interfaces defined by inner layers.

---

## Presentation

Responsible for:

- HTTP APIs,
- UI,
- browser extension interfaces,
- CLI,
- mobile screens.

Presentation delegates business work to application services.

---

# SOLID Principles

CareerOS applies all five SOLID principles where they improve maintainability.

---

# Single Responsibility Principle (SRP)

Each module should have one primary reason to change.

Examples:

- Repository handles persistence.
- Service coordinates business logic.
- Validator performs validation.
- Parser extracts data.

Avoid classes or modules with multiple unrelated responsibilities.

---

# Open/Closed Principle (OCP)

Software should be:

- open for extension,
- closed for modification.

New behavior should be introduced through extension rather than changing stable code whenever practical.

---

# Liskov Substitution Principle (LSP)

Implementations should be safely substitutable for their abstractions.

Consumers should not need special knowledge of specific implementations.

---

# Interface Segregation Principle (ISP)

Prefer small, focused interfaces.

Avoid large "god interfaces" that force implementations to provide unused behavior.

---

# Dependency Inversion Principle (DIP)

High-level modules should depend on abstractions.

Low-level modules implement those abstractions.

Example:

```text
Application

↓

Repository Interface

↓

Prisma Repository
```

The application layer remains independent of Prisma.

---

# Business Rules First

Business rules belong in the domain layer.

Examples:

- application lifecycle,
- resume matching,
- duplicate detection,
- analytics calculations.

Business logic should never depend on UI or persistence concerns.

---

# Framework Independence

Frameworks are implementation details.

Examples:

- React
- Hono
- Prisma
- PostgreSQL
- Browser APIs

Replacing a framework should have minimal impact on business logic.

---

# Database Independence

The domain model should not depend on database implementation.

Repository interfaces abstract persistence.

Infrastructure provides concrete implementations.

---

# UI Independence

User interface technologies should not influence business rules.

Whether functionality is accessed through:

- Web
- Browser Extension
- Mobile
- CLI

the same application and domain logic should be reused where appropriate.

---

# Testability

Business rules should be testable without:

- database,
- network,
- browser,
- framework,
- filesystem.

Domain and application layers should support isolated testing.

---

# Shared Packages

Shared packages should expose reusable abstractions.

Examples:

```text
packages/domain

packages/shared

packages/utils
```

Avoid leaking infrastructure-specific details into shared packages.

---

# Feature Organization

Feature-based organization complements Clean Architecture.

Within a feature:

```text
presentation

↓

application

↓

domain

↓

infrastructure
```

Each feature maintains clear internal boundaries.

---

# Error Handling

Errors should be:

- explicit,
- typed where appropriate,
- meaningful,
- recoverable when possible.

Business errors belong in the domain or application layers.

Infrastructure errors should be translated before crossing boundaries.

---

# Dependency Injection

Dependencies should be injected rather than instantiated directly.

Example:

Instead of:

```text
ApplicationService

↓

new PrismaClient()
```

Prefer:

```text
ApplicationService

↓

Repository Interface

↓

Injected Implementation
```

This improves flexibility and testability.

---

# Cross-Layer Communication

Allowed:

```text
Presentation

↓

Application

↓

Domain
```

Not allowed:

```text
Presentation

↓

Database
```

or

```text
Domain

↓

React
```

Layer boundaries should be respected.

---

# Code Reuse

Prefer:

- composition,
- shared abstractions,
- reusable services.

Avoid inheritance unless it provides a clear modeling benefit.

---

# AI-Assisted Development

AI-generated code must preserve:

- dependency direction,
- layer boundaries,
- abstractions,
- existing architecture.

AI should not introduce shortcuts that violate Clean Architecture.

---

# Refactoring

Refactoring should improve:

- cohesion,
- readability,
- dependency direction,
- testability,
- maintainability.

Behavioral changes should remain separate from structural refactoring whenever practical.

---

# Testing Strategy

Each layer has different testing priorities.

## Domain

- Unit tests

---

## Application

- Unit tests
- Integration tests

---

## Infrastructure

- Integration tests

---

## Presentation

- Integration tests
- End-to-end tests

---

# Alternatives Considered

## MVC

Rejected because:

- encourages business logic leakage,
- weaker separation of concerns.

---

## Framework-Centric Design

Rejected because:

- tight coupling,
- difficult testing,
- poor portability.

---

## Active Record Everywhere

Rejected because:

- persistence coupled to business rules,
- difficult abstraction,
- limited flexibility.

---

# Consequences

## Positive

- Better maintainability.
- Easier testing.
- Reduced coupling.
- Improved scalability.
- Framework independence.
- Cleaner architecture.
- Better AI-generated code consistency.

---

## Negative

- More abstractions.
- Slightly higher initial implementation cost.
- Additional architectural discipline required.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Business rules remain independent of frameworks.
- Dependencies always point inward.
- Application logic depends on abstractions rather than implementations.
- Infrastructure implements interfaces defined by inner layers.
- Layer boundaries are respected.
- SOLID principles guide software design.
- New code should improve or preserve architectural consistency.
- AI-generated code must comply with these principles.

Changes to the architectural design philosophy require a new ADR.

# Decision Summary

CareerOS adopts **SOLID Principles** and **Clean Architecture** as its primary software design philosophy. Business rules are isolated from frameworks and infrastructure, dependencies always point inward, application logic depends on abstractions, and each architectural layer has clearly defined responsibilities. These principles ensure the platform remains maintainable, testable, scalable, framework-independent, and well suited to long-term evolution and AI-assisted development.
