# ADR-012: Activity History

- **Status:** Superseded
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** ADR-043

---

# Context

CareerOS manages long-running workflows across multiple domains:

- Applications
- Companies
- Jobs
- Tasks
- Notes
- Resumes
- Browser Extension
- Notifications

Users need visibility into **what happened**, **when it happened**, and **why it happened**.

Examples include:

- An application was created.
- A pipeline status changed.
- A follow-up task was completed.
- A resume was attached.
- A browser extension captured a job.
- A note was added.

Without a centralized activity history:

- Users lose context.
- Auditing becomes difficult.
- Timeline views cannot be built.
- Notifications become disconnected.
- Analytics become less meaningful.
- AI features lack historical context.

Activity History must therefore be treated as a core domain rather than a UI convenience.

---

# Decision

CareerOS will maintain a centralized **Activity History** that records significant business events across the platform.

Activity History is:

- Append-only
- Chronological
- Immutable
- User-scoped
- Generated automatically

Activity History represents **facts** that occurred within the system.

It is not intended to store application state.

---

# Goals

The activity history should:

- Provide a complete audit trail.
- Power timeline views.
- Improve user understanding.
- Support analytics.
- Enable future AI capabilities.
- Support notifications.
- Simplify debugging.
- Preserve historical context.

---

# Principles

Activity History is:

- Immutable
- Chronological
- Human-readable
- Machine-readable
- Event-driven

Existing events are never modified.

Corrections generate new events.

# Timeline

Events are presented chronologically.

Example:

```text
10:45

Application Created

↓

10:46

Application Submitted

↓

13:15

Interview Scheduled

↓

17:20

Follow-up Task Created
```

Newest events appear first unless otherwise specified.

---

# Activity vs State

Activity History records **events**.

It does not represent the current state.

Example:

Current State:

```text
Interview
```

History:

```text
Created

↓

Applied

↓

Screening

↓

Interview
```

Current state belongs to domain entities.

History records how that state evolved.

---

# Immutability

Events are append-only.

Incorrect events are never edited.

Instead:

```text
Incorrect Event

↓

Correction Event
```

This preserves auditability.

---

# Metadata

Events may include structured metadata.

Example:

```json
{
  "previousStatus": "APPLIED",
  "newStatus": "INTERVIEW",
  "source": "KANBAN"
}
```

Metadata supports future analytics without changing the event model.

---

# User Ownership

Every event belongs to one user.

Users may only access their own activity history.

Administrative access follows separate authorization policies.

---

# API Representation

Example:



# Integration with Notifications

Notifications are generated from activity events.

Example:

```text

↓

Activity Event

↓

Notification
```

Notifications do not create activity events themselves unless a user action occurs.

---

# Analytics

Activity History enables metrics such as:

- Daily activity
- Weekly activity
- User engagement
- Pipeline velocity
- Automation usage

Analytics consumes activity events but does not modify them.

---

# AI Integration

Future AI capabilities may analyze activity history to:

- Recommend follow-ups.
- Detect inactivity.
- Identify application patterns.
- Generate weekly summaries.
- Suggest productivity improvements.

The immutable event stream provides valuable historical context.

---

# Retention

Activity History is retained for the lifetime of the user's account unless deleted through account deletion or legal data removal processes.

Events are not automatically purged during normal operation.

---

# Alternatives Considered

## No Activity History

Advantages:

- Simpler implementation.

Rejected because:

- No audit trail.
- Poor user visibility.
- Weak analytics.

---

## Editable Timeline

Rejected because:

- Breaks audit integrity.
- Difficult to reason about historical events.

---

## Separate Timelines Per Domain

Rejected because:

- Fragmented user experience.
- Harder cross-domain reporting.
- Duplicated infrastructure.

---

# Consequences

## Positive

- Complete audit history.
- Better user experience.
- Strong analytics foundation.
- Improved debugging.
- Future AI support.
- Consistent cross-domain timeline.

---

## Negative

- Increased storage requirements.
- Additional event generation logic.
- Larger database over time.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Activity History is append-only.
- Events are immutable.
- Events originate from application services.
- The UI never writes directly to Activity History.
- Every event belongs to one user.
- Timeline ordering is chronological.
- Metadata remains structured and machine-readable.
- Analytics consume activity events without modifying them.

Changes to the Activity History model require a new ADR.

# Decision Summary

CareerOS adopts a centralized, immutable **Activity History** that records significant business events across the platform. Activity History is append-only, user-scoped, and automatically generated by application services. It serves as the foundation for timeline views, auditing, analytics, notifications, debugging, and future AI-powered insights while remaining separate from the application's current state.
