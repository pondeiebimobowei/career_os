# ADR-017: Resume Library Design

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

Job seekers rarely use a single resume throughout their job search.

Instead, they often maintain multiple tailored versions for different roles, industries, or levels of experience.

Examples include:

- Frontend Resume
- Backend Resume
- Full Stack Resume
- Mobile Resume
- Product Engineer Resume
- Senior Engineer Resume

Users also need to know which resume was submitted with each application.

Without a dedicated resume management system:

- Resume files become difficult to organize.
- Users lose track of which resume was used.
- Analytics cannot correlate resume usage with outcomes.
- Future AI features cannot recommend the most effective resume.

Resume management is therefore a first-class domain within CareerOS.

---

# Decision

CareerOS will implement a dedicated **Resume Library** that allows users to upload, organize, manage, and associate multiple resumes with applications.

The Resume Library manages **resume assets and metadata**, not resume authoring.

CareerOS is not a document editor in the MVP.

---

# Goals

The Resume Library should:

- Store multiple resumes.
- Associate resumes with applications.
- Track resume metadata.
- Support secure file storage.
- Enable future analytics.
- Support future AI recommendations.
- Keep resume history immutable.

---

# Scope

The Resume Library manages:

- Resume uploads
- Resume metadata
- Resume versions
- Resume associations
- Resume previews
- Resume downloads
- Resume deletion
- Default resume selection

It does **not** manage:

- Resume editing
- Resume generation
- Resume templates
- PDF rendering

These may be added in future releases.

---

# Domain Model

Core entities include:

```text
Resume

↓

Resume Version

↓

Application Association
```

A resume is a user-owned document that may be linked to many applications.

---

# High-Level Architecture

```text
User

↓

Resume Library

↓

Metadata

+

File Storage

↓

Application

↓

Analytics
```

The library separates metadata from binary file storage.

---

# Resume Entity

Each resume includes metadata such as:

- Resume ID
- User ID
- Display Name
- Original Filename
- Storage Key
- MIME Type
- File Size
- Created At
- Updated At

The binary file is stored separately.

---

# File Storage

Resume files are stored outside the relational database.

Recommended storage:

- Cloud object storage
- S3-compatible storage
- Local development storage

The database stores only references.

---

# Supported Formats

MVP supports:

- PDF

Future support may include:

- DOCX
- ODT

PDF is preferred because formatting remains consistent across devices.

---

# Resume Metadata

Metadata includes:

```text
Resume

↓

Name

Role

Tags

Version

Default Flag
```

Metadata enables search and filtering without accessing file contents.

---

# Default Resume

Users may designate one resume as their default.

The default resume is automatically selected during application creation unless overridden.

Only one default resume is allowed per user.

---

# Resume Associations

Applications reference resumes.

Relationship:

```text
Resume

1

↓

Many

↓

Applications
```

This preserves which resume was submitted with each application.

---

# Resume Versioning

Resume revisions create new versions rather than overwriting previous files.

Example:

```text
Frontend Resume

↓

v1

↓

v2

↓

v3
```

Applications continue referencing the version originally submitted.

---

# Immutability

Previously submitted resumes remain immutable.

Updating a resume creates a new version rather than modifying existing historical records.

This preserves auditability.

---

# Upload Workflow

```text
Upload File

↓

Validate

↓

Virus Scan (future)

↓

Store File

↓

Create Metadata

↓

Return Resume
```

The upload completes only after both storage and metadata persistence succeed.

---

# Validation

Uploads are validated for:

- File type
- Maximum size
- Supported MIME type

Invalid uploads are rejected before storage.

---

# Preview

Users can preview uploaded resumes without downloading them.

The preview is read-only.

Rendering implementation is infrastructure-specific.

---

# Download

Users may download any resume version they own.

Authorization is enforced before generating access URLs.

---

# Delete Strategy

Deleting a resume:

- Removes it from active use.
- Prevents new associations.
- Does not invalidate historical application references.

Physical deletion of stored files follows retention policies.

---

# Search & Filtering

Users can search resumes by:

- Name
- Tags
- Role
- Creation date
- Last updated

Search operates on metadata.

---

# Storage Keys

Files are identified by opaque storage keys.

Example:

```text
resume_01JXYZABCD1234567890.pdf
```

File paths are never derived directly from user input.

---

# Security

Security requirements include:

- User ownership enforcement
- Authorization checks
- Signed download URLs
- File validation
- MIME verification
- Storage isolation

Users cannot access another user's resumes.

---

# Browser Extension Integration

The browser extension may retrieve the user's default resume during job application workflows.

The extension does not upload or modify resumes directly.

---

# Application Integration

During application creation:

```text
Application

↓

Resume Selection

↓

Association Created
```

Applications always reference a specific resume version.

---

# Analytics

Resume metadata enables future insights including:

- Resume usage frequency
- Interview rate by resume
- Offer rate by resume
- Resume effectiveness over time

Analytics consume metadata without accessing binary files.

---

# AI Integration

Future AI features may include:

- Resume recommendations
- Resume-to-job matching
- Missing skills detection
- Resume optimization suggestions

AI systems analyze structured metadata and extracted content where appropriate.

---

# Backup & Recovery

Resume metadata is backed up with the database.

Binary files follow storage provider backup strategies.

Recovery procedures must restore both metadata and associated files.

---

# Database Model

Recommended tables:

```text

application_resumes
```

Binary files remain outside PostgreSQL.

# Alternatives Considered

## Single Resume Per User

Advantages:

- Simpler implementation.

Rejected because:

- Does not reflect real-world job searches.
- Prevents tailored applications.

---

## Store Files in PostgreSQL

Rejected because:

- Larger database size.
- Poor scalability.
- Backup inefficiencies.

---

## Overwrite Existing Files

Rejected because:

- Breaks historical accuracy.
- Loses application context.
- Weak auditability.

---

# Consequences

## Positive

- Organized resume management.
- Historical accuracy.
- Better analytics.
- Strong audit trail.
- Future AI readiness.
- Scalable file storage.

---

## Negative

- Additional storage infrastructure.
- Version management complexity.
- File lifecycle management.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Resume files are stored outside PostgreSQL.
- Metadata resides in the database.
- Users may own multiple resumes.
- Applications reference specific resume versions.
- Resume updates create new versions.
- Historical associations are immutable.
- Authorization is enforced for every file operation.
- Metadata and file storage remain synchronized.

Changes to the Resume Library architecture require a new ADR.

# Decision Summary

CareerOS adopts a dedicated **Resume Library** that manages user-owned resume files, metadata, version history, and application associations. Resume files are stored in external object storage while PostgreSQL maintains structured metadata and relationships. Applications reference immutable resume versions, providing historical accuracy, scalable storage, reliable auditing, and a strong foundation for analytics and future AI-powered resume recommendations.
