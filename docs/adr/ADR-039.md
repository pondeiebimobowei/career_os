# ADR-039 — Error Tracking & Incident Management Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS consists of multiple independently deployed applications that interact continuously.

Current architecture includes:

- Backend API
- Web Application
- Browser Extension
- Shared Packages
- GitHub Actions
- PostgreSQL
- Cloudflare
- Coolify

Despite comprehensive testing, failures will inevitably occur in production.

Examples include:

- Unexpected runtime exceptions
- Parser failures after website changes
- Synchronization failures
- Database connectivity issues
- Authentication errors
- Browser API changes
- Third-party service outages
- Infrastructure failures

Logging alone is insufficient.

Logs answer:

> "What happened?"

Error tracking answers:

> "Which errors are affecting users right now?"

CareerOS therefore requires centralized error collection, grouping, alerting, and incident management.

---

# Decision

CareerOS will implement centralized error tracking across every production application.

The strategy consists of:

1. Automatic exception capture
2. Error grouping
3. Stack trace collection
4. Context enrichment
5. Release tracking
6. User impact analysis
7. Incident response workflow

Error tracking complements—not replaces—structured logging.

---

# Architecture

```text
Application

↓

Exception

↓

Error Tracker SDK

↓

Central Error Platform

↓

Grouping

↓

Alerting

↓

Incident Dashboard

↓

Engineering Team
```

Every production application participates in the same error tracking pipeline.

---

# Goals

The platform should answer:

- Which errors are occurring?
- How often?
- Which release introduced them?
- Which users are affected?
- Which environments are impacted?
- Is the error new?
- Has it already been fixed?

---

# Scope

Error tracking applies to:

- Backend API
- Web Application
- Browser Extension
- Background jobs
- CLI tools (optional)
- Deployment automation (where applicable)

---

# Automatic Exception Capture

Unhandled exceptions should automatically be reported.

Examples:

- runtime exceptions
- promise rejections
- uncaught exceptions
- parser failures
- rendering failures

Manual reporting should rarely be necessary.

---

# Manual Error Reporting

Expected failures that require visibility may be reported manually.

Examples:

- synchronization failure
- third-party API failure
- repeated parser fallback
- storage failures

Manual reports should include structured context.

---

# Error Severity

Errors are classified consistently.

## Critical

System unavailable.

Examples:

- API unavailable
- database unavailable
- authentication unavailable

Immediate response required.

---

## High

Core functionality broken.

Examples:

- imports failing
- resume uploads failing
- synchronization unavailable

---

## Medium

Feature degradation.

Examples:

- parser partially failing
- analytics unavailable
- notification failures

---

## Low

Minor issues.

Examples:

- UI rendering issue
- non-blocking warning
- recoverable client error

---

# Error Context

Every captured error should include:

```text
Timestamp

Application

Version

Environment

Request ID

Correlation ID

User ID (if authenticated)

Module

Platform

Browser

Operating System
```

Context should support rapid diagnosis.

---

# Browser Extension Context

Extension reports should include:

- browser version
- extension version
- detected platform
- parser version
- synchronization status
- page URL (sanitized)
- manifest version

Sensitive browsing information must never be transmitted.

---

# Backend Context

Backend reports include:

- endpoint
- HTTP method
- response status
- request duration
- authenticated user
- deployment version

Secrets must never appear in reports.

---

# Release Tracking

Every deployment includes a release identifier.

Example:

```text
v1.4.2
```

Errors should be grouped by release to identify regressions.

---

# Error Grouping

Identical failures should be grouped automatically.

Grouping considers:

- stack trace
- exception type
- module
- message

Grouping prevents alert fatigue.

---

# Duplicate Suppression

Repeated occurrences of the same failure should increment occurrence counts rather than create new incidents.

Example:

```text
ParserException

Occurrences:

1

↓

24

↓

315
```

Engineering should focus on unique failures.

---

# User Impact

Track:

- affected users
- affected sessions
- first occurrence
- last occurrence
- frequency

Impact helps prioritize fixes.

---

# Incident Lifecycle

Every incident progresses through:

```text
Detected

↓

Triaged

↓

Assigned

↓

Investigating

↓

Fix Implemented

↓

Verified

↓

Resolved
```

Incident state should be visible to the engineering team.

---

# Notifications

Critical incidents trigger alerts.

Examples:

- Slack
- Email
- Pager (future)

Alerts should contain:

- severity
- application
- release
- occurrence count
- first occurrence
- latest occurrence

---

# Source Maps

Frontend builds should upload source maps.

Benefits:

- readable stack traces
- accurate source locations
- easier debugging

Source maps should not be publicly accessible.

---

# Parser Failures

Every parser exception should include:

- parser name
- parser version
- platform
- page type
- normalization stage

DOM contents should never be uploaded.

---

# Privacy

Never collect:

- passwords
- JWTs
- OAuth tokens
- API keys
- resume contents
- uploaded documents
- payment information

Personal data should be minimized and redacted where possible.

---

# Performance

Error reporting should:

- execute asynchronously
- avoid blocking requests
- retry failed submissions
- batch events where appropriate

Reporting should not noticeably impact user experience.

---

# Sampling

High-volume environments may sample low-priority events.

Critical events are never sampled.

Example:

```text
Critical

100%

High

100%

Medium

50%

Low

10%
```

Sampling policies should be configurable.

---

# Offline Behavior

Browser Extension:

If offline:

- queue reports
- retry later
- discard expired reports after retention limits

Users should not experience degraded functionality because of telemetry.

---

# Testing

Error tracking should be verified by automated tests.

Validate:

- exception capture
- stack traces
- source maps
- context enrichment
- duplicate grouping
- release association

---

# AI Assistant Rules

AI-assisted development must:

- preserve existing error reporting
- maintain contextual metadata
- avoid swallowing exceptions
- report unexpected failures
- never expose sensitive data in reports

Removing error tracking requires architectural approval.

---

# Operational Metrics

Track:

- new incidents
- resolved incidents
- mean time to detect (MTTD)
- mean time to acknowledge (MTTA)
- mean time to resolve (MTTR)
- recurring incidents

These metrics help improve operational maturity.

---

# Incident Reviews

Critical incidents should produce a post-incident review including:

- timeline
- root cause
- contributing factors
- customer impact
- corrective actions
- preventive actions

Reviews focus on improving systems rather than assigning blame.

---

# Integration with Logging

Error tracking complements structured logging.

Relationship:

```text
Logs

↓

Context

↓

Error Event

↓

Incident

↓

Resolution
```

Every error should be traceable back to correlated logs.

---

# Consequences

## Positive

- Faster incident detection
- Better production visibility
- Improved regression detection
- Easier debugging
- Reduced duplicate investigations
- Improved release confidence

## Negative

- Additional operational infrastructure
- Storage costs
- Alert maintenance
- SDK integration effort
- Ongoing incident management responsibilities

---

# Compliance

All CareerOS production applications, browser extensions, backend services, and future client applications must implement this centralized error tracking strategy.

Any deviation requires an approved Architecture Decision Record (ADR).
