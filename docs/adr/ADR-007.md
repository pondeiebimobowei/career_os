# ADR-007: Prisma ORM

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS uses PostgreSQL as its primary relational database (see ADR-006).

The application requires a data access layer that provides:

- Strong TypeScript support
- Type-safe database queries
- Schema versioning
- Reliable migrations
- Good developer experience
- Transaction support
- Predictable query generation
- Maintainable database interactions

Direct SQL queries scattered throughout the application would increase duplication, reduce maintainability, and make future schema changes more difficult.

The platform requires a single, consistent approach to database access.

---

# Decision

CareerOS will use **Prisma ORM** as its primary Object-Relational Mapping (ORM) and database access tool.

Prisma will be responsible for:

- Schema definition
- Type generation
- Query execution
- Database migrations
- Transaction management
- Seed data
- Development tooling

All application database access must go through Prisma repositories or services.

---

# Goals

Prisma should provide:

- Type-safe queries
- Centralized schema management
- Predictable migrations
- Excellent developer experience
- Reduced runtime errors
- Easy refactoring
- Strong IDE support
- Consistent data access

---

# Why Prisma

Prisma was selected because it offers:

- First-class TypeScript support
- Automatically generated types
- Excellent migration tooling
- Modern developer experience
- Comprehensive documentation
- Active ecosystem
- Strong PostgreSQL support

Prisma aligns closely with CareerOS's TypeScript-first engineering strategy.

---

# Prisma Responsibilities

Prisma is responsible for:

- Database schema definition
- Migration generation
- Query execution
- Transactions
- Seed scripts
- Type generation
- Connection management

Prisma is **not** responsible for:

- Business rules
- Authorization
- Domain validation
- Application workflows

These remain outside the ORM.

---

# Schema Management

The database schema is defined using:

```text
schema.prisma
```

This file represents the canonical database model.

Changes to the database schema must originate from this file.

---

# Migration Strategy

Schema changes are managed using Prisma Migrations.

Typical workflow:

```text
Update schema.prisma

↓

Generate Migration

↓

Review Migration

↓

Commit Migration

↓

Deploy Migration
```

Manual production schema changes are prohibited.

---

# Repository Pattern

Application services must not call Prisma directly.

Instead:

```text
Application Service

↓

Repository Interface

↓

Prisma Repository

↓

Prisma Client

↓

PostgreSQL
```

This provides:

- Testability
- Decoupling
- Easier future migrations
- Better separation of concerns

---

# Type Safety

Prisma generates strongly typed models.

Benefits include:

- Compile-time validation
- Safer refactoring
- Better autocomplete
- Reduced runtime failures

Application code should rely on generated types where appropriate.

---

# Transactions

Prisma transactions should be used when multiple operations must succeed or fail together.

Examples:

- Creating an application and pipeline state
- Updating application status and activity history
- Import workflows
- Bulk operations

Transactions protect data consistency.

---

# Query Principles

Queries should be:

- Explicit
- Predictable
- Efficient
- Readable

Avoid:

- Hidden side effects
- Excessive nesting
- Unbounded queries
- N+1 query patterns

---

# Pagination

Large result sets must use pagination.

Preferred methods:

- Cursor pagination
- Offset pagination (where appropriate)

Endpoints must never return unbounded collections.

---

# Eager Loading

Relationships should be loaded intentionally.

Example:

```typescript
include: {
  company: true,
  job: true,
}
```

Only load required relationships.

Avoid unnecessary over-fetching.

---

# Raw SQL

Raw SQL is permitted only when Prisma cannot efficiently express a query.

Examples include:

- Advanced reporting
- Database-specific features
- Performance-critical operations

Raw SQL must:

- Be parameterized
- Be reviewed
- Include justification
- Avoid SQL injection risks

---

# Validation

Prisma is not responsible for request validation.

Validation occurs before database interaction using shared Zod schemas.

Prisma constraints complement—but do not replace—application-level validation.

---

# Connection Management

A single Prisma Client instance should be reused within each application process.

Benefits include:

- Efficient connection pooling
- Lower memory usage
- Predictable behavior

Creating multiple Prisma Client instances unnecessarily should be avoided.

---

# Seeding

Development and testing environments should use Prisma Seed scripts.

Seed data may include:

- Test users
- Sample companies
- Sample jobs
- Demo applications
- Pipeline stages

Production seed data must be carefully controlled.

---

# Testing

Tests should avoid relying on production data.

Preferred approaches:

- Dedicated test database
- Transaction rollback
- Seeded fixtures

Prisma repositories should be mockable for unit tests.

---

# Performance

Performance best practices include:

- Proper indexing
- Select only required fields
- Avoid excessive includes
- Batch operations where possible
- Analyze slow queries

Performance optimization should be driven by measurement.

---

# Error Handling

Prisma exceptions should be translated into domain or application errors.

Example:

```text
Prisma Unique Constraint Error

↓

DuplicateCompanyError
```

Infrastructure-specific exceptions should not leak into higher layers.

---

# Soft Deletes

Soft-delete logic should be implemented consistently.

Repositories should:

- Exclude deleted records by default
- Provide explicit methods for accessing deleted data when required

---

# Auditing

Common audit fields include:

- createdAt
- updatedAt
- deletedAt

Repositories should maintain these fields consistently.

---

# Development Workflow

Typical workflow:

```text
Modify schema.prisma

↓

Generate migration

↓

Apply migration

↓

Generate Prisma Client

↓

Run tests

↓

Commit changes
```

# Alternatives Considered

## Drizzle ORM

Advantages:

- Lightweight
- SQL-first approach

Rejected because:

- Prisma provides a more mature migration system and a stronger overall developer experience for the current team.

---

## TypeORM

Advantages:

- Mature ecosystem

Rejected because:

- Decorator-based model
- Weaker TypeScript ergonomics
- More runtime complexity

---

## Knex

Advantages:

- Flexible query builder

Rejected because:

- Lacks generated types
- Requires additional tooling for schema management
- Less integrated developer experience

---

## Direct SQL

Advantages:

- Maximum flexibility

Rejected because:

- Increased maintenance
- Reduced type safety
- Higher likelihood of runtime errors
- More duplicated query logic

---

# Consequences

## Positive

- Strong type safety
- Better developer experience
- Reliable migrations
- Centralized schema
- Easier refactoring
- Predictable queries
- Excellent PostgreSQL integration

---

## Negative

- Learning curve for Prisma schema language
- Generated client must remain synchronized with schema
- Some advanced SQL features require raw queries

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Database access uses Prisma.
- Schema changes originate from `schema.prisma`.
- Migrations are generated through Prisma.
- Application services access data through repositories.
- Raw SQL requires justification and review.
- Validation occurs before database interaction.
- Prisma exceptions are translated into application-level errors.
- A single Prisma Client instance is reused per application process.

Technology changes require a new ADR.

# Decision Summary

CareerOS adopts **Prisma ORM** as the standard data access layer for PostgreSQL. Prisma provides a type-safe, schema-driven development workflow with reliable migrations, generated TypeScript models, and a modern developer experience. All database interactions will be encapsulated behind repository abstractions, ensuring a maintainable, testable, and scalable persistence layer.
