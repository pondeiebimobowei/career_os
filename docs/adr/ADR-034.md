# ADR-034: Browser Extension Testing Strategy

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

The CareerOS Browser Extension is a first-class product responsible for:

- detecting supported job boards,
- extracting job information,
- normalizing data,
- communicating with CareerOS,
- importing applications,
- maintaining synchronization,
- assisting users while browsing jobs.

Unlike traditional web applications, browser extensions execute across multiple isolated runtime environments:

- Popup
- Options Page
- Content Scripts
- Background Service Worker
- Browser Storage
- Runtime Messaging
- Web Navigation APIs

These execution contexts introduce unique testing requirements.

Failures within the extension can lead to:

- incorrect job extraction,
- duplicate applications,
- synchronization failures,
- broken user workflows,
- browser compatibility issues.

CareerOS therefore requires a dedicated testing strategy for the browser extension.

---

# Decision

CareerOS adopts a **layered browser extension testing strategy** that validates functionality at the unit, integration, parser, browser, and end-to-end levels.

Testing is mandatory for all production extension features.

---

# Goals

The testing strategy should:

- ensure reliable job extraction,
- validate parser correctness,
- detect browser-specific regressions,
- protect synchronization workflows,
- support rapid iteration,
- maintain compatibility across supported browsers,
- provide confidence for AI-assisted development.

---

# Testing Philosophy

Browser extension testing follows the same engineering principles as the rest of the platform:

- automate wherever practical,
- test observable behavior,
- isolate business logic,
- verify complete workflows.

The extension should be testable without relying exclusively on manual browser testing.

---

# Testing Pyramid

```text
          Browser E2E

     Extension Integration

 Parser & Component Tests

          Unit Tests
```

Most tests should remain fast, deterministic unit tests.

---

# Runtime Coverage

Each runtime context is tested independently.

| Runtime | Testing Required |
|---------|------------------|
| Content Scripts | Yes |
| Background Service Worker | Yes |
| Popup UI | Yes |
| Options Page | Yes |
| Browser Storage | Yes |
| Runtime Messaging | Yes |

---

# Unit Testing

Unit tests verify isolated logic.

Examples:

- utility functions,
- URL detection,
- parser helpers,
- normalization,
- duplicate detection,
- validation.

Unit tests should execute without launching a browser.

---

# Parser Testing

Every parser must include comprehensive automated tests.

Coverage includes:

- supported pages,
- missing fields,
- malformed HTML,
- optional fields,
- localization,
- edge cases,
- duplicate detection.

Parser accuracy is considered mission-critical.

---

# HTML Fixture Testing

Parser tests should primarily use saved HTML fixtures rather than live websites.

Benefits include:

- deterministic execution,
- no network dependency,
- reproducible failures,
- stable CI.

Fixtures should represent real production pages.

---

# Normalization Testing

After extraction, normalized job models should be verified.

Examples:

- company name,
- job title,
- location,
- salary,
- employment type,
- remote status,
- application URL.

Normalization must produce consistent CareerOS domain models regardless of source.

---

# Content Script Testing

Content scripts should be tested for:

- page detection,
- DOM extraction,
- parser execution,
- runtime messaging,
- duplicate prevention,
- error handling.

Content scripts should degrade gracefully when unsupported pages are encountered.

---

# Background Service Worker Testing

Background services should be tested for:

- message routing,
- synchronization,
- authentication,
- browser events,
- retries,
- alarms,
- notifications.

Background logic should remain deterministic.

---

# Popup Testing

Popup tests should verify:

- rendering,
- application state,
- loading states,
- empty states,
- user interactions,
- error handling.

Presentation behavior should remain independent of browser APIs where practical.

---

# Options Page Testing

Configuration pages should verify:

- preference persistence,
- account connection,
- parser settings,
- synchronization options.

Configuration should remain stable across browser sessions.

---

# Browser Storage Testing

Storage behavior should verify:

- reads,
- writes,
- migrations,
- cache invalidation,
- corruption recovery.

Storage failures should not corrupt application state.

---

# Runtime Messaging

Messaging tests should verify communication between:

```text
Popup

↓

Background

↓

Content Script
```

Messages should:

- validate payloads,
- handle failures,
- remain backward compatible where required.

---

# Synchronization Testing

Synchronization tests verify:

- authentication,
- upload,
- retry behavior,
- conflict handling,
- offline recovery,
- duplicate prevention.

Synchronization should remain idempotent.

---

# Browser Compatibility

The extension must be tested against supported browsers.

Initial targets:

- Google Chrome
- Microsoft Edge

Future browser support should extend existing test coverage.

---

# UI Component Testing

Shared UI components should include:

- rendering tests,
- interaction tests,
- accessibility verification,
- keyboard navigation where applicable.

Visual regressions should be minimized.

---

# End-to-End Testing

Critical workflows should be automated.

Examples:

- visiting a supported job page,
- detecting a job,
- importing into CareerOS,
- viewing success notification,
- preventing duplicate imports.

These workflows validate the extension as users experience it.

---

# Error Handling

Tests should verify:

- unsupported pages,
- parser failures,
- missing permissions,
- offline mode,
- malformed responses,
- expired authentication.

Failures should remain recoverable whenever possible.

---

# Performance Testing

Extension performance should be evaluated for:

- parser execution time,
- popup startup,
- background responsiveness,
- synchronization latency.

The extension should avoid unnecessary DOM traversal and expensive operations.

---

# Security Testing

Security-related tests include:

- message validation,
- origin validation,
- permission enforcement,
- storage protection,
- authentication handling.

Browser APIs should never be trusted without validation.

---

# Mocking Strategy

Mock only browser infrastructure.

Examples:

- Chrome APIs,
- storage,
- runtime messaging,
- alarms,
- notifications.

Business logic and parser behavior should remain real.

---

# Test Data

Test fixtures should include:

- complete job pages,
- partial job pages,
- invalid pages,
- archived jobs,
- remote jobs,
- localized pages.

Fixtures should remain version-controlled.

---

# Continuous Integration

Every pull request affecting the extension executes:

- type checking,
- linting,
- unit tests,
- parser tests,
- integration tests,
- build verification.

Failures block merging.

---

# AI-Assisted Development

AI-generated extension code must include:

- parser tests,
- unit tests,
- runtime validation,
- updated fixtures when necessary.

AI should reuse existing testing utilities rather than introducing inconsistent patterns.

---

# Regression Testing

Every parser bug should produce a new regression test.

Bug fixes without corresponding tests are considered incomplete.

---

# Definition of Done

An extension feature is complete only when:

- implementation is finished,
- parser tests pass,
- integration tests pass,
- browser workflows succeed,
- documentation is updated,
- CI succeeds,
- review is approved.

---

# Alternatives Considered

## Manual Browser Testing

Rejected because:

- unreliable,
- time-consuming,
- difficult to reproduce.

---

## Unit Tests Only

Rejected because:

- browser runtime remains unverified,
- messaging failures go undetected.

---

## Live Website Testing Only

Rejected because:

- websites change frequently,
- unreliable CI,
- network dependency.

---

# Consequences

## Positive

- Reliable parser behavior.
- Stable browser workflows.
- Safer releases.
- Faster regression detection.
- Better AI-generated code quality.
- Improved cross-browser confidence.

---

## Negative

- Larger fixture library.
- Additional browser test infrastructure.
- Ongoing maintenance as supported job boards evolve.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every parser includes automated tests.
- Browser runtime messaging is tested.
- HTML fixture-based parser tests are maintained.
- Critical workflows include end-to-end coverage.
- Browser APIs are mocked appropriately in unit tests.
- Regression bugs include new automated tests.
- CI validates extension functionality before merge.
- AI-generated extension features include corresponding tests.

Changes to the browser extension testing strategy require a new ADR.

# Decision Summary

CareerOS adopts a **layered browser extension testing strategy** that combines unit, parser, integration, browser runtime, and end-to-end testing to ensure reliable operation across all supported environments. Every parser is validated using deterministic HTML fixtures, browser messaging and synchronization are thoroughly tested, and critical user workflows are automated. Testing is integrated into continuous integration and is a mandatory part of the definition of done for all browser extension features, ensuring a stable, maintainable, and production-ready extension.
