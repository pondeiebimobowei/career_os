# ADR-044 — Security Architecture & Threat Model

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-037 (Secret Management)
- **Superseded By:** None

---

# Context

CareerOS manages sensitive user information including:

- User accounts
- Authentication credentials
- Job applications
- Resume metadata
- Resume files
- Activity history
- Browser Extension synchronization
- Analytics
- Personal settings

The platform also communicates with external systems including:

- Browser APIs
- Recruitment platforms
- Cloud infrastructure
- GitHub
- Cloudflare
- Email providers

Because CareerOS processes personally identifiable information (PII), security must be considered a foundational architectural concern rather than an implementation detail.

Every application, service, and deployment pipeline must operate under a consistent security model.

---

# Decision

CareerOS adopts a **Defense in Depth** security architecture.

Security is implemented through multiple independent layers:

1. Identity & Authentication
2. Authorization
3. Secure Communication
4. Data Protection
5. Infrastructure Security
6. Browser Extension Security
7. Secure Development Practices
8. Monitoring & Incident Response

No single security control should be relied upon exclusively.

---

# Security Principles

The platform follows these principles:

- Least Privilege
- Zero Trust
- Fail Secure
- Secure by Default
- Defense in Depth
- Principle of Explicit Access
- Privacy by Design
- Immutable Auditability

Security requirements take precedence over implementation convenience.

- API abuse

- browser exploitation

## Malicious Users

Examples:

- unauthorized data access
- privilege escalation
- excessive API usage
- manipulation of client requests

---

## Compromised Clients

Examples:

- modified Browser Extensions
- automated scripts
- replay attacks
- forged requests

## Infrastructure Risks

Examples:

- server compromise

- deployment misconfiguration

---

## Third-Party Risks

Examples:

# Trust Boundaries

CareerOS defines explicit trust boundaries.

```text
Browser

↓

Browser Extension

↓

HTTPS

↓

Backend API

↓

Database

↓

Storage
```

Only the Backend API is trusted to enforce business rules.

Clients are never trusted.

---

# Authentication

Authentication verifies user identity.

Supported mechanisms:

- Email + Password
- OAuth providers (future)
- Password reset
- Session refresh

Authentication is centralized in the Backend API.

---

# Password Storage

Passwords must never be stored in plain text.

Requirements:

- strong password hashing
- unique salt
- adaptive hashing algorithm

Passwords are never recoverable.

Only password reset workflows are supported.

---

# Session Management

Sessions must support:

- expiration
- renewal
- revocation
- logout from all devices (future)

Session identifiers must be cryptographically secure.

---

# Authorization

Authorization determines what authenticated users may access.

The platform enforces:

- ownership-based authorization
- resource-level authorization
- server-side enforcement

Every protected endpoint validates authorization.

---

# Browser Extension Security

The Browser Extension must never:

- contain backend secrets
- bypass API authorization
- access unsupported domains
- execute remote code
- store privileged credentials

The extension acts as an untrusted client.

---

# Principle of Least Privilege

Every system component receives only the permissions it requires.

Examples:

Database account:

- read/write application data

No administrative permissions.

Cloudflare token:

- DNS management only

GitHub token:

- repository automation only

---

# Secure Communication

All communication uses HTTPS.

Requirements:

- TLS encryption
- certificate validation
- secure cookies where applicable

Plain HTTP is not supported in production.

---

# API Security

Every API endpoint should implement:

- authentication
- authorization
- request validation
- rate limiting
- structured error responses

Input is never trusted.

---

# Input Validation

All external input is validated using shared Zod schemas.

Validation applies to:

- API requests
- Browser Extension payloads
- query parameters
- configuration
- synchronization events

Invalid requests fail before business logic executes.

---

# Output Encoding

Applications must safely encode untrusted output.

Examples:

- HTML rendering
- Markdown rendering
- URLs
- user-generated content

Output encoding reduces cross-site scripting (XSS) risks.

---

# SQL Injection Protection

Database access uses Prisma ORM.

Requirements:

- parameterized queries
- ORM abstractions
- no dynamic SQL without explicit review

Raw SQL should be avoided unless justified.

---

# Cross-Site Scripting (XSS)

Mitigation includes:

- output encoding
- React escaping
- Content Security Policy
- input validation

User-generated content should never execute as code.

---

# Cross-Site Request Forgery (CSRF)

State-changing operations must protect against CSRF where cookie-based authentication is used.

Token-based authentication should follow established best practices.

---

# Content Security Policy

The Web Application should define a restrictive CSP.

Goals:

- prevent inline script execution
- restrict external resources
- reduce XSS attack surface

Policies should be reviewed as features evolve.

---

# Browser Extension Permissions

The extension requests only the permissions it requires.

Permissions should be:

- documented
- justified
- periodically reviewed

Unused permissions should be removed.

---

# Secure Storage

Sensitive information should be stored only where necessary.

Examples:

Backend:

- database
- encrypted tokens

Browser Extension:

- access token
- refresh token (if required)
- synchronization queue

Secrets must never be embedded in client code.

---

# Encryption

Encryption applies:

## In Transit

HTTPS/TLS

---

## At Rest

Database encryption where supported

Encrypted backups

Encrypted storage

---

## Sensitive Fields

OAuth refresh tokens

API credentials

Third-party secrets

Passwords remain hashed rather than encrypted.

---

# Rate Limiting

Public APIs should enforce rate limits.

Protect against:

- brute-force attacks
- abuse
- denial-of-service attempts

Rate limits should be configurable.

---

# Dependency Security

Dependencies should be:

- actively maintained
- regularly updated
- vulnerability scanned
- license reviewed

Critical vulnerabilities require immediate review.

---

# Secure CI/CD

The deployment pipeline should:

- protect secrets
- validate builds
- execute automated tests
- scan dependencies
- require code review

Production deployments require successful CI validation.

---

# Logging

Security-relevant events should be logged.

Examples:

- authentication failures
- permission failures
- suspicious activity
- administrative actions

Sensitive values must never appear in logs.

---

# Audit Trail

Critical security actions should produce immutable audit records.

Examples:

- password changes
- login events
- account deletion
- security configuration changes

Audit records should not be editable.

---

# Monitoring

Security monitoring includes:

- authentication failures
- unusual API activity
- elevated error rates
- dependency vulnerabilities
- deployment anomalies

Monitoring supports early incident detection.

---

# Incident Response

Security incidents follow a documented process.

```text
Detection

↓

Containment

↓

Investigation

↓

Recovery

↓

Post-Incident Review

↓

Preventive Improvements
```

Incident reviews focus on systemic improvements.

---

# Data Privacy

CareerOS follows data minimization principles.

Collect only information required to provide platform functionality.

Avoid collecting unnecessary personal information.

---

# Backup Security

Backups must:

- remain encrypted
- use restricted access
- be verified regularly

Backup procedures follow ADR-040.

---

# Browser Parser Security

Parsers should:

- avoid executing page scripts
- avoid modifying recruitment websites
- perform read-only extraction
- validate extracted data

Parser behavior should be deterministic.

---

# AI Assistant Rules

AI-assisted development must:

- preserve security boundaries
- avoid introducing insecure defaults
- never expose secrets
- maintain validation
- preserve authorization checks
- update security documentation when introducing privileged features

Security-related changes require peer review.

---

# Security Reviews

The platform should periodically review:

- permissions
- dependencies
- authentication
- authorization
- infrastructure
- Browser Extension permissions
- API exposure

Security reviews are part of regular engineering operations.

---

## Automated Security Checks

# Future Considerations

Potential future enhancements include:

- Multi-factor authentication (MFA)
- Hardware security keys (WebAuthn)
- Single Sign-On (SSO)
- Device management
- Security dashboard
- Risk-based authentication
- Account activity notifications

These features can be introduced without altering the core security architecture.

---

# Consequences

## Positive

- Consistent security posture across the platform
- Reduced attack surface
- Strong separation of trust boundaries
- Improved protection of user data
- Easier security audits
- Clear operational security practices

## Negative

- Additional implementation complexity
- Increased operational overhead
- More comprehensive testing requirements
- Ongoing dependency and infrastructure maintenance

---

# Compliance

All CareerOS applications, Browser Extension modules, backend services, shared packages, deployment pipelines, and operational processes must comply with this security architecture.

Any deviation requires an approved Architecture Decision Record (ADR).
