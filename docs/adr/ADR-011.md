# ADR-011: Application Pipeline

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

The central purpose of CareerOS is to help users manage the lifecycle of their job applications.

A job application is not a static record—it progresses through a series of states from discovery to final outcome. Users need visibility into where every application is, what actions are required next, and how their overall job search is progressing.

Without a formal pipeline model:

- Status values become inconsistent.
- Reporting becomes unreliable.
- Automation is difficult.
- Historical analysis is impossible.
- Different parts of the application may interpret application state differently.

A standardized application pipeline is required to ensure consistency across the database, backend API, frontend, browser extension, analytics, notifications, and automation.

---

# Decision

CareerOS will model the application journey as a **finite state pipeline**.

Every application has:

- One current status.
- A complete history of status transitions.
- Associated timestamps.
- Optional metadata describing the transition.

Pipeline state is treated as a first-class business concept rather than a simple string field.

---

# Goals

The application pipeline should:

- Represent the user's real hiring journey.
- Standardize application states.
- Preserve transition history.
- Enable analytics.
- Support reminders and automation.
- Power Kanban-style workflows.
- Be extensible without breaking existing data.

---

# Pipeline States

The initial CareerOS pipeline consists of the following states.

```text
Saved

↓

Applied

↓

Screening

↓

Interview

↓

Offer

↓

Accepted
```

or

```text
Rejected
```

An application always exists in exactly one current state.

---

# State Definitions

## Saved

The job has been identified but no application has been submitted.

Examples:

- Captured from browser extension.
- Saved for later.
- Draft application.

---

## Applied

The application has been submitted.

Typical metadata:

- Application date
- Resume used
- Source URL

---

## Screening

The employer has acknowledged the application and initiated an initial evaluation.

Examples:

- Recruiter outreach
- Phone screen
- HR screening

---

## Interview

The application has entered one or more interview rounds.

Examples:

- Technical interview
- Behavioral interview
- System design interview
- Final interview

Multiple interview rounds are represented separately as events rather than separate pipeline states.

---

## Offer

An offer has been extended.

Metadata may include:

- Salary
- Benefits
- Expiration date

---

## Accepted

The user has accepted the offer.

This represents a terminal state.

---

## Rejected

The application is no longer active.

Examples:

- Employer rejection.
- Candidate withdrawal.

This is also a terminal state.

---

# State Diagram

```text
            Saved
               │
               ▼
           Applied
               │
               ▼
          Screening
               │
               ▼
          Interview
               │
               ▼
             Offer
            /     \
           ▼       ▼
    Accepted   Rejected
```

Certain transitions may bypass intermediate states when appropriate.

Example:

```text
Applied

↓

Rejected
```

---

# Transition History

Current state alone is insufficient.

Every transition is recorded.

Example:

```text
Saved

↓

Applied

↓

Screening

↓

Interview

↓

Offer
```

Historical records are never overwritten.

---

# Pipeline Event Model

Each transition generates an immutable pipeline event.

Example:

```text
Application

↓

Pipeline Event

Status

Timestamp

User

Metadata
```

This enables historical reporting.

---

# Transition Rules

Examples:

Allowed:

```text
Saved

↓

Applied
```

Allowed:

```text
Interview

↓

Offer
```

Allowed:

```text
Offer

↓

Accepted
```

Allowed:

```text
Offer

↓

Rejected
```

Disallowed:

```text
Accepted

↓

Applied
```

Terminal states cannot transition back into active states without an explicit administrative action.

---

# Timestamps

Every transition records:

- Previous status
- New status
- Timestamp
- Actor
- Optional notes

Example:

```text
Applied

↓

Interview

at

2026-08-10T15:22:14Z
```

---

# Activity History

Every pipeline transition generates an activity history event.

Example:

```text
Application moved

Applied

↓

Interview
```

Pipeline history and activity history remain synchronized.

---

# Kanban Board

The application pipeline powers the Kanban interface.

Columns correspond to pipeline states.

Example:

```text
Saved

Applied

Screening

Interview

Offer

Accepted

Rejected
```

Dragging a card updates the application's current status and records a transition event.

---

# Browser Extension Integration

Applications captured from the browser extension begin in the **Saved** state unless the user explicitly indicates that they have already applied.

This ensures newly captured opportunities enter the pipeline consistently.

---

# Tasks Integration

Pipeline transitions may automatically generate tasks.

Examples:

- Applied → Create follow-up reminder.
- Interview → Prepare interview checklist.
- Offer → Review compensation package.

Automation rules are configurable.

---

# Notifications Integration

Notifications may be triggered by:

- Status changes.
- Long periods of inactivity.
- Upcoming follow-ups.
- Interview reminders.

Notifications consume pipeline events but do not modify pipeline state.

---

# Analytics Integration

Pipeline events power analytics.

Examples:

- Applications submitted.
- Interview conversion rate.
- Offer rate.
- Acceptance rate.
- Average time in each stage.
- Funnel visualization.

Analytics is derived from transition history rather than current status alone.

---

# API Representation

Current state example:

```json
{
  "status": "INTERVIEW"
}
```

History example:

```json
[
  {
    "from": "SCREENING",
    "to": "INTERVIEW",
    "timestamp": "2026-08-10T15:22:14Z"
  }
]
```

The API exposes both the current status and the transition history.

---

# Database Model

Recommended tables:

```text
applications

application_pipeline_events
```

The `applications` table stores the current status.

The `application_pipeline_events` table stores the immutable transition history.

---

# Soft Deletes

Pipeline events are append-only.

Events are never deleted during normal operation.

Deleting an application does not remove historical pipeline events unless required by data deletion policies.

---

# Future Extensions

Potential future enhancements include:

- Custom pipeline stages.
- Multiple concurrent interview rounds.
- Offer negotiation.
- Counteroffers.
- Candidate withdrawal reason.
- Automated status detection.
- AI-powered pipeline recommendations.

The base pipeline is intentionally conservative to maximize consistency.

---

# Alternatives Considered

## Free-Form Status Strings

Advantages:

- Flexible.

Rejected because:

- Inconsistent terminology.
- Difficult reporting.
- Impossible validation.

---

## Status Stored Without History

Advantages:

- Simpler schema.

Rejected because:

- No audit trail.
- Weak analytics.
- No historical insights.

---

## Fully Custom User Pipelines

Advantages:

- Highly flexible.

Rejected for MVP because:

- Increased complexity.
- More difficult analytics.
- Inconsistent reporting across users.

May be reconsidered in future versions.

---

# Consequences

## Positive

- Consistent workflow.
- Reliable analytics.
- Better automation.
- Complete audit history.
- Strong API contracts.
- Improved user experience.

---

## Negative

- Additional database tables.
- More complex transition validation.
- Requires immutable event storage.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every application has one current pipeline state.
- Pipeline states use the standardized enumeration.
- Every transition creates an immutable pipeline event.
- Transition history is never overwritten.
- Kanban interactions update pipeline state through the same transition service.
- Analytics derive from pipeline history.
- Terminal states require explicit administrative intervention to reopen.

Changes to the standard pipeline require a new ADR.

# Decision Summary

CareerOS adopts a **finite-state Application Pipeline** as the canonical model for tracking a user's hiring journey. Every application has one current status and a complete immutable history of status transitions. This model powers the Kanban board, analytics, automation, notifications, activity history, and reporting while providing a consistent and extensible foundation for the platform.
