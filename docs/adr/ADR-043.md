# ADR-043 — Event Tracking & Product Analytics Architecture

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-018 (Analytics Model), ADR-012 (Activity History)
- **Superseded By:** None

---

# Context

CareerOS is designed to help users manage and optimize their job search process.

Understanding how users interact with the platform is essential for:

- Measuring feature adoption
- Improving user experience
- Identifying friction points
- Monitoring product health
- Supporting business decisions
- Diagnosing workflow failures
- Evaluating new feature releases

Traditional application logs focus on system behavior.

Activity history records user-visible actions.

Neither provides complete product analytics.

CareerOS therefore requires a dedicated event tracking architecture that captures meaningful product events across every application while remaining privacy-conscious and independent of operational logging.

---

# Decision

CareerOS will implement a centralized, event-driven product analytics architecture.

The architecture consists of:

1. Event Producers
2. Event Schema
3. Client Event SDK
4. Backend Event Ingestion
5. Event Processing Pipeline
6. Analytics Storage
7. Reporting Layer

Events are treated as immutable business facts and are separate from operational logs.

---

```text

↓

↓

Event SDK

↓

Backend API

↓

Event Validation

↓

Event Store

↓

↓
```

The event pipeline should be consistent across all CareerOS applications.

# Design Goals

The event tracking architecture should provide:

- Consistent event definitions
- Cross-platform analytics
- Privacy by design
- Schema validation
- Reliable delivery
- Low overhead
- Historical reporting
- Future extensibility

---

# Event Producers

Events may originate from:

- Web Application
- Browser Extension
- Backend API
- Background Jobs
- CLI Tools (optional)

Each producer emits events using shared contracts.

---

# Event Categories

CareerOS classifies events into five categories.

## Product Events

Represent meaningful user interactions.

Examples:

- Application Imported
- Resume Uploaded
- Resume Selected
- Application Updated
- Company Added

---

## Navigation Events

Track movement through the application.

Examples:

- Dashboard Viewed
- Resume Library Viewed
- Analytics Viewed
- Settings Opened

---

## System Events

Represent platform behavior.

Examples:

- Synchronization Started
- Synchronization Completed
- Queue Drained
- Parser Executed

---

## Error Events

Represent recoverable product failures.

Examples:

- Import Failed
- Upload Failed
- Authentication Failed

Operational exceptions remain part of the error tracking system defined in ADR-039.

---

## Business Events

Represent milestones in a user's job search.

Examples:

- Interview Scheduled
- Offer Received
- Offer Accepted
- Application Rejected

These events support long-term analytics.

---

# Event Lifecycle

Every event follows the same lifecycle.

```text
User Action

↓

Event Created

↓

Validation

↓

Queue

↓

Backend

↓

Storage

↓

Aggregation

↓

Reporting
```

Events are immutable after creation.

---

# Event Schema

Every event follows a shared schema.

Required fields:

```text
Event ID

Event Name

Category

Timestamp

Application

Application Version

Schema Version

User ID

Session ID

Correlation ID
```

Optional fields may be included for event-specific metadata.

---

# Event Naming Convention

Events use PascalCase and describe completed actions.

Examples:

```text
ApplicationImported

ResumeUploaded

DashboardViewed

InterviewScheduled

ParserExecuted
```

Avoid vague names such as:

```text
ClickedButton

Event1

ActionDone
```

Names should express business intent.

---

# Event Payload

Payloads should contain only information required for analytics.

Example:

```json
{
  "event": "ApplicationImported",
  "company": "Acme Inc.",
  "platform": "LinkedIn",
  "jobType": "Full-Time",
  "importMethod": "BrowserExtension"
}
```

Payloads should avoid unnecessary detail.

---

# Event Versioning

Each event includes a schema version.

Example:

```text
Schema Version: 1
```

Breaking schema changes require a new version.

Backward compatibility should be maintained where practical.

---

# Client Event SDK

Applications emit events through a shared SDK.

Responsibilities include:

- validation
- batching
- retry
- queueing
- serialization

Applications should not send raw analytics requests directly.

---

# Queueing

Events should be queued before transmission.

Benefits:

- offline support
- retry capability
- reliable delivery

The Browser Extension reuses the synchronization queue where appropriate.

---

# Event Validation

Events are validated using shared Zod schemas.

Validation verifies:

- required fields
- value ranges
- enumerations
- payload integrity

Invalid events are rejected before transmission.

---

# Backend Ingestion

The Backend API is responsible for:

- authentication
- validation
- deduplication
- persistence
- processing

Analytics data should never be written directly from client applications to storage.

---

# Deduplication

Every event includes a globally unique identifier.

Duplicate events should be ignored during ingestion.

Idempotency protects analytics accuracy.

---

# Event Storage

Events are stored in an append-only event store.

Characteristics:

- immutable
- chronological
- queryable
- auditable

Historical events are never updated.

---

# Aggregation

Dashboards should consume aggregated data rather than raw event streams.

Examples:

- daily imports
- weekly applications
- interview conversion rate
- offer acceptance rate

Aggregation improves performance and simplifies reporting.

---

# Privacy

The analytics platform must not collect:

- passwords
- authentication tokens
- resume contents
- uploaded documents
- browser history
- personally sensitive information unrelated to product analytics

Only data required to understand product usage should be collected.

---

# User Identity

Authenticated events include a stable user identifier.

Anonymous events should use a temporary session identifier.

Identity transitions should preserve analytical continuity where appropriate.

---

# Correlation IDs

Events should include correlation IDs when associated with requests or workflows.

Example:

```text
Import Started

↓

Parser Executed

↓

Synchronization Completed

↓

Application Imported
```

Correlation IDs allow complete workflow analysis.

---

# Sampling

Critical business events are always collected.

Low-value, high-frequency events may be sampled.

Example:

| Event Type | Sampling |
|------------|----------|
| Application Imported | 100% |
| Resume Uploaded | 100% |
| Dashboard Viewed | 100% |
| Scroll Depth | 25% |
| UI Hover | 0% (Not Collected) |

Sampling policies should be configurable.

---

# Retention

Recommended retention:

| Event Type | Retention |
|------------|-----------|
| Product Events | 24 months |
| Navigation Events | 12 months |
| System Events | 12 months |
| Business Events | Permanent (or long-term) |

Retention policies should balance analytical value and storage costs.

# Integration with Activity History

Activity History and Event Tracking serve different purposes.

| Activity History | Event Tracking |
|------------------|----------------|
| User-facing | Internal analytics |
| Editable presentation | Immutable facts |
| Business timeline | Product telemetry |
| Individual user | Aggregated insights |

Both systems may originate from the same user action but serve different audiences.

---

# Integration with Logging

Event tracking is independent of structured logging.

Relationship:

```text
User Action

↓

Product Event

↓

Analytics

↓

Dashboard
```

Logging focuses on system diagnostics.

Analytics focuses on product behavior.

---

# Error Handling

Failed event submissions should:

- retry automatically
- preserve ordering where required
- avoid blocking user workflows

Loss of analytics should never prevent core functionality.

---

# Testing Strategy

Event tracking requires:

## Unit Tests

- event validation
- serialization
- schema compliance

---

## Integration Tests

- ingestion
- batching
- retries
- deduplication

---

## End-to-End Tests

Verify:

- event creation
- ingestion
- aggregation
- reporting

Analytics correctness is part of production quality.

---

# AI Assistant Rules

AI-assisted development must:

- preserve event naming conventions
- avoid emitting duplicate events
- maintain shared schemas
- preserve privacy requirements
- update analytics documentation when introducing new tracked events

Analytics changes should accompany corresponding tests.

---

# Consequences

## Positive

- Accurate product insights
- Consistent analytics across applications
- Better feature prioritization
- Reliable business reporting
- Extensible event architecture
- Improved understanding of user workflows

## Negative

- Additional implementation effort
- Increased storage requirements
- Ongoing schema governance
- Aggregation infrastructure maintenance

---

# Compliance

All CareerOS applications, Browser Extension modules, backend services, and future clients must emit analytics events through this standardized event tracking architecture.

Any deviation requires an approved Architecture Decision Record (ADR).
