# ADR-020: CareerOS Backlog Schema (CBS v1.0)

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** CBS v1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS adopts a repository-first planning model where YAML backlog files are the single source of truth for product planning.

To enable:

- deterministic validation,
- GitHub synchronization,
- AI-assisted development,
- reporting,
- release automation,

every backlog file must conform to a single, versioned specification.

Without a formal schema:

- different backlog files evolve inconsistently,
- automation becomes fragile,
- validation becomes impossible,
- AI assistants receive inconsistent context,
- GitHub synchronization becomes unreliable.

CareerOS therefore requires a canonical backlog specification.

---

# Decision

CareerOS adopts the **CareerOS Backlog Schema (CBS) v1.0** as the mandatory specification for all backlog files.

Every backlog document MUST conform to CBS.

The Backlog CLI validates CBS compliance before synchronization.

---

# Goals

CBS is designed to provide:

- deterministic planning,
- machine readability,
- human readability,
- validation,
- extensibility,
- versioning,
- automation,
- AI compatibility.


# Core Concepts

CBS defines six primary planning objects.

```text
Workspace

↓

Epic

↓

Feature

↓

Issue

↓

Acceptance Criteria

↓

Dependencies
```

These objects form the planning hierarchy.

---

# Workspace

The workspace defines operational configuration.

Examples include:

- active milestone,
- enabled domains,
- GitHub configuration,
- automation options.

The workspace never contains backlog items.

---

# Epic

An epic represents a complete business capability.

An epic includes:

- identifier,
- title,
- objective,
- milestone,
- success metrics,
- dependencies,
- features.

Each domain YAML contains one epic.

---

# Feature

A feature represents a coherent functional capability.

Features:

- belong to one epic,
- contain one or more issues,
- define acceptance tests,
- may define future scope.

---

# Issue

Issues represent executable work.

Each issue includes:

- unique identifier,
- title,
- type,
- priority,
- estimate,
- labels,
- dependencies,
- acceptance criteria.

Issues synchronize directly to GitHub.

---

# Acceptance Criteria

Acceptance criteria define completion requirements.

They:

- are testable,
- are deterministic,
- are implementation independent,
- define "done."

Every issue must include acceptance criteria.

---

# Success Metrics

Epics define measurable outcomes.

Example:

```text
Application creation

< 30 seconds
```

Metrics describe product success rather than implementation.

---

# Identifier Conventions

Identifiers follow fixed conventions.

Epic:

```text
APPLICATIONS
```

Feature:

```text
APPLICATION-CREATE
```

Issue:

```text
APP-001
```

Identifiers are immutable.

---

# Issue Types

CBS defines the following issue types.

```text
task

story

bug

spike

chore

research

documentation
```

No additional types are permitted without schema evolution.

---

# Priority Levels

Priority values:

```text
P0

P1

P2

P3
```

Definitions:

| Priority | Meaning |
|----------|----------|
| P0 | Critical |
| P1 | High |
| P2 | Medium |
| P3 | Low |

---

# Estimation

Estimates use integer story points.

Recommended range:

```text
1

2

3

5

8

13
```

Estimates represent implementation effort.

---

# Milestones

Milestones organize delivery phases.

Examples:

```text
FOUNDATION

CORE_TRACKER

PRODUCTIVITY

CAPTURE

MVP_POLISH

BETA

POST_MVP
```

Every epic belongs to one milestone.

---

# Dependencies

Dependencies reference identifiers.

Example:

```yaml
dependencies:
  - APP-001
```

Dependencies may target:

- issues,
- features,
- epics.

Circular dependencies are prohibited.

---

# Labels

Labels provide GitHub categorization.

Examples:

```text
frontend

backend

database

extension

security
```

Labels synchronize automatically.

---

# Acceptance Tests

Features may define end-to-end acceptance tests.

Example:

```text
User creates an application.

↓

Application appears in dashboard.
```

Acceptance tests validate complete user workflows.

---

# Future Scope

Features may define:

```yaml
future_scope:
  - AI suggestions
  - Smart recommendations
```

Future scope documents planned evolution without affecting MVP implementation.

---

# Validation Rules

CBS validation includes:

- required fields,
- identifier format,
- duplicate identifiers,
- dependency resolution,
- milestone validation,
- priority validation,
- issue type validation,
- schema version validation,
- circular dependency detection.

Validation failures block synchronization.

---

# README.yaml

README.yaml defines:

- project metadata,
- domain catalog,
- file discovery.

It contains no executable work.

---

# 99-workspace.yaml

Workspace defines:

- enabled domains,
- active milestone,
- GitHub configuration,
- automation configuration.

Workspace never contains backlog issues.

---

# Domain Files

Every domain file contains:

```text
Epic

↓

Features

↓

Issues

↓

Acceptance Criteria
```

The file is self-contained.

---

# Browser Extension

The browser extension backlog follows CBS.

Subdomains include:

- architecture,
- parsers,
- UI,
- synchronization,
- testing.

CBS remains unchanged.

---

# GitHub Mapping

CBS maps directly to GitHub.

| CBS | GitHub |
|------|---------|
| Issue | GitHub Issue |
| Labels | Labels |
| Milestone | Milestone |
| Acceptance Criteria | Issue Body |
| Dependencies | Issue References |

GitHub is a projection of CBS.

---

# AI Integration

AI assistants consume CBS directly.

CBS provides:

- planning,
- requirements,
- dependencies,
- context,
- acceptance criteria.

AI should not infer requirements from GitHub metadata.

---

# Versioning

CBS follows semantic versioning.

Example:

```text
CBS v1.0
```

Breaking schema changes require:

- new version,
- migration,
- documentation.

---

# Extensibility

Future schema versions may introduce:

- new planning objects,
- metadata,
- workflow automation,
- richer analytics.

Backward compatibility should be maintained whenever practical.

# Alternatives Considered

## Markdown Planning

Rejected because:

- unstructured,
- difficult to validate,
- poor automation.

---

## GitHub-Only Planning

Rejected because:

- weak version control,
- limited automation,
- difficult AI integration.

---

## JSON

Rejected because:

- verbose,
- less readable,
- more difficult for manual editing.

YAML provides better readability while remaining machine-readable.

---

# Consequences

## Positive

- deterministic planning,
- reliable validation,
- repository-first workflow,
- AI-friendly architecture,
- reproducible automation,
- strong tooling foundation.

---

## Negative

- schema maintenance,
- contributor learning curve,
- version migration over time.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every backlog file conforms to CBS.
- Every issue has a unique identifier.
- Every issue includes acceptance criteria.
- Circular dependencies are prohibited.
- Invalid backlog files fail validation.
- GitHub synchronization only occurs after successful validation.
- CBS changes require version updates.
- Schema evolution requires architectural review.

---

# Migration Strategy

Future CBS versions should include:

1. Version declaration.
2. Migration guide.
3. Validator updates.
4. Synchronizer updates.
5. Backward compatibility strategy where practical.

# Decision Summary

CareerOS adopts the **CareerOS Backlog Schema (CBS) v1.0** as the canonical specification for all planning artifacts. CBS standardizes the structure of epics, features, issues, dependencies, milestones, acceptance criteria, and validation rules, enabling deterministic tooling, reliable GitHub synchronization, AI-assisted engineering workflows, and repository-first project management. Every backlog file must conform to CBS, and all automation is built on top of this versioned schema.
