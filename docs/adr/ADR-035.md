# ADR-035: Deployment Platform

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS consists of multiple deployable applications and services, including:

- Backend API
- Web Application
- Browser Extension build pipeline
- Background workers
- Shared infrastructure services
- CLI tooling

The platform requires a deployment strategy that is:

- cost-effective,
- repeatable,
- infrastructure-as-code friendly,
- suitable for continuous deployment,
- compatible with Docker,
- easy to scale over time.

CareerOS is developed and operated by a small engineering team with significant AI-assisted development. Operational simplicity is therefore a primary design objective.

After evaluating available deployment approaches, the project standardizes on self-hosted infrastructure managed through container orchestration.

---

# Decision

CareerOS adopts a **self-hosted Docker-based deployment platform** managed with **Coolify**.

Applications are containerized, deployed through Git-based workflows, and hosted on self-managed virtual private servers (VPSs).

Cloudflare provides DNS, TLS termination, and edge networking services.

---

# Goals

The deployment platform should:

- minimize operational complexity,
- remain cloud-provider independent,
- support continuous deployment,
- reduce hosting costs,
- provide repeatable deployments,
- support multiple environments,
- enable future horizontal scaling.

---

# Platform Overview

The production deployment stack is:

```text
GitHub

↓

GitHub Actions (CI)

↓

Container Registry

↓

Coolify

↓

Docker

↓

VPS

↓

Cloudflare

↓

Users
```

Planning and deployment remain separate concerns.

---

# Hosting Strategy

CareerOS is hosted on self-managed Linux VPS infrastructure.

Responsibilities include:

- application hosting,
- persistent storage,
- Docker runtime,
- networking,
- monitoring.

Infrastructure should remain reproducible through configuration rather than manual setup.

---

# Containerization

Every deployable application is packaged as a Docker image.

Examples:

- Backend API
- Web frontend
- Background workers
- Supporting services

Container images provide consistent execution across environments.

---

# Deployment Orchestration

Coolify is the standard deployment platform.

Responsibilities include:

- Git integration,
- container deployment,
- environment variable management,
- SSL provisioning,
- service lifecycle management,
- deployment history,
- rollback support.

Application deployments should occur through Coolify rather than manual Docker commands whenever practical.

---

# Reverse Proxy

Traffic is routed through a reverse proxy managed by the deployment platform.

Responsibilities include:

- HTTPS,
- routing,
- virtual hosts,
- service discovery,
- certificate management.

Application containers remain unaware of public networking concerns.

---

# DNS and Edge Services

Cloudflare is responsible for:

- DNS management,
- TLS,
- CDN capabilities where appropriate,
- DDoS protection,
- edge networking.

Cloudflare sits in front of the deployment platform.

---

# Continuous Deployment

Deployment workflow:

```text
Merge to main

↓

CI

↓

Build Docker Image

↓

Publish Image

↓

Coolify Deployment

↓

Health Check

↓

Production
```

Only validated builds are deployed.

---

# Build Strategy

Application builds occur in CI.

Artifacts include:

- production Docker images,
- static assets,
- browser extension packages,
- release metadata.

Builds should be deterministic and reproducible.

---

# Environment Separation

Separate environments are maintained for:

```text
Development

↓

Staging

↓

Production
```

Each environment has:

- independent configuration,
- isolated secrets,
- separate databases where applicable.

---

# Environment Variables

Configuration is supplied through environment variables managed by the deployment platform.

Examples:

- database URLs,
- API keys,
- OAuth secrets,
- storage credentials,
- feature flags.

Secrets are never committed to the repository.

---

# Persistent Storage

Persistent data includes:

- PostgreSQL
- uploaded files
- backups
- logs (where applicable)

Persistent storage must survive container replacement.

Application containers should remain stateless whenever practical.

---

# Database Deployment

PostgreSQL is deployed as an independent service.

Database lifecycle is managed separately from application deployments.

Application updates should not recreate databases.

---

# Database Migrations

Schema migrations execute during deployment using controlled migration tooling.

Migration failures block deployment.

Database changes should remain backward compatible whenever practical.

---

# Browser Extension Deployment

Browser extensions are versioned and packaged through CI.

Distribution targets include supported browser extension stores.

Extension deployment is independent from backend deployment.

---

# Health Checks

Every production service exposes health endpoints.

Health checks verify:

- application availability,
- dependency readiness,
- startup completion.

Deployments should fail if health checks do not succeed.

---

# Logging

Applications should produce structured logs.

Logs should support:

- debugging,
- operational monitoring,
- incident investigation.

Applications should log to stdout/stderr wherever practical.

---

# Monitoring

Production monitoring should include:

- uptime,
- resource utilization,
- application errors,
- deployment status,
- health checks.

Operational visibility is required for production services.

---

# Backup Strategy

Regular backups are required for:

- PostgreSQL,
- uploaded assets,
- configuration where appropriate.

Backup restoration should be periodically validated.

---

# Rollback Strategy

Deployments should support rollback through:

- previous container images,
- previous releases,
- database rollback procedures where appropriate.

Rollback procedures should be documented.

---

# Scaling Strategy

Initial deployment targets a single VPS.

Future scaling may include:

- multiple application instances,
- load balancing,
- dedicated database servers,
- object storage,
- managed caching.

The deployment architecture should support incremental scaling.

---

# Security

Production infrastructure should follow secure defaults.

Examples include:

- HTTPS everywhere,
- least-privilege access,
- firewall rules,
- secret management,
- image updates,
- dependency patching.

Security is an operational responsibility as well as an engineering concern.

---

# Disaster Recovery

Recovery procedures should document:

- infrastructure recreation,
- database restoration,
- deployment restoration,
- DNS recovery.

Recovery should be reproducible from documented procedures.

---

# AI-Assisted Operations

AI may assist with:

- deployment scripts,
- Dockerfiles,
- CI workflows,
- infrastructure documentation,
- troubleshooting.

Humans remain responsible for production deployments and operational decisions.

---

# Continuous Integration

Before deployment, CI executes:

- type checking,
- linting,
- unit tests,
- integration tests,
- build verification,
- backlog validation.

Failed pipelines prevent deployment.

---

# Alternatives Considered

## Platform-as-a-Service

Examples:

- Render
- Railway
- Fly.io

Rejected because:

- higher long-term operational cost,
- less infrastructure control,
- platform-specific constraints.

---

## Kubernetes

Rejected because:

- unnecessary operational complexity,
- excessive infrastructure overhead for current scale.

The architecture should remain compatible with future Kubernetes migration if needed.

---

## Manual Docker Deployment

Rejected because:

- inconsistent deployments,
- limited auditability,
- greater operational risk.

---

# Consequences

## Positive

- Low operating cost.
- Full infrastructure control.
- Deterministic deployments.
- Cloud-provider independence.
- Simple scaling path.
- Strong Docker integration.

---

## Negative

- Infrastructure maintenance responsibility.
- Self-managed security updates.
- Backup and monitoring ownership.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Deployable services are containerized.
- Production deployments occur through Coolify.
- Cloudflare manages public DNS and edge networking.
- CI must succeed before deployment.
- Secrets are managed outside the repository.
- Persistent data is stored independently of application containers.
- Health checks are required for production services.
- Deployment procedures remain automated and reproducible.

Changes to the deployment platform require a new ADR.

# Decision Summary

CareerOS adopts a **self-hosted Docker-based deployment platform** managed by **Coolify** on Linux VPS infrastructure, with **Cloudflare** providing DNS, TLS, and edge networking. All deployable services are containerized, built through continuous integration, deployed using automated Git-based workflows, and operated as reproducible, stateless services where practical. This deployment strategy provides low operating costs, infrastructure independence, operational simplicity, and a clear path for future scaling while maintaining reliable, repeatable production deployments.
