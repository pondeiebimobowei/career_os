# ADR-009: Shared Packages Strategy

- **Status:** Superseded
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** ADR-047

---

# Context

CareerOS is a monorepo containing multiple independent applications.

Current applications include:

- Web Application
- Backend API
- Browser Extension
- Backlog CLI

Future applications may include:

- Admin Portal
- Documentation Site
- Mobile Application

Without a structured approach to code sharing, common logic would be duplicated across applications, leading to:

- Inconsistent implementations
- Version drift
- Increased maintenance
- More bugs
- Difficult refactoring

A deliberate strategy is required to define:

- What belongs in shared packages
- What belongs inside an application
- Package ownership
- Dependency rules
- Public APIs
- Versioning
- Governance

---

# Decision

CareerOS will maintain a dedicated **Shared Packages** layer within the monorepo.

Reusable functionality that is used by two or more applications should be extracted into shared packages when doing so improves maintainability and does not introduce unnecessary coupling.

Each package must have:

- A single responsibility
- A well-defined public API
- Independent tests
- Clear ownership
- Stable interfaces

Applications consume packages but never modify package internals directly.

---

# Goals

The shared package strategy should:

- Reduce duplication
- Encourage reuse
- Maintain consistency
- Improve maintainability
- Support independent application development
- Improve type safety
- Simplify AI-assisted development
- Provide stable building blocks

---

# Package Layer

The shared package layer sits between applications and third-party libraries.

```text
Applications

↓

Shared Packages

↓

External Libraries
```

Applications should depend on packages instead of duplicating common logic.

# Package Responsibilities

## ui

Contains reusable user interface components.

Examples:

- Buttons
- Inputs
- Dialogs
- Cards
- Tables
- Icons
- Layout primitives

The package should remain business-domain agnostic.

---

## design-tokens

Contains shared design decisions.

Examples:

- Colors
- Typography
- Spacing
- Shadows
- Border radius
- Breakpoints
- Animation durations

Applications should not redefine design tokens independently.

---

## validation

Contains reusable Zod schemas.

Examples:

- User schema
- Company schema
- Job schema
- Application schema
- Pagination schema

Validation logic should be shared whenever possible.

---

## types

Contains shared TypeScript types.

Examples:

- DTOs
- Enums
- Interfaces
- Domain contracts
- API models

Business logic should not live here.

---

## api-client

Contains the reusable API client.

Responsibilities include:

- HTTP client
- Authentication headers
- Error mapping
- Request utilities
- Response parsing

Applications should not duplicate API access logic.

---

## config

Contains shared configuration.

Examples:

- Environment parsing
- Feature flags
- Constants
- Shared settings

---

## utils

Contains generic utilities.

Examples:

- Date formatting
- String helpers
- Array utilities
- Object utilities

Utilities should remain framework-independent.

---

## backlog-cli

Contains backlog tooling.

Responsibilities include:

- YAML parsing
- CBS validation
- GitHub synchronization
- Planning automation

This package is independent of application runtime logic.

# Package Design Principles

Every package must:

- Have a single responsibility
- Expose a minimal public API
- Hide implementation details
- Be independently testable
- Avoid circular dependencies
- Minimize external dependencies

---

# Public API

Each package exposes functionality through an entry point.

Example:

```text
packages/ui/

src/

index.ts
```

Consumers import only from the package root.

Example:

✅

```typescript
import { Button } from "@careeros/ui";
```

Not:

```typescript
import { Button } from "@careeros/ui/src/components/button/Button";
```

Internal files are considered private.

---

# Dependency Rules

Packages may depend on:

- External libraries
- Lower-level shared packages

Packages must not depend on applications.

Example:

✅

```text
packages/ui

↓

packages/design-tokens
```

Not:

```text
packages/ui

↓

apps/web
```

---

# Circular Dependencies

Circular dependencies are prohibited.

Example:

```text
ui

↓

types

↓

ui
```

Package dependency graphs should remain acyclic.

---

# Package Extraction Criteria

Code should generally move into a package when:

- It is reused by multiple applications.
- It represents stable platform functionality.
- It has long-term value.
- It improves consistency.

Avoid extracting code prematurely.

The "Rule of Two" applies:

> A capability should generally be used by at least two applications before becoming a shared package, unless it is clearly foundational (for example, `types`, `config`, or `validation`).

---

# Business Logic

Business logic should remain inside application features.

Shared packages should avoid:

- Product workflows
- Feature orchestration
- Authorization decisions
- Business policies

Those belong in application or domain layers.

---

# Testing

Each package owns its own test suite.

Tests should verify:

- Public API behavior
- Backward compatibility
- Utility correctness
- Component rendering (where applicable)

Applications should not be responsible for testing package internals.

---

# Documentation

Every package should include:

```text
README.md
```

Containing:

- Purpose
- Public API
- Usage examples
- Dependency rules
- Development guidelines

---

# Versioning

Packages evolve with the monorepo.

Although versioned together internally, each package should follow Semantic Versioning principles when introducing breaking API changes.

Public interfaces should remain stable.

---

# Build System

Packages participate in Turborepo build pipelines.

Build order respects dependency relationships.

Example:

```text
design-tokens

↓

ui

↓

web
```

This enables incremental builds and caching.

---

# AI Development

Shared packages improve AI-assisted development by providing:

- Stable abstractions
- Predictable APIs
- Reusable implementations
- Consistent naming

AI assistants should prefer extending shared packages over duplicating functionality.

---

# Alternatives Considered

## No Shared Packages

Advantages:

- Simpler initial development

Rejected because:

- High duplication
- Inconsistent implementations
- Difficult maintenance

---

## Copy-and-Paste Reuse

Rejected because:

- Creates divergence over time.
- Difficult to fix bugs consistently.

---

## Single Massive Shared Library

Advantages:

- One import path

Rejected because:

- Violates single responsibility.
- Creates unnecessary coupling.
- Slower builds.
- Harder ownership.

---

# Consequences

## Positive

- Reduced duplication
- Consistent behavior
- Easier maintenance
- Faster development
- Better type safety
- Clear ownership
- Improved testing
- Better AI support

---

## Negative

- Requires discipline to maintain boundaries.
- Risk of over-extraction if packages are created prematurely.
- Additional package management overhead.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Shared functionality belongs in packages.
- Packages expose stable public APIs.
- Applications never import package internals.
- Packages never depend on applications.
- Circular dependencies are prohibited.
- Every package has a single responsibility.
- Every package includes tests and documentation.
- Business workflows remain outside shared packages.

Architectural changes to shared package organization require a new ADR.

# Decision Summary

CareerOS adopts a **Shared Packages Strategy** in which reusable, application-agnostic functionality is centralized within dedicated packages in the monorepo. Each package has a single responsibility, exposes a stable public API, and is independently testable. Applications consume these packages rather than duplicating logic, resulting in a more maintainable, consistent, and scalable platform.
