# ADR-010: CareerOS Domain Model

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a career management platform that enables users to organize every stage of their job search.

The system manages multiple business concepts that are highly interconnected, including:

- Users
- Companies
- Jobs
- Applications
- Pipeline Stages
- Tasks
- Notes
- Resumes
- Notifications
- Activity History

A consistent domain model is required to ensure:

- Clear ownership of business entities
- Consistent terminology
- Predictable API contracts
- Stable database schema
- Shared understanding across engineering, design, documentation, and automation

Without a formal domain model, different parts of the application may use inconsistent names, duplicate concepts, or implement conflicting business rules.

---

# Decision

CareerOS adopts a **domain-driven business model** where all core functionality is organized around well-defined business entities and their relationships.

Every persistent concept must belong to a clearly defined domain.

All applications—including the web app, backend API, browser extension, and future clients—must use the same domain vocabulary.

---

# Goals

The domain model should:

- Represent real business concepts.
- Minimize ambiguity.
- Encourage consistency.
- Enable future growth.
- Support automation.
- Provide stable API contracts.
- Align database design with business needs.

---

# Core Domains

The primary domains of CareerOS are:

```text
Identity

Companies

Jobs

Applications

Pipeline

Tasks

Notes

Resumes

Activity History

Notifications

Analytics

Settings

Billing (future)

Administration (future)
```

Each domain owns its business rules and data.

---

# Domain Relationships

The overall relationship between domains is illustrated below.

```text
User
│
├── Companies
│     └── Jobs
│            └── Applications
│                    ├── Pipeline
│                    ├── Tasks
│                    ├── Notes
│                    └── Activity History
│
├── Resumes
│
├── Notifications
│
└── Settings
```

Every entity belongs to exactly one user unless explicitly designed as shared system data.

---

# Aggregate Roots

The following entities are aggregate roots.

## User

Represents the authenticated CareerOS account.

Owns:

- Profile
- Companies
- Jobs
- Applications
- Tasks
- Notes
- Resumes
- Settings

---

## Company

Represents an employer.

Contains:

- Name
- Industry
- Website
- Location
- Notes

Relationships:

- One company
- Many jobs

---

## Job

Represents an advertised position.

Contains:

- Title
- Description
- Salary
- Employment Type
- Remote Status
- Source URL

Relationships:

- Belongs to one company
- May have one or more applications

---

## Application

Represents a user's application to a job.

Contains:

- Current status
- Dates
- Resume
- Notes
- Metadata

Relationships:

- Belongs to one job
- Belongs to one company
- Owns pipeline history
- Owns activity history
- Owns follow-up tasks

---

## Resume

Represents a resume stored by the user.

Contains:

- File
- Version
- Metadata

Applications reference resumes.

---

## Task

Represents an actionable reminder.

Examples:

- Follow up
- Prepare interview
- Send thank-you email

Tasks may optionally reference an application.

---

## Note

Represents user-authored information.

Notes may belong to:

- Company
- Job
- Application

---

# Application Pipeline

Applications move through a finite lifecycle.

```text
Saved

↓

Applied

↓

Screening

↓

Interview

↓

Offer

↓

Accepted

or

Rejected
```

Pipeline state is modeled separately from the application entity to preserve history.

---

# Activity History

Every significant business event is recorded.

Examples:

- Application created
- Status changed
- Resume attached
- Interview scheduled
- Task completed

Activity history is append-only.

Existing events are never modified.

---

# Browser Extension Domain

The browser extension introduces additional domain concepts.

Examples:

- Capture Session
- Parsed Job
- Parser
- Synchronization Queue

These exist only within the extension and map into core CareerOS entities.

---

# Analytics Domain

Analytics derives insights from existing business entities.

Examples:

- Applications per week
- Interview rate
- Offer rate
- Response rate
- Pipeline conversion

Analytics does not own business data.

It consumes existing domain data.

---

# Notifications Domain

Notifications communicate events to users.

Examples:

- Upcoming follow-up
- Interview reminder
- Sync completed
- Capture failed

Notifications reference business entities but do not own them.

---

# Ownership Rules

Every entity has a single owner.

Example:

```text
Application

owns

Tasks

Notes

Activity History
```

Ownership should remain unambiguous.

---

# Entity Identity

Every entity has a stable unique identifier.

Example:

```text
usr_xxxxx

cmp_xxxxx

job_xxxxx

app_xxxxx

tsk_xxxxx

nte_xxxxx
```

Identifiers never change.

---

# Lifecycle

Each entity defines its own lifecycle.

Example:

```text
Application

Created

↓

Updated

↓

Status Changes

↓

Archived

↓

Deleted (Soft Delete)
```

Lifecycle transitions must follow business rules.

---

# Business Rules

Examples include:

- A job belongs to one company.
- An application references one job.
- A task may reference one application.
- A resume belongs to one user.
- Users cannot access another user's entities.

Business rules are enforced by the domain layer.

---

# Soft Deletes

User-owned business entities use soft deletes.

Example:

```text
deletedAt
```

Deleted entities are excluded from normal queries.

---

# Cross-Domain Communication

Domains communicate through services rather than directly modifying each other's state.

Example:

```text
Application Service

↓

Activity Service

↓

Notification Service
```

This preserves clear boundaries.

---

# Domain Language

The following terminology is standardized.

Use:

- Company
- Job
- Application
- Pipeline
- Resume
- Task
- Note

Avoid introducing synonyms such as:

- Employer
- Position Record
- Candidate Record
- Reminder Item

Consistent terminology improves communication and automation.

---

# API Mapping

Each aggregate maps to a primary API resource.

Examples:

```text
/users

/companies

/jobs

/applications

/tasks

/resumes

/notes
```

The API mirrors the domain model.

---

# Database Mapping

Each aggregate root maps to its own primary table.

Example:

```text
users

companies

jobs

applications

tasks

notes

resumes
```

Relationships are enforced using foreign keys.

---

# Extensibility

New domains may be introduced without modifying existing domains excessively.

Examples:

- Interview Scheduling
- AI Assistant
- Contacts
- Networking CRM

Extensions should preserve existing boundaries.

---

# Alternatives Considered

## Flat CRUD Model

Advantages:

- Simpler implementation

Rejected because:

- Weak domain boundaries.
- Difficult long-term maintenance.
- Poor scalability.

---

## Database-Driven Design

Rejected because:

- Prioritizes tables over business concepts.
- Leads to an anemic domain model.

---

## Service-Oriented Domain Split

Rejected for the MVP because:

- Unnecessary complexity.
- Better suited for future microservice architectures.

---

# Consequences

## Positive

- Shared business language.
- Clear ownership.
- Stable API contracts.
- Consistent database schema.
- Easier onboarding.
- Better documentation.
- Improved AI-assisted development.

---

## Negative

- Requires discipline to preserve domain boundaries.
- Initial modeling effort is higher.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every business concept belongs to a domain.
- Aggregate ownership is respected.
- Domain terminology remains consistent.
- APIs reflect the domain model.
- Database schema aligns with aggregate boundaries.
- Business rules reside in the domain layer.
- User-owned entities use soft deletes unless otherwise justified.

Changes to the core domain model require a new ADR.

# Decision Summary

CareerOS adopts a **domain-driven business model** centered on clearly defined aggregate roots such as Users, Companies, Jobs, Applications, Tasks, Notes, and Resumes. These domains form the foundation for the database schema, API design, business logic, backlog organization, and future platform evolution, ensuring a consistent and scalable architecture across all CareerOS applications.
