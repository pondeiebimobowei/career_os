# ADR-031: TypeScript Strict Mode

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a TypeScript-first platform consisting of:

- Web applications
- Backend services
- Browser extensions
- Shared packages
- CLI tooling
- AI-assisted development tools

The majority of the codebase is shared across multiple applications and packages.

Without strict type checking, the project becomes vulnerable to:

- runtime type errors,
- null reference exceptions,
- unsafe API contracts,
- incorrect assumptions,
- fragile refactoring,
- inconsistent developer experience.

As the project grows and AI contributes code generation, compile-time correctness becomes increasingly important.

CareerOS therefore requires a strict, repository-wide TypeScript configuration.

---

# Decision

CareerOS enables **TypeScript Strict Mode** across the entire repository.

Every application, package, service, CLI, and shared library must compile successfully under strict type checking.

Strict mode is mandatory and may not be disabled for individual packages without an approved architectural decision.

---

# Goals

Strict Mode should:

- eliminate common runtime errors,
- improve developer confidence,
- strengthen API contracts,
- simplify refactoring,
- improve IDE support,
- improve AI-generated code quality,
- encourage explicit modeling.

---

# Repository Policy

Every TypeScript project inherits the shared repository configuration.

Example:

```text
packages/config/typescript

↓

apps/*

packages/*
```

Individual projects may extend the configuration but must not weaken strictness.

---

# Strict Compiler Options

The repository enables:

```json
{
  "strict": true
}
```

This enables the TypeScript strict family of compiler checks.

---

# Null Safety

Null and undefined are treated as distinct types.

Developers must explicitly handle nullable values.

Example:

Good:

```typescript
if (user != null) {
  // ...
}
```

Avoid:

```typescript
user.name
```

without verifying that `user` exists.

---

# No Implicit Any

Implicit `any` is prohibited.

Bad:

```typescript
function process(data) {
  return data.id;
}
```

Good:

```typescript
function process(data: User) {
  return data.id;
}
```

Every public API should expose explicit types.

---

# Type Inference

Type inference is encouraged where it improves readability.

Explicit annotations should be added when:

- public APIs are defined,
- inference becomes ambiguous,
- readability suffers.

The goal is clarity rather than verbosity.

---

# Unknown over Any

When the type is not known, prefer:

```typescript
unknown
```

instead of:

```typescript
any
```

`unknown` forces explicit narrowing before use.

---

# Type Narrowing

Runtime checks should narrow uncertain values.

Example:

```typescript
if (typeof value === "string") {
    // value is string
}
```

Type assertions should be minimized.

---

# Non-Null Assertions

The non-null assertion operator:

```typescript
!
```

should be avoided.

It is permitted only when:

- correctness is guaranteed,
- alternative approaches are impractical,
- the reasoning is obvious from surrounding code.

---

# Type Assertions

Avoid unnecessary assertions.

Bad:

```typescript
const user = value as User;
```

Preferred:

- validation,
- parsing,
- narrowing,
- runtime checks.

Assertions should not hide type problems.

---

# Exhaustive Switches

Union types should be handled exhaustively.

Example:

```typescript
switch (status) {
    case "pending":
    case "completed":
    case "failed":
        break;

    default:
        assertNever(status);
}
```

Compiler errors should surface when new variants are introduced.

---

# Interfaces vs Types

Guidelines:

Use **interfaces** for:

- object contracts,
- public APIs,
- dependency abstractions.

Use **type aliases** for:

- unions,
- mapped types,
- utility types,
- compositions.

Consistency is preferred over rigid rules.

---

# Readonly by Default

Immutable data should be modeled using:

```typescript
readonly
```

where practical.

Immutability reduces accidental mutation and improves reasoning.

---

# Enums

Prefer:

- string literal unions,
- const objects,

over traditional TypeScript enums unless enums provide a clear benefit.

Example:

```typescript
type Status =
    | "pending"
    | "completed"
    | "failed";
```

---

# Utility Types

Prefer existing TypeScript utilities when appropriate.

Examples:

- Partial
- Pick
- Omit
- Record
- Required
- Readonly

Avoid recreating standard utilities.

---

# Validation

Compile-time types do not replace runtime validation.

External inputs should be validated using repository-approved validation libraries.

Examples include:

- HTTP requests,
- browser messages,
- database input,
- third-party APIs.

---

# Shared Types

Shared domain types belong in shared packages.

Avoid duplicating type definitions across applications.

---

# Public APIs

Every exported function, class, and interface should expose stable, explicit typing.

Public APIs should not rely on implicit inference.

---

# AI-Assisted Development

AI-generated TypeScript code must:

- compile under strict mode,
- avoid `any`,
- use existing shared types,
- preserve type safety,
- avoid unnecessary assertions.

Generated code should strengthen rather than weaken typing.

---

# Testing

Tests are also written in strict TypeScript.

Mocks and fixtures should remain fully typed whenever practical.

Using `any` in tests is discouraged unless there is a compelling reason.

---

# Build Enforcement

Continuous Integration executes:

```bash
pnpm check-types
```

Compilation failures block merging.

No package is exempt from strict type checking.

---

# Refactoring

Strong typing should support safe refactoring.

Compiler errors should guide developers to affected code whenever contracts change.

---

# Exceptions

Temporary exceptions require:

- documented justification,
- clear TODO,
- planned removal.

Permanent disabling of strict mode is prohibited.

---

# Alternatives Considered

## Loose TypeScript

Rejected because:

- weaker guarantees,
- runtime failures,
- inconsistent APIs.

---

## JavaScript

Rejected because:

- no static analysis,
- weaker tooling,
- higher maintenance cost.

---

## Selective Strictness

Rejected because:

- inconsistent developer experience,
- uneven code quality,
- difficult maintenance.

---

# Consequences

## Positive

- Improved correctness.
- Safer refactoring.
- Better IDE support.
- Stronger APIs.
- Better AI-generated code.
- Reduced runtime errors.

---

## Negative

- More explicit typing.
- Slightly higher learning curve.
- Additional compiler errors during development.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- TypeScript Strict Mode is enabled repository-wide.
- `any` should be avoided unless explicitly justified.
- External inputs are validated at runtime.
- Public APIs expose explicit types.
- Shared types are reused rather than duplicated.
- Compiler warnings are treated as engineering work, not ignored.
- CI blocks merges when type checking fails.
- AI-generated code must compile under strict mode.

Changes to the TypeScript configuration require a new ADR.

# Decision Summary

CareerOS adopts **TypeScript Strict Mode** across the entire repository. Every application, package, service, browser extension, and CLI must compile successfully with strict type checking enabled. Developers are expected to favor explicit, well-modeled types, avoid unsafe constructs such as `any`, validate external inputs at runtime, and leverage the compiler as a primary tool for correctness, maintainability, and safe refactoring. Strict typing is a foundational part of the project's engineering standards and AI-assisted development workflow.
