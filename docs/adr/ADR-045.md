# ADR-045 — Feature Flag Strategy

- **Status:** Superseded
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** ADR-046

---

# Context

CareerOS is an actively evolving platform consisting of multiple independently deployable applications:

- Backend API
- Web Application
- Browser Extension
- Shared Packages
- Background Jobs
- Future Mobile Application

As the platform grows, features will increasingly need to be:

- released gradually
- tested in production
- enabled for selected users
- disabled quickly without redeployment
- experimented with safely

Examples include:

- New parsers
- AI-powered resume analysis
- Resume scoring
- Analytics dashboards
- Experimental synchronization engine
- New browser platforms
- Beta features

Without feature flags, deployments become tightly coupled to releases, increasing operational risk.

---

# Decision

CareerOS will adopt a centralized, configuration-driven feature flag system.

Feature flags control feature availability independently from deployments.

The system supports:

1. Global flags
2. Environment flags
3. User-targeted flags
4. Percentage rollouts
5. Time-based activation
6. Emergency kill switches

Feature flags are temporary release mechanisms, not permanent architecture.

---

# Goals

The feature flag system should enable:

- Safe deployments
- Progressive rollouts
- Canary releases
- Internal testing
- Beta programs
- Fast rollback
- Reduced deployment risk

---

# Architecture

```text
Application

↓

Feature Flag Service

↓

Flag Evaluation

↓

Application Decision

↓

Feature Enabled

or

↓

Feature Disabled
```

Business logic remains independent of deployment timing.

---

# Feature Flag Types

## Release Flags

Used to gradually introduce new functionality.

Examples:

```text
resume-library-v2

analytics-dashboard-v2

new-sync-engine
```

These flags should be removed after full rollout.

---

## Experiment Flags

Used for A/B testing.

Examples:

```text
new-onboarding-flow

dashboard-layout-b

resume-upload-flow-v2
```

Experiments should have defined success metrics.

---

## Operational Flags

Control operational behavior.

Examples:

```text
background-sync-enabled

parser-debug-mode

maintenance-mode
```

These may remain long-term if operationally valuable.

---

## Permission Flags

Enable functionality based on user plans or roles.

Examples:

```text
premium-resume-library

advanced-analytics

team-workspaces
```

Permission flags are part of authorization and may persist indefinitely.

---

# Evaluation Order

Feature evaluation occurs in the following order:

```text
Emergency Kill Switch

↓

Environment Rules

↓

User Targeting

↓

Percentage Rollout

↓

Default Value
```

The first matching rule determines the result.

---

# Sources of Truth

Feature flag definitions are centrally managed.

Applications should not hardcode feature availability.

Flags may be delivered through:

- backend configuration
- cached configuration
- build-time defaults (for development only)

---

# Flag Naming

Flags use lowercase kebab-case.

Examples:

```text
resume-library-v2

new-sync-engine

ai-resume-review

greenhouse-parser-v2
```

Avoid vague names such as:

```text
feature1

test

new-ui
```

Names should clearly describe functionality.

---

# Flag Ownership

Every feature flag must have:

- owner
- creation date
- intended removal date
- associated feature
- rollout plan

Unowned flags should not exist.

---

# Lifecycle

Every feature flag progresses through:

```text
Created

↓

Development

↓

Internal Testing

↓

Beta

↓

General Availability

↓

Flag Removed
```

Flags should not remain indefinitely after rollout.

---

# Environment Support

Each environment may have independent flag values.

Supported environments:

- Development
- Staging
- Production

Production flags should not affect development workflows.

---

# Browser Extension

Feature flags may control:

- parser availability
- synchronization engine versions
- diagnostics
- experimental UI
- platform support

Flags should synchronize from the backend where appropriate.

---

# Backend

The backend is responsible for:

- flag evaluation (where required)
- serving configuration
- authorization-aware flags
- rollout management

Critical business decisions should not rely solely on client evaluation.

---

# Percentage Rollouts

Features may be enabled gradually.

Example:

```text
1%

↓

5%

↓

10%

↓

25%

↓

50%

↓

100%
```

Users should receive stable assignments.

Percentage allocation should be deterministic.

---

# User Targeting

Flags may target:

- internal users
- beta testers
- administrators
- premium users
- selected organizations

Targeting rules should be explicit and auditable.

---

# Emergency Kill Switch

Critical features should support immediate deactivation.

Examples:

- faulty parser
- unstable synchronization engine
- AI integration outage

Kill switches should not require redeployment.

---

# Caching

Applications may cache flag configurations.

Requirements:

- configurable expiration
- background refresh
- safe defaults

Applications should continue operating if flag retrieval temporarily fails.

---

# Offline Behavior

Browser Extension behavior:

If offline:

- use cached configuration
- apply expiration policy
- refresh when connectivity returns

Users should experience predictable behavior.

---

# Defaults

Every flag defines a default value.

Defaults should be conservative.

Example:

```text
Experimental Feature

Default:

Disabled
```

---

# Security

Feature flags must never expose:

- secrets
- privileged configuration
- internal infrastructure details

Permission-based features still require backend authorization.

Feature flags do not replace access control.

---

# Observability

Every evaluation may emit analytics events.

Examples:

- feature enabled
- feature disabled
- rollout participation
- experiment assignment

Analytics should support rollout evaluation.

---

# Logging

Feature evaluations should log:

- flag name
- evaluated value
- source
- application version

Sensitive targeting rules should not appear in client logs.

---

# Testing

Feature flags require:

## Unit Tests

- evaluation logic
- rollout calculations
- cache behavior

---

## Integration Tests

- backend configuration
- Browser Extension synchronization
- environment overrides

---

## End-to-End Tests

Verify:

- gradual rollout
- kill switch behavior
- offline operation
- cache refresh
- targeted users

---

# Documentation

Each feature flag should document:

- purpose
- owner
- rollout strategy
- removal plan
- associated issue
- associated ADR (if applicable)

Documentation prevents long-lived flag accumulation.

---

# Technical Debt

Feature flags are temporary unless explicitly classified as operational or permission flags.

Completed rollout flags should be removed promptly.

Engineering should periodically review and retire obsolete flags.

---

# AI Assistant Rules

AI-assisted development must:

- avoid introducing permanent release flags
- preserve existing rollout logic
- remove obsolete flags when completing migrations
- update tests when flag behavior changes
- document newly introduced flags

Feature flag additions should include an ownership and retirement plan.

---

# Future Enhancements

Potential future capabilities include:

- Remote configuration service
- Experiment analytics dashboard
- Multi-variant experiments
- Organization-level configuration
- Dynamic rollout rules
- Scheduled activations

These enhancements should build upon the same architectural model.

---

# Consequences

## Positive

- Safer production releases
- Progressive feature rollouts
- Faster rollback capability
- Improved experimentation
- Reduced deployment risk
- Better operational flexibility

## Negative

- Additional configuration management
- Increased testing complexity
- Potential technical debt from stale flags
- Operational overhead for rollout management

---

# Compliance

All CareerOS applications, Browser Extension modules, backend services, and future client applications must implement feature flags according to this strategy.

Feature flags must never replace authorization or security controls.

Any deviation requires an approved Architecture Decision Record (ADR).
