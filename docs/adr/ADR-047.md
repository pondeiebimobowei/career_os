# ADR-047 — Versioning Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-009 (Shared Packages Strategy), ADR-036 (CI/CD), ADR-046 (Release Strategy)
- **Superseded By:** None

---

# Context

CareerOS is developed as a monorepo containing multiple independently deployable applications and shared packages.

Current architecture includes:

- Backend API
- Web Application
- Browser Extension
- Shared Packages
- Database Schema
- API Contracts
- Parser Framework
- Browser Extension Parsers
- Infrastructure
- Documentation

Each component evolves at a different pace.

Without a clearly defined versioning strategy, the platform risks:

- incompatible deployments
- API contract mismatches
- parser incompatibilities
- browser extension synchronization failures
- package dependency conflicts
- difficult rollbacks
- unclear release history

CareerOS therefore requires a unified versioning strategy that applies consistently across the platform.

---

# Decision

CareerOS adopts **Semantic Versioning (SemVer 2.0.0)** as the primary versioning strategy.

The strategy applies to:

- applications
- shared packages
- APIs
- schemas
- parsers
- browser extension releases
- documentation releases

Versioning communicates compatibility, not development effort.

---

# Version Format

The standard format is:

```text
MAJOR.MINOR.PATCH
```

Examples:

```text
1.0.0

1.1.0

1.1.7

2.0.0
```

Optional pre-release identifiers may be used during development.

---

# Semantic Meaning

## MAJOR

Increment when introducing breaking changes.

Examples:

- incompatible API changes
- breaking parser interfaces
- incompatible shared package contracts
- removed endpoints
- incompatible synchronization protocol

---

## MINOR

Increment when introducing backward-compatible functionality.

Examples:

- new parser
- new API endpoint
- new dashboard
- additional analytics
- new browser extension capability

---

## PATCH

Increment when introducing backward-compatible fixes.

Examples:

- parser bug fix
- UI bug
- synchronization improvement
- documentation correction
- performance optimization

---

# Pre-Release Versions

Development builds may include identifiers.

Examples:

```text
1.2.0-alpha.1

1.2.0-beta.2

1.2.0-rc.1
```

Definitions:

- alpha → active development
- beta → feature complete, testing
- rc → release candidate

Production releases should not use pre-release identifiers.

---

# Build Metadata

Build metadata may be appended when required.

Example:

```text
1.3.0+20260806

1.4.1+build.152
```

Build metadata does not affect version precedence.

---

# Monorepo Strategy

Applications maintain independent versions.

Example:

```text
Backend API

v1.6.0

Web Application

v1.4.3

Browser Extension

v1.3.2

Shared UI Package

v2.1.0
```

Independent versioning minimizes unnecessary releases.

---

# Backend Versioning

The Backend API follows semantic versioning.

Breaking API changes require:

- MAJOR version increment
- migration documentation
- compatibility assessment

Backward compatibility should be maintained whenever practical.

---

# API Versioning

Public APIs should expose explicit versions.

Preferred format:

```text
/api/v1
```

Future incompatible APIs:

```text
/api/v2
```

API versioning is independent of application versioning.

---

# Database Schema Versioning

Database schema changes are tracked through Prisma migrations.

Each migration represents a schema version increment.

Requirements:

- deterministic
- ordered
- reproducible

Database migration history is immutable.

---

# Shared Package Versioning

Each shared package follows independent semantic versioning.

Breaking contract changes require:

- major version
- migration notes
- updated documentation

Consumers should intentionally upgrade major versions.

---

# Browser Extension Versioning

Browser Extension releases follow semantic versioning.

Example:

```text
1.5.0
```

Version increments should reflect user-visible functionality rather than store submission count.

---

# Parser Versioning

Every parser maintains its own version.

Example:

```text
LinkedIn Parser

2.1.0

Greenhouse Parser

1.4.2
```

Parser versions assist with diagnostics and compatibility tracking.

---

# Synchronization Protocol Version

Synchronization payloads include a protocol version.

Example:

```text
Protocol Version

1
```

Protocol changes should remain backward compatible where possible.

Breaking protocol changes require staged deployment.

---

# Event Schema Versioning

Analytics events include schema versions.

Example:

```text
Event Schema

v1
```

Breaking analytics schema changes require a new version.

---

# Resume Schema Versioning

Resume metadata structures should include version information.

Benefits:

- migration support
- compatibility
- future evolution

---

# Configuration Versioning

Configuration formats should define explicit versions.

Example:

```yaml
version: 1
```

Configuration migrations should be deterministic.

---

# YAML Backlog Versioning

Backlog definitions include schema versions.

Example:

```yaml
schemaVersion: 1
```

Schema evolution should preserve compatibility where possible.

---

# Documentation Versioning

Major architectural documentation should evolve alongside platform releases.

Examples:

- ADRs
- API documentation
- architecture guides

Documentation versions should reflect platform evolution.

---

# Dependency Versioning

External dependencies should:

- follow pinned version ranges where appropriate
- upgrade intentionally
- avoid uncontrolled major upgrades

Major dependency upgrades require testing.

---

# Compatibility Matrix

Engineering should maintain compatibility between:

- Backend API ↔ Browser Extension
- Backend API ↔ Web Application
- Shared Packages ↔ Applications
- Synchronization Protocol ↔ Extension
- Parser Framework ↔ Parsers

Compatibility should be documented before major releases.

---

# Deprecation Policy

Breaking changes should follow a defined deprecation process.

Example:

```text
Announce

↓

Deprecate

↓

Maintain

↓

Remove
```

Deprecation periods should provide adequate migration time.

---

# Version Source of Truth

Versions should be defined in source control.

They should never be manually maintained in multiple locations.

Automation should propagate versions during build and release processes.

---

# Release Tagging

Every production release should create a Git tag.

Example:

```text
v1.4.0

v2.0.1
```

Git tags provide immutable release references.

---

# Changelog Integration

Version increments should accompany changelog updates.

Recommended categories:

- Added
- Changed
- Fixed
- Deprecated
- Removed
- Security

Version history should be transparent.

---

# CI/CD Integration

The CI pipeline should verify:

- version consistency
- changelog presence (where applicable)
- package compatibility
- migration ordering

Versioning should be automated where practical.

---

# Rollback

Version history should support rollback.

Rollback targets must be:

- identifiable
- reproducible
- documented

Version metadata simplifies operational recovery.

---

# Observability

Operational telemetry should include:

- application version
- parser version
- synchronization protocol version
- API version

Version information improves incident diagnosis.

---

# Testing

Version-related testing includes:

## Unit Tests

- version parsing
- compatibility logic

---

## Integration Tests

- package compatibility
- API compatibility
- protocol compatibility

---

## Release Validation

Verify:

- version increments
- release tags
- changelog updates
- migration sequencing

---

# AI Assistant Rules

AI-assisted development must:

- preserve semantic versioning
- avoid arbitrary version increments
- update version-related documentation
- maintain compatibility rules
- document breaking changes
- update migration guidance for major releases

Version changes should accompany corresponding release documentation.

---

# Future Enhancements

Potential future improvements include:

- automated semantic release
- conventional commit-based version generation
- automated changelog generation
- package release automation
- compatibility dashboards

These enhancements should extend rather than replace the core strategy.

---

# Consequences

## Positive

- Clear compatibility expectations
- Predictable release management
- Easier dependency management
- Improved rollback capability
- Consistent version communication
- Better operational diagnostics

## Negative

- Additional release discipline
- Version governance overhead
- Documentation maintenance
- Compatibility testing requirements

---

# Compliance

All CareerOS applications, Browser Extension components, backend services, shared packages, schemas, APIs, parsers, and future platform modules must follow this versioning strategy.

Breaking compatibility requires a major version increment and appropriate migration documentation.

Any deviation requires an approved Architecture Decision Record (ADR).
