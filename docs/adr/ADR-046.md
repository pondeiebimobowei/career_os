# ADR-046 — Release Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-026 (Trunk-Based Development), ADR-035 (Deployment Platform), ADR-036 (CI/CD), ADR-045 (Feature Flag Strategy)
- **Superseded By:** None

---

# Context

CareerOS is a multi-application platform developed within a monorepo.

The platform currently consists of:

- Backend API
- Web Application
- Browser Extension
- Shared Packages
- GitHub Actions
- Deployment Infrastructure
- Future Mobile Applications

Each application has different release constraints.

Examples:

- The Backend API can be deployed multiple times per day.
- The Web Application can be deployed immediately after successful CI.
- The Browser Extension requires review and publication through browser extension stores.
- Shared packages must be versioned without breaking downstream consumers.

To support rapid delivery while maintaining stability, CareerOS requires a standardized release strategy.

---

# Decision

CareerOS adopts a **Continuous Delivery** release strategy with controlled production promotion.

The strategy combines:

1. Trunk-Based Development
2. Automated CI/CD
3. Progressive Rollouts
4. Feature Flags
5. Semantic Versioning
6. Release Documentation
7. Safe Rollback Procedures

Deployment and release are treated as separate concerns.

---

# Release Principles

The release strategy follows these principles:

- Deploy frequently
- Release safely
- Keep releases small
- Automate repetitive work
- Roll back quickly
- Measure release quality
- Minimize production risk

---

# Release Workflow

```text
Development

↓

Pull Request

↓

Code Review

↓

CI Pipeline

↓

Merge to Main

↓

Automated Deployment

↓

Verification

↓

Feature Flag Rollout

↓

Production Release
```

Production availability may occur after deployment through feature flags.

---

# Branch Strategy

Development follows ADR-026.

Workflow:

```text
main

↓

Short-lived Feature Branch

↓

Pull Request

↓

Merge

↓

Delete Branch
```

Long-lived development branches are not permitted.

---

# Versioning

CareerOS uses Semantic Versioning (SemVer).

Format:

```text
MAJOR.MINOR.PATCH
```

Examples:

```text
1.0.0

1.2.0

1.2.4
```

---

# Version Rules

## MAJOR

Breaking API or contract changes.

---

## MINOR

New backward-compatible functionality.

---

## PATCH

Bug fixes.

---

# Release Scope

Every release should include:

- implemented features
- bug fixes
- migrations
- documentation updates
- relevant ADRs
- changelog entries

Large, unrelated changes should be split into separate releases where practical.

---

# Application Release Independence

Applications may release independently.

Examples:

```text
Backend

v1.6.0

↓

Web

v1.4.2

↓

Extension

v1.3.1
```

Independent releases reduce coupling.

---

# Backend Releases

Backend deployments should be:

- automated
- repeatable
- reversible

Deployment should occur after successful CI.

---

# Web Application Releases

The Web Application supports continuous deployment.

Requirements:

- successful build
- passing tests
- deployment verification

Feature visibility may still be controlled through feature flags.

---

# Browser Extension Releases

Browser Extension releases require additional validation.

Release workflow:

```text
Build

↓

Tests

↓

Package

↓

Manual Verification

↓

Store Submission

↓

Store Approval

↓

Public Availability
```

Store approval timelines are outside engineering control.

---

# Shared Package Releases

Shared packages should:

- follow semantic versioning
- preserve backward compatibility
- document breaking changes

Consumers should upgrade intentionally.

---

# Database Migrations

Database migrations are part of the release process.

Requirements:

- reviewed
- tested
- reversible where possible

Breaking schema changes should be introduced incrementally.

---

# Feature Flags

Feature rollout is controlled independently of deployment.

Example:

```text
Deploy

↓

Feature Disabled

↓

Internal Testing

↓

5%

↓

25%

↓

100%
```

Feature flags reduce release risk.

---

# Release Frequency

Preferred cadence:

Backend:

- multiple releases per week (or daily)

Web Application:

- continuous deployment

Browser Extension:

- as required by feature readiness and store approval

Release frequency should optimize quality and responsiveness.

---

# Release Checklist

Before release:

- CI passing
- code reviewed
- documentation updated
- migrations verified
- feature flags configured
- monitoring prepared
- rollback plan confirmed

No production release should bypass the checklist.

---

# Changelog

Every release should produce a changelog.

Recommended sections:

- Added
- Changed
- Fixed
- Deprecated
- Removed
- Security

Changelogs improve transparency for developers and users.

---

# Release Notes

User-facing releases should include concise release notes.

Examples:

- new features
- improvements
- bug fixes
- known limitations

Release notes should focus on user impact rather than implementation details.

---

# Rollback Strategy

Every deployment should support rollback.

Rollback methods include:

- application rollback
- infrastructure rollback
- feature flag disablement

Rollback should be documented and tested.

---

# Hotfix Releases

Critical production issues may require hotfixes.

Workflow:

```text
Issue Detected

↓

Fix

↓

Review

↓

CI

↓

Deploy

↓

Post-Release Verification
```

Hotfixes should be merged back into `main` immediately after deployment.

---

# Release Verification

After deployment, verify:

- application startup
- health endpoints
- database connectivity
- authentication
- synchronization
- critical user workflows

Verification confirms deployment success before broader rollout.

---

# Monitoring

Release monitoring should observe:

- error rates
- response times
- deployment success
- synchronization failures
- parser failures
- user impact

Unexpected regressions should trigger investigation.

---

# Incident Response

If a release causes significant production issues:

1. Assess impact.
2. Roll back or disable affected features.
3. Stabilize production.
4. Investigate root cause.
5. Document findings.
6. Implement preventive improvements.

Incident response prioritizes service restoration.

---

# Release Metrics

Track:

- deployment frequency
- lead time for changes
- change failure rate
- mean time to recovery (MTTR)
- rollback frequency

These metrics support continuous delivery maturity.

---

# Browser Extension Compatibility

The Backend API should maintain compatibility with supported Browser Extension versions during rollout.

Breaking synchronization changes require version negotiation or staged deployment.

---

# Documentation

Every release should update relevant:

- ADRs
- implementation plans
- backlog items
- architecture documentation
- API documentation

Documentation is part of the release, not a follow-up task.

---

# Testing Requirements

Releases require:

## Unit Tests

Pass

---

## Integration Tests

Pass

---

## End-to-End Tests

Critical workflows verified

---

## Manual Verification

Required for Browser Extension releases and high-risk changes.

---

# AI Assistant Rules

AI-assisted development must:

- preserve release automation
- avoid bypassing CI
- update changelogs where applicable
- maintain semantic versioning
- respect feature flag rollout strategy
- update documentation alongside code changes

Release-related changes require corresponding tests and documentation.

---

# Future Enhancements

Potential future improvements include:

- Automated release notes generation
- Canary deployments
- Blue-green deployments
- Progressive infrastructure rollouts
- Automated rollback based on health metrics
- Multi-region deployment orchestration

These enhancements should extend the existing release strategy rather than replace it.

---

# Consequences

## Positive

- Predictable release process
- Faster delivery of features
- Reduced deployment risk
- Consistent version management
- Improved operational visibility
- Easier rollback during incidents

## Negative

- Additional release process discipline
- Documentation overhead
- More comprehensive testing requirements
- Operational monitoring responsibilities

---

# Compliance

All CareerOS applications, Browser Extension releases, backend deployments, shared packages, and future client applications must follow this release strategy.

Production deployments must satisfy CI requirements, documentation standards, and release verification procedures before feature rollout.

Any deviation requires an approved Architecture Decision Record (ADR).
