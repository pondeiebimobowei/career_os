# ADR-050 — Documentation Hierarchy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-049 (Documentation as Code), ADR-027 (Engineering Playbook)
- **Superseded By:** None

---

# Context

CareerOS is intended to be a long-lived engineering platform with multiple applications, shared packages, infrastructure, browser extensions, and extensive product documentation.

As the codebase grows, so does the amount of documentation.

Without a well-defined hierarchy, documentation quickly becomes:

- duplicated
- inconsistent
- difficult to discover
- contradictory
- outdated
- difficult for AI assistants to navigate
- difficult for new contributors to understand

A consistent documentation hierarchy establishes where information belongs, prevents duplication, and creates a predictable structure for both humans and automation.

---

# Decision

CareerOS adopts a **layered documentation hierarchy**.

Each documentation type has:

- a clearly defined purpose
- a single source of truth
- an intended audience
- an ownership model
- relationships with other documentation

Documentation should flow from **high-level strategy** down to **implementation details**, never the reverse.

---

# Documentation Philosophy

The documentation hierarchy follows this progression:

```text
Vision

↓

Product

↓

Architecture

↓

Engineering Standards

↓

Implementation

↓

Code

↓

Operations
```

Higher levels explain **why**.

Lower levels explain **how**.

# Documentation Layers

## Layer 1 — Repository Documentation

Purpose:

Repository orientation.

Contains:

- project overview
- quick start
- contribution guide
- repository structure
- development setup

Primary file:

```text
README.md
```

Audience:

Everyone.

---

## Layer 2 — Product Documentation

Purpose:

Explain **what** CareerOS is.

Contains:

- vision
- objectives
- personas
- feature definitions
- workflows
- roadmap
- business rules

Audience:

Product, engineering, design.

---

## Layer 3 — Architecture Documentation

Purpose:

Explain **why** technical decisions exist.

Contains:

- ADRs
- architecture diagrams
- system boundaries
- domain models
- integration architecture

Audience:

Engineers.

Architecture documentation should rarely change after acceptance.

---

## Layer 4 — Engineering Documentation

Purpose:

Standardize engineering practices.

Contains:

- coding standards
- branching strategy
- pull request process
- testing strategy
- AI operational rules
- development workflow

Audience:

Developers.

---

## Layer 5 — Implementation Documentation

Purpose:

Explain **how the work will be executed**.

Contains:

- implementation roadmap
- project phases
- milestones
- sequencing
- dependencies

Audience:

Developers.

Implementation documents evolve throughout development.

---

## Layer 6 — Technical Documentation

Purpose:

Describe technical systems.

Examples:

Backend:

- services
- APIs
- authentication

Browser Extension:

- parser architecture
- messaging
- synchronization

Frontend:

- routing
- state management
- component architecture

Infrastructure:

- deployments
- networking

Audience:

Developers.

---

## Layer 7 — Reference Documentation

Purpose:

Provide lookup information.

Examples:

- API reference
- schema reference
- parser reference
- environment variables
- configuration

Reference documentation should be factual rather than explanatory.

---

## Layer 8 — Operational Documentation

Purpose:

Support production operations.

Examples:

- deployments
- monitoring
- backups
- disaster recovery
- incident response
- troubleshooting

Audience:

Engineering and operations.

---

# Documentation Relationships

Information flows downward.

Example:

```text
Product Vision

↓

Architecture Decision

↓

Engineering Standard

↓

Implementation Plan

↓

Code

↓

Operations
```

Lower layers should reference higher layers.

Higher layers should not depend on implementation details.

---

# Single Source of Truth

Every subject has one authoritative location.

Examples:

| Topic | Source |
|--------|--------|
| Product Scope | Product Docs |
| Architecture | ADRs |
| Development Process | Engineering Docs |
| API Contracts | API Documentation |
| Database Schema | Prisma Schema |
| Implementation Order | Implementation Plan |
| Deployment Process | Operations Documentation |

Duplicate documentation should be eliminated.

---

# Documentation Discovery

Documentation should be discoverable within three steps.

Example:

```text
README

↓

docs/

↓

Target Document
```

Deep nesting should be avoided unless justified.

---

# README Strategy

Every major directory should contain a README.

Examples:

```text
apps/

README.md

packages/

README.md

docs/

README.md

browser-extension/

README.md
```

READMEs should describe:

- purpose
- contents
- navigation
- ownership

---

# ADR Organization

Architecture Decision Records are stored under:

```text
docs/architecture/adr/
```

Naming convention:

```text
ADR-001

ADR-002

...

ADR-050
```

Each ADR is immutable after acceptance except for status updates or clarifications.

# Documentation Ownership

Each documentation area has an owner.

Ownership includes:

- accuracy
- updates
- reviews
- restructuring
- archival

Ownership should be explicit.

---

# Documentation Lifecycle

Documentation follows this lifecycle:

```text
Draft

↓

Review

↓

Approved

↓

Published

↓

Maintained

↓

Deprecated

↓

Archived
```

Documentation should never become orphaned.

---

# Cross-Referencing

Documentation should link to related documents.

Examples:

An implementation plan should reference:

- relevant ADRs
- product requirements
- engineering standards

Cross-referencing improves discoverability and consistency.

---

# AI Navigation

The hierarchy is designed to support AI-assisted development.

AI agents should resolve questions in the following order:

1. Product Documentation
2. ADRs
3. Engineering Standards
4. Implementation Plan
5. Technical Documentation
6. Source Code

This ordering reduces contradictory guidance.

---

# Automation

Future automation may include:

- documentation indexing
- dependency graphs
- broken-link detection
- ADR relationship mapping
- documentation coverage reports
- documentation search

Automation should reinforce the hierarchy rather than replace it.

---

# AI Assistant Rules

AI-assisted development must:

- place new documentation in the correct layer
- avoid creating duplicate sources of truth
- update related documents when introducing architectural changes
- preserve documentation hierarchy
- maintain cross-references
- recommend ADRs for architectural decisions

Documentation structure should remain predictable.

---

# Consequences

## Positive

- Clear information architecture
- Faster onboarding
- Reduced duplication
- Better documentation discoverability
- Improved architectural consistency
- Strong foundation for AI-assisted engineering

## Negative

- Additional organizational discipline
- Initial documentation restructuring effort
- Ongoing maintenance responsibility

---

# Compliance

All CareerOS documentation must conform to this hierarchy.

New documentation should be placed in the appropriate layer, reference higher-level documentation where applicable, and avoid creating duplicate sources of truth.

Any deviation requires an approved Architecture Decision Record (ADR).
