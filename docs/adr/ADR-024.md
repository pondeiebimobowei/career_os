# ADR-024: Pull Request Convention

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is developed using:

- Repository-first planning
- CBS v1.0 backlog management
- GitHub Issues generated from YAML
- AI-assisted implementation
- Continuous integration
- Protected branches
- Mandatory code reviews

The Pull Request (PR) is the primary mechanism through which code enters the `main` branch.

Without a standardized PR convention:

- Reviews become inconsistent.
- Important implementation context is lost.
- Acceptance criteria are overlooked.
- Releases become difficult to audit.
- AI-generated code becomes harder to verify.

CareerOS therefore requires a deterministic pull request convention.

---

# Decision

Every code change merged into the repository **must** go through a Pull Request that follows the CareerOS Pull Request Convention.

Pull requests are execution artifacts that connect:

- Backlog issues
- Feature branches
- Code changes
- Reviews
- CI validation
- Releases

The Backlog CLI generates PR metadata directly from the YAML backlog.

---

# Goals

The PR convention should:

- Standardize reviews.
- Improve code quality.
- Preserve implementation context.
- Enable automation.
- Support AI-assisted development.
- Simplify release generation.
- Improve repository history.

---

# Pull Request Lifecycle

Every implementation follows the same workflow.

```text
Backlog Issue

↓

Feature Branch

↓

Implementation

↓

Pull Request

↓

Review

↓

Merge

↓

Delete Branch
```

---

# Source of Truth

PR content is derived from:

```text
CBS Schema

↓

Backlog YAML

↓

GitHub Issue

↓

Pull Request
```

The backlog defines *what* should be built.

The PR explains *how* it was built.

---

# Pull Request Ownership

Each PR should implement **one primary backlog issue**.

Example:

```text
APP-001

↓

feature/app-001-create-application

↓

PR
```

Large features should be split into multiple backlog issues rather than merged in a single oversized PR.

---

# PR Title Format

Every PR title follows:

```text
<ISSUE-ID>: <Short Description>
```

Examples:

```text
APP-001: Create application creation API
```

```text
JOB-014: Add company filtering
```

```text
EXT-009: Implement LinkedIn parser
```

---

# PR Description Structure

Every PR follows the same structure.

```markdown
## Summary

## Related Issue

## Changes

## Acceptance Criteria

## Testing

## Screenshots (if applicable)

## Checklist
```

The Backlog CLI generates this structure automatically.

---

# Summary

The summary explains:

- What changed.
- Why it changed.
- Scope of implementation.

Implementation details belong later in the PR.

---

# Related Issue

Every PR links the associated GitHub Issue.

Example:

```text
Fixes #APP-001
```

or

```text
Closes #APP-001
```

Closing keywords ensure GitHub automatically closes the issue after merge.

---

# Changes Section

Summarizes implementation work.

Examples:

- Added application API endpoint.
- Added validation.
- Added repository implementation.
- Added tests.
- Updated documentation.

This section is concise and implementation-focused.

---

# Acceptance Criteria

Acceptance criteria are copied directly from the backlog.

Example:

```markdown
- [x] User can create an application.
- [x] Validation errors are returned correctly.
- [x] Application appears in dashboard.
```

Reviewers verify these criteria before approval.

---

# Testing Section

The author documents verification performed.

Examples:

- Unit tests
- Integration tests
- End-to-end tests
- Manual verification
- Browser testing

Example:

```text
✓ Unit Tests

✓ Integration Tests

✓ Manual Testing
```

---

# Screenshots

Required when UI changes are introduced.

Examples:

- Dashboard updates
- Browser extension UI
- Mobile interface
- Responsive layouts

Backend-only changes do not require screenshots.

---

# Checklist

Recommended checklist:

```markdown
- [ ] Acceptance criteria satisfied
- [ ] Tests added or updated
- [ ] Documentation updated
- [ ] CI passing
- [ ] No debug code remaining
- [ ] Ready for review
```

---

# Pull Request Size

Preferred PR characteristics:

- Focused
- Reviewable
- Single responsibility

Recommended size:

- One backlog issue
- One feature branch
- One coherent change

Large PRs should be divided.

---

# Draft Pull Requests

Draft PRs are encouraged when:

- Work is incomplete.
- Feedback is required.
- Design decisions are being discussed.

Draft PRs are not eligible for merge.

---

# Review Requirements

A PR cannot be merged until:

- Required CI passes.
- Required reviews are approved.
- Branch protection rules are satisfied.
- Merge conflicts are resolved.

---

# Merge Strategy

Approved merge strategy:

```text
Squash and Merge
```

Benefits include:

- Clean Git history.
- One commit per backlog issue.
- Easier release generation.
- Simpler reverts.

Alternative strategies require explicit approval.

---

# Branch Deletion

After merge:

```text
Feature Branch

↓

Deleted
```

Short-lived branches reduce repository clutter.

---

# AI-Assisted Development

AI may:

- Generate code.
- Draft PR descriptions.
- Suggest tests.
- Recommend improvements.

Human reviewers remain responsible for approving all changes.

AI authorship does not reduce review requirements.

---

# Automation

The Backlog CLI generates:

- PR title
- PR description
- Acceptance criteria
- Related issue links
- Review checklist

Developers should use generated templates whenever possible.

Example:

```bash
pnpm backlog:pr APP-001
```

---

# CI Integration

Every PR triggers:

- Type checking
- Linting
- Unit tests
- Integration tests
- Backlog validation
- Build verification

Failed required checks block merging.

---

# Documentation

Documentation must be updated whenever changes affect:

- Architecture
- Public APIs
- User workflows
- Engineering processes
- Backlog definitions

Documentation updates should be included in the same PR whenever practical.

---

# Security

Security-sensitive PRs should include:

- Threat considerations
- Dependency changes
- Secret handling
- Permission changes

Reviewers should pay additional attention to these changes.

---

# Release Notes

Release tooling derives summaries from:

- PR title
- Linked issue
- Backlog metadata
- Milestone

Consistent PR structure improves release automation.

---

# Testing Strategy

The PR itself should demonstrate that testing has been performed.

Verification includes:

## Unit Tests

Business logic.

---

## Integration Tests

Component interactions.

---

## End-to-End Tests

Critical user workflows.

---

## Manual Verification

Where automation is impractical.

---

# Alternatives Considered

## Direct Push to Main

Rejected because:

- No review.
- No audit trail.
- Weak quality control.
- Increased deployment risk.

---

## Optional Pull Requests

Rejected because:

- Inconsistent workflow.
- Reduced automation.
- Poor traceability.

---

## Free-Form PRs

Rejected because:

- Inconsistent documentation.
- Difficult reviews.
- Weak release generation.

---

# Consequences

## Positive

- Consistent reviews.
- Better documentation.
- Reliable automation.
- Cleaner Git history.
- Easier releases.
- Strong AI workflow.

---

## Negative

- Slightly more structured process.
- Additional review discipline required.
- Template maintenance.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every change to `main` occurs through a Pull Request.
- Every PR references a primary CBS issue.
- PR titles follow the approved format.
- Acceptance criteria originate from the backlog.
- Required CI checks must pass.
- Required reviews must be approved.
- Squash merge is the default merge strategy.
- Feature branches are deleted after merge.
- Generated PR templates should be used whenever possible.

Changes to the pull request workflow require a new ADR.

# Decision Summary

CareerOS adopts a standardized **Pull Request Convention** in which every change is delivered through a structured pull request linked to a single CBS backlog issue. Pull requests are generated from repository-defined backlog metadata, include standardized descriptions and acceptance criteria, require successful CI and code review, and are merged using a squash strategy. This convention ensures consistent reviews, high code quality, reliable automation, and complete traceability from planning through implementation and release.
