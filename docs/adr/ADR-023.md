# ADR-023: Branch Naming Convention

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS follows a repository-first engineering workflow with:

- CBS-backed backlog planning
- GitHub Issues generated from YAML
- AI-assisted development
- Pull request automation
- Continuous integration
- Short-lived feature branches

As the project grows, inconsistent branch names make it difficult to:

- Understand the purpose of a branch.
- Associate work with GitHub Issues.
- Generate release notes.
- Automate pull requests.
- Review changes.
- Navigate Git history.

A deterministic branch naming strategy is therefore required.

---

# Decision

CareerOS adopts a **structured, deterministic branch naming convention**.

Every implementation branch is derived from the corresponding backlog issue.

Branches are temporary and exist only for the duration of the work.

---

# Goals

The naming convention should:

- Be predictable.
- Be human-readable.
- Be machine-readable.
- Support automation.
- Link naturally to backlog issues.
- Improve Git history.
- Simplify AI workflows.

---

# Branch Lifecycle

Development follows the workflow:

```text
Backlog Issue

↓

Feature Branch

↓

Pull Request

↓

Merge

↓

Branch Deleted
```

Branches are disposable implementation artifacts.

---

# General Format

Every branch follows the format:

```text
<type>/<issue-id>-<short-description>
```

Example:

```text
feature/app-001-create-application-api
```

---

# Components

The naming convention consists of three parts.

## Type

Represents the category of work.

## Issue Identifier

The canonical CBS issue ID.

## Description

A short kebab-case summary.

---

# Branch Types

Approved branch types include:

```text
feature

bugfix

hotfix

chore

refactor

docs

test

ci

release
```

No additional prefixes should be introduced without architectural review.

---

# Feature Branches

Examples:

```text
feature/app-001-create-application-api
```

```text
feature/job-012-search-filtering
```

```text
feature/auth-004-google-sign-in
```

Feature branches implement planned functionality.

---

# Bug Fixes

Examples:

```text
bugfix/app-021-status-update-error
```

```text
bugfix/ext-013-linkedin-parser
```

Bugfix branches correct defects.

---

# Hotfixes

Examples:

```text
hotfix/api-004-auth-token-expiry
```

Hotfixes target urgent production issues.

---

# Refactoring

Examples:

```text
refactor/core-014-domain-services
```

Refactoring improves implementation without changing observable behavior.

---

# Documentation

Examples:

```text
docs/adr-018-analytics-model
```

```text
docs/readme-update
```

Documentation branches modify documentation only.

---

# Testing

Examples:

```text
test/app-004-integration-tests
```

Testing branches add or improve automated tests.

---

# CI/CD

Examples:

```text
ci/github-actions-cache
```

```text
ci/docker-build
```

CI branches modify automation infrastructure.

---

# Release Branches

Examples:

```text
release/v1.0.0
```

```text
release/v1.1.0-beta
```

Release branches prepare official releases when required.

---

# Description Rules

Descriptions:

- use lowercase,
- use kebab-case,
- remain concise,
- describe intent,
- avoid unnecessary words.

Example:

Good:

```text
feature/app-001-create-application-api
```

Avoid:

```text
feature/new-feature
```

---

# Character Rules

Allowed:

- lowercase letters
- numbers
- hyphens
- forward slash

Not allowed:

- spaces
- underscores
- uppercase letters
- punctuation

---

# Branch Length

Branch names should remain concise.

Recommended maximum:

```text
80 characters
```

Long descriptions should be shortened without losing meaning.

---

# Branch Generation

Developers should not manually invent branch names.

The Backlog CLI generates them.

Example:

```bash
pnpm backlog:start APP-001
```

Output:

```text
feature/app-001-create-application-api
```

The CLI may also create the branch automatically.

---

# Issue Association

Every implementation branch references exactly one primary backlog issue.

Example:

```text
APP-001

↓

feature/app-001-create-application-api
```

Large features are split into multiple issues rather than sharing one branch.

---

# Pull Request Association

Each pull request originates from a single feature branch.

Example:

```text
Branch

↓

Pull Request

↓

Merge
```

PR titles reference the same issue identifier.

---

# Short-Lived Branches

Branches are intentionally short-lived.

Recommended lifecycle:

- Create branch.
- Implement feature.
- Open PR.
- Review.
- Merge.
- Delete branch.

Long-running branches are discouraged.

---

# Main Branches

Permanent branches include:

```text
main
```

Additional long-lived branches should be introduced only when justified by the release strategy.

---

# Merge Strategy

Feature branches merge into:

```text
main
```

using the repository's approved merge strategy.

The merged feature branch is deleted immediately after a successful merge.

---

# AI Integration

AI assistants use branch names to infer:

- Active issue.
- Scope of work.
- Related backlog item.
- Pull request metadata.

Deterministic names improve automation.

---

# Automation

Branch names are used by:

- Backlog CLI
- Pull Request generator
- GitHub Actions
- Release tooling
- Documentation generator

Automation depends on predictable naming.

---

# Validation

The Backlog CLI validates generated branch names.

Validation ensures:

- valid issue identifier,
- supported branch type,
- kebab-case description,
- allowed characters.

Invalid names are rejected.

# Alternatives Considered

## Random Branch Names

Rejected because:

- Poor traceability.
- Weak automation.
- Difficult reviews.

---

## Developer-Defined Names

Rejected because:

- Inconsistent.
- Difficult validation.
- Reduced automation.

---

## GitHub Issue Number Only

Example:

```text
feature/123
```

Rejected because:

- Loses semantic meaning.
- Difficult navigation.
- Weak AI context.

---

# Consequences

## Positive

- Consistent Git history.
- Easy issue traceability.
- Reliable automation.
- Better AI context.
- Predictable pull requests.
- Simplified reviews.

---

## Negative

- Slightly longer branch names.
- Requires developers to use generated names.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every implementation branch references one CBS issue.
- Branch names follow the approved format.
- Branches are generated by the Backlog CLI whenever possible.
- Branches are short-lived.
- Feature branches are deleted after merge.
- Unsupported prefixes are prohibited.
- Permanent branches require architectural approval.

Changes to the branch naming convention require a new ADR.

# Decision Summary

CareerOS adopts a **deterministic branch naming convention** based on CBS issue identifiers. Every implementation branch follows the format `<type>/<issue-id>-<short-description>`, is generated by the Backlog CLI where possible, remains short-lived, and maps directly to a single backlog issue. This convention improves traceability, automation, AI-assisted development, code reviews, and repository consistency while supporting a clean Git history.
