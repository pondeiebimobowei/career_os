# ADR-038 — Logging & Observability Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a distributed platform consisting of multiple independently deployed applications.

Current architecture includes:

- Backend API
- Web Application
- Browser Extension
- Shared Packages
- Backlog CLI
- GitHub Actions
- PostgreSQL
- Coolify
- Cloudflare

As the platform grows, failures become increasingly difficult to diagnose without a comprehensive observability strategy.

Examples include:

- Failed browser imports
- Synchronization failures
- Database errors
- Slow API requests
- Authentication failures
- Parser regressions
- Deployment failures
- Infrastructure outages

Without standardized logging and observability:

- incidents take longer to diagnose
- production debugging becomes difficult
- regressions remain undetected
- performance issues go unnoticed
- user-impacting problems are discovered too late

CareerOS therefore requires a unified observability strategy across every application.

---

# Decision

CareerOS will implement a structured logging and observability architecture built around five pillars:

1. Structured Logging
2. Metrics
3. Distributed Tracing
4. Health Monitoring
5. Alerting

Every application must emit observable events using the same standards.

---

# Observability Architecture

```text
Applications

↓

Structured Logs

↓

Metrics

↓

Traces

↓

Monitoring Platform

↓

Dashboards

↓

Alerts

↓

Engineering Team
```

Observability is treated as part of the platform rather than an optional feature.

---

# Observability Goals

The platform should allow engineers to answer:

- What failed?
- Why did it fail?
- When did it fail?
- Which user was affected?
- Which request caused it?
- Which deployment introduced it?
- How severe is the issue?
- Has it happened before?

Answers should be available without reproducing the issue whenever possible.

---

# Pillar 1 — Structured Logging

All logs must be structured.

Avoid free-form log messages whenever practical.

Preferred format:

```json
{
  "timestamp": "2026-08-06T10:15:00Z",
  "level": "INFO",
  "service": "api",
  "module": "applications",
  "requestId": "req_123",
  "userId": "usr_456",
  "message": "Application imported successfully"
}
```

Logs should be machine-readable.

---

# Log Levels

Use consistent log levels.

## TRACE

Very detailed diagnostics.

Used only during development.

---

## DEBUG

Useful engineering diagnostics.

Disabled in production by default.

---

## INFO

Normal application events.

Examples:

- user login
- application import
- synchronization complete
- deployment started

---

## WARN

Unexpected but recoverable conditions.

Examples:

- retry initiated
- deprecated API
- duplicate import detected

---

## ERROR

Failures requiring attention.

Examples:

- database failure
- parser exception
- failed synchronization

Errors should include stack traces where appropriate.

---

## FATAL

Application cannot continue.

Examples:

- missing configuration
- startup failure
- database unavailable during boot

Fatal events should terminate the process.

---

# Required Log Fields

Every log entry should include:

```text
timestamp

level

service

environment

version

message
```

Where available, also include:

```text
requestId

userId

sessionId

organizationId

correlationId

module

duration

statusCode
```

---

# Correlation IDs

Every request receives a unique correlation identifier.

Example:

```text
req_01JABCDE123XYZ
```

The same identifier flows through:

- API
- Services
- Database operations
- External APIs
- Logs

This enables end-to-end request tracing.

---

# Request Logging

Every API request should log:

- method
- path
- status
- duration
- request ID
- response size

Sensitive payloads must not be logged.

---

# Browser Extension Logging

Extension logs include:

- parser selected
- detected platform
- import duration
- synchronization status
- storage operations
- authentication state

Extension logs should aid debugging without exposing user data.

---

# Parser Logging

Each parser should log:

- parser version
- platform
- page type
- extraction duration
- normalization duration
- validation failures

DOM contents must never be logged in production.

---

# Database Logging

Capture:

- query duration
- transaction failures
- migration events
- connection failures

Do not log SQL containing sensitive values.

---

# Authentication Logging

Record:

- login
- logout
- token refresh
- authorization failure
- invalid credentials

Passwords and tokens must never appear in logs.

---

# Background Jobs

Background processes should log:

- start
- completion
- retries
- failures
- execution duration

Jobs should include correlation identifiers where applicable.

---

# Metrics

Track operational metrics including:

## API

- requests per second
- latency
- error rate
- throughput

---

## Database

- active connections
- query duration
- slow queries
- transaction failures

---

## Browser Extension

- imports
- parser success rate
- parser failures
- synchronization latency
- offline queue size

---

## User Activity

- active users
- application imports
- resume uploads
- synchronization frequency

---

## Infrastructure

- CPU
- memory
- storage
- network
- uptime

---

# Distributed Tracing

Support request tracing across:

```text
Browser Extension

↓

Backend API

↓

Repositories

↓

Database

↓

External Services
```

Each span should include:

- duration
- status
- parent span
- correlation ID

---

# Health Endpoints

Expose:

```text
/health

/health/live

/health/ready

/version
```

Health endpoints should avoid expensive operations.

---

# Readiness Checks

Readiness verifies:

- database connectivity
- configuration
- storage provider
- required services

Applications should reject traffic until ready.

---

# Liveness Checks

Liveness verifies:

- process responsiveness
- runtime health

Liveness checks should remain lightweight.

---

# Error Reporting

Unexpected exceptions should include:

- stack trace
- request ID
- service
- version
- deployment identifier

Sensitive information must be removed before reporting.

---

# Alerting

Generate alerts for:

- high error rate
- API downtime
- database unavailable
- failed deployments
- failed backups
- excessive response times
- synchronization failures
- parser failure spikes

Alerts should prioritize actionable incidents.

---

# Dashboards

Maintain dashboards for:

## Backend

- request volume
- latency
- errors
- authentication
- database

---

## Browser Extension

- parser success rate
- imports
- synchronization
- platform distribution

---

## Product

- active users
- applications imported
- resumes uploaded
- analytics generation

---

# Performance Budgets

Target thresholds:

| Metric | Target |
|---------|---------|
| API P95 latency | < 300 ms |
| API error rate | < 1% |
| Parser execution | < 500 ms |
| Synchronization | < 2 seconds |
| Health endpoint | < 50 ms |
| Cold API startup | < 5 seconds |

Performance budgets should be reviewed regularly.

---

# Privacy

Logs must never include:

- passwords
- JWTs
- API keys
- OAuth secrets
- payment information
- personal documents
- uploaded resume contents

Sensitive values should be automatically redacted.

---

# Retention

Recommended retention:

| Environment | Retention |
|--------------|-----------|
| Development | 7 days |
| Staging | 30 days |
| Production | 90 days (minimum) |

Retention policies should comply with organizational and legal requirements.

---

# Testing

Observability should be verified through automated tests.

Examples:

- request IDs propagated
- structured log format
- health endpoints
- metrics emission
- alert triggers
- trace propagation

Observability should be treated as a production feature.

---

# AI Assistant Rules

AI-assisted development must:

- preserve structured logging
- maintain correlation IDs
- avoid introducing `console.log()` into production code
- never log secrets
- avoid removing telemetry without justification

Changes affecting observability require code review.

---

# Consequences

## Positive

- Faster incident diagnosis
- Better production visibility
- Consistent debugging workflow
- Improved performance monitoring
- Easier capacity planning
- Reliable operational metrics

## Negative

- Additional implementation effort
- Increased storage requirements for logs
- Ongoing dashboard and alert maintenance
- Potential performance overhead if logging is excessive

---

# Compliance

All CareerOS applications, services, browser extensions, shared packages, automation tools, and deployment pipelines must implement this logging and observability strategy.

Any deviation requires an approved Architecture Decision Record (ADR).
