# ADR-022: GitHub Projects as the Execution Layer

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS uses a repository-first planning model.

Planning artifacts—including epics, features, issues, milestones, dependencies, and acceptance criteria—are defined in version-controlled YAML files.

GitHub Projects provides an excellent interface for:

- Sprint planning
- Work visualization
- Kanban boards
- Progress tracking
- Status reporting
- Team collaboration

However, GitHub Projects is **not** designed to be the authoritative planning system.

If planning data is maintained directly in GitHub Projects:

- Planning drifts from the repository.
- Manual updates become necessary.
- AI assistants lose deterministic context.
- Project configuration becomes difficult to reproduce.
- Project history becomes disconnected from architectural decisions.

CareerOS therefore requires a clear separation between planning and execution.

---

# Decision

CareerOS will use **GitHub Projects as the execution layer only**.

GitHub Projects visualize and manage execution of work that has already been defined in the repository.

The repository remains the authoritative source for planning.

---

# Goals

GitHub Projects should:

- Visualize work.
- Track execution.
- Coordinate development.
- Provide workflow transparency.
- Support automation.
- Never become the planning authority.

---

# Project Board Purpose

GitHub Projects answer questions such as:

- What is in progress?
- What is blocked?
- What is ready for review?
- What remains for the current milestone?
- What has been completed?

Projects do **not** answer:

- What should we build?
- What are the requirements?
- What are the acceptance criteria?

Those answers come from the backlog.

# AI Integration

AI assistants should consume backlog YAML for requirements.

GitHub Projects provide execution context such as:

- Current status
- Active work
- Assigned developer
- Review stage

AI should not infer requirements from project status.

---

# Progress Reporting

# Alternatives Considered

## GitHub Projects as Planning System

Advantages:

- Familiar interface.

Rejected because:

- Not version-controlled.
- Weak review workflow.
- Difficult automation.
- Planning drift.

---

## No Project Board

Rejected because:

- Reduced visibility.
- Poor execution tracking.
- Limited collaboration.

---

## Manual Project Management

Rejected because:

- Repetitive.
- Error-prone.
- Difficult to maintain.

---

# Consequences

## Positive

- Clear separation of planning and execution.
- Better developer visibility.
- Reliable automation.
- Consistent workflow.
- Improved reporting.
- Strong AI compatibility.

---

## Negative

- Requires synchronization tooling.
- Contributors must understand repository-first planning.
- Project configuration requires occasional maintenance.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- GitHub Projects are execution tools.
- Repository backlog remains authoritative.
- Project status reflects execution only.
- Planning changes originate from YAML.
- Synchronization updates project metadata.
- Developers manage workflow state within Projects.
- Project fields derived from CBS remain synchronized.

Architectural changes to execution workflow require a new ADR.

# Decision Summary

CareerOS adopts **GitHub Projects as the execution layer** for the engineering workflow. Product planning remains exclusively defined in the repository using CBS-compliant YAML backlog files, while GitHub Projects visualize, organize, and track the execution of generated GitHub Issues through the development lifecycle. This separation preserves a deterministic, version-controlled planning process while leveraging GitHub Projects for collaboration, progress tracking, and delivery management.
