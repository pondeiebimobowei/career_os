# ADR-019: YAML Backlog as the Single Source of Truth

- **Status:** Superseded
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** ADR-049, ADR-050

---

# Context

CareerOS is developed using an AI-assisted engineering workflow.

Unlike traditional teams where planning primarily occurs in project management tools, CareerOS requires planning artifacts that are:

- Human-readable
- Machine-readable
- Version-controlled
- Reviewable
- Automatable
- Deterministic

Typical project management tools (GitHub Issues, Linear, Jira, Trello, etc.) are excellent execution tools but poor planning systems.

They have several limitations:

- Difficult to review large structural changes.
- Poor support for code review.
- Limited branching and versioning.
- Difficult to automate consistently.
- Planning becomes disconnected from the codebase.

CareerOS requires a planning system that evolves alongside the source code.

---

# Decision

CareerOS adopts **YAML backlog files stored in the repository** as the **single source of truth** for product planning.

GitHub Issues, Projects, Milestones, Labels, Pull Requests, and Releases are generated or synchronized from these YAML files.

Planning originates in the repository—not in GitHub.

---

# Goals

The backlog system should:

- Be version-controlled.
- Be human-readable.
- Be machine-readable.
- Support AI tooling.
- Enable deterministic automation.
- Minimize manual project management.
- Keep planning close to the codebase.

---

# Source of Truth Hierarchy

Planning follows a strict hierarchy.

```text
CBS Schema

↓

Backlog YAML

↓

Backlog CLI

↓

GitHub

↓

Code
```

The repository is authoritative.

---

# Planning Layers

CareerOS planning is divided into four layers.

## Layer 1 — CBS Schema

Defines:

- Field names
- Allowed values
- Validation rules
- Relationships
- ID conventions

The schema governs all backlog files.

---

## Layer 2 — YAML Backlog

Backlog files describe:

- Epics
- Features
- Issues
- Acceptance criteria
- Dependencies
- Milestones
- Success metrics

These files represent the canonical project plan.

---

## Layer 3 — Backlog Tooling

The Backlog CLI:

- Validates
- Synchronizes
- Generates
- Reports

The CLI transforms planning into executable project artifacts.

---

## Layer 4 — GitHub

GitHub contains:

- Issues
- Milestones
- Labels
- Projects
- Pull Requests

GitHub is the execution layer—not the planning layer.

---

# Repository Structure

The planning system resides within the repository.

```text
docs/

backlog/

README.yaml

99-workspace.yaml

product/

engineering/

release/
```

Every backlog artifact is committed to version control.

---

# README.yaml

Purpose:

Repository catalog.

Defines:

- Domains
- File locations
- Project metadata

It does **not** contain issues.

---

# 99-workspace.yaml

Purpose:

Operational configuration.

Defines:

- Active milestone
- Enabled domains
- GitHub synchronization settings
- Automation configuration

It does **not** contain backlog items.

---

# Domain YAML Files

Each domain YAML file defines:

- Epic
- Objective
- Success metrics
- Features
- Issues
- Acceptance criteria
- Dependencies
- Future scope

Each file is self-contained.

---

# GitHub Synchronization

The Backlog CLI synchronizes:

- Labels
- Milestones
- Issues
- Projects

Synchronization is deterministic and idempotent.

Repeated synchronization produces identical results when no backlog changes exist.

---

# Planning Workflow

The expected workflow is:

```text
Edit YAML

↓

Validate

↓

Review

↓

Merge

↓

Sync

↓

Execute
```

Planning changes undergo the same review process as source code.

---

# Backlog Validation

Before synchronization:

```text
pnpm backlog:validate
```

Validation includes:

- Schema validation
- Duplicate IDs
- Missing dependencies
- Circular dependencies
- Invalid milestones
- Invalid priorities
- Invalid issue types

Invalid backlog files block synchronization.

---

# AI Integration

AI assistants consume backlog files directly.

Backlog files provide:

- Objectives
- Acceptance criteria
- Dependencies
- Success metrics
- Context

AI should never infer requirements from GitHub alone.

---

# GitHub as Projection

GitHub is treated as a projection of repository planning.

Examples:

```text
Backlog YAML

↓

GitHub Issue
```

```text
Backlog YAML

↓

GitHub Milestone
```

GitHub artifacts may be regenerated if necessary.

---

# Issue Lifecycle

Issue state is managed in GitHub.

Planning is managed in YAML.

Examples:

YAML defines:

- Title
- Description
- Acceptance criteria
- Labels
- Priority

GitHub manages:

- Open
- Closed
- Assigned
- Comments
- Review
- Linked Pull Requests

Responsibilities remain clearly separated.

---

# Pull Requests

Pull Requests reference GitHub Issues.

The Backlog CLI generates:

- Branch names
- PR titles
- PR descriptions
- Acceptance criteria checklists

PRs do not modify backlog definitions.

---

# Releases

Release notes are generated from:

- Completed GitHub Issues
- Associated backlog metadata

The backlog remains the planning authority.

---

# Version Control

Planning benefits from Git features including:

- Branching
- Code review
- History
- Reverts
- Diffs
- Tags

Backlog evolution is fully traceable.

---

# Automation

Automation includes:

```text
Validate

↓

Sync

↓

Status

↓

Generate

↓

Next

↓

Start

↓

PR

↓

Release
```

All automation derives from backlog YAML.

---

# Branching

Feature branches modify:

- Code
- Tests
- Documentation
- Backlog (when appropriate)

Planning evolves alongside implementation.

---

# Extensibility

New backlog domains require:

1. Create domain YAML.
2. Register in README.yaml.
3. Enable in workspace.
4. Validate.
5. Synchronize.

No GitHub reconfiguration is required.

---

# Offline Development

Because planning resides in the repository:

- Planning works offline.
- Reviews remain local.
- CI validation remains deterministic.

Developers are not dependent on GitHub availability.

# Alternatives Considered

## GitHub as Source of Truth

Advantages:

- Familiar workflow.

Rejected because:

- Weak versioning.
- Limited automation.
- Poor review experience.
- Difficult AI integration.

---

## Linear or Jira

Rejected because:

- External dependency.
- Separate planning system.
- Limited repository integration.

---

## Markdown TODO Files

Rejected because:

- Not structured.
- Difficult validation.
- Poor automation support.

---

# Consequences

## Positive

- Version-controlled planning.
- Deterministic automation.
- AI-friendly workflows.
- Better review process.
- Reproducible project state.
- Strong developer experience.

---

## Negative

- Requires maintenance of YAML files.
- Initial tooling investment.
- Contributors must learn the backlog schema.

These trade-offs are justified by the long-term benefits.

---

# Compliance

The following rules are mandatory.

- The repository is the planning authority.
- CBS governs every backlog file.
- GitHub is an execution layer.
- Planning changes require pull requests.
- Backlog validation passes before synchronization.
- Synchronization is idempotent.
- AI assistants consume backlog files as primary planning context.
- GitHub artifacts must not become the authoritative planning source.

Architectural changes to the planning system require a new ADR.

# Decision Summary

CareerOS adopts **repository-based YAML backlog files as the single source of truth for planning**. The CBS schema defines the planning model, domain YAML files describe the product and engineering backlog, and the Backlog CLI validates and synchronizes these definitions into GitHub Issues, Milestones, Labels, Projects, and release artifacts. GitHub is treated as the execution layer, while the repository remains the authoritative planning system.
