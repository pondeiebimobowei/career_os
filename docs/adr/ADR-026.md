# ADR-026: Trunk-Based Development with Short-Lived Branches

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is developed by a small engineering team augmented by AI assistants.

The engineering workflow emphasizes:

- rapid iteration,
- continuous integration,
- repository-first planning,
- automated testing,
- deterministic releases,
- AI-assisted implementation.

Traditional long-lived branching models (for example, Git Flow) introduce unnecessary complexity for this style of development.

Long-lived branches typically result in:

- large merge conflicts,
- stale code,
- delayed feedback,
- difficult reviews,
- unpredictable releases.

CareerOS requires a workflow that keeps the `main` branch continuously releasable while enabling developers to work independently.

---

# Decision

CareerOS adopts **Trunk-Based Development (TBD)** using **short-lived feature branches**.

The `main` branch is the trunk and is always considered the source of truth for the current releasable state of the application.

All implementation work is performed on temporary branches that are merged back into `main` as quickly as possible.

---

# Goals

The development model should:

- Keep `main` releasable.
- Minimize merge conflicts.
- Encourage small pull requests.
- Support continuous integration.
- Simplify AI-assisted development.
- Enable frequent deployments.
- Improve developer productivity.

---

# Development Model

The workflow is:

```text
Backlog Issue

↓

Feature Branch

↓

Implementation

↓

Pull Request

↓

Review

↓

Merge

↓

Delete Branch
```

`main` remains the integration branch.

---

# The Trunk

The trunk is:

```text
main
```

Characteristics:

- Protected
- Stable
- Continuously integrated
- Continuously tested
- Continuously deployable

Direct commits to `main` are prohibited.

---

# Feature Branches

Feature branches are temporary implementation branches.

Example:

```text
feature/app-001-create-application-api
```

Feature branches exist only until the corresponding pull request is merged.

---

# Branch Lifetime

Branches should remain short-lived.

Recommended duration:

- Less than one day whenever practical.
- Ideally merged within one to three days.
- Rarely longer than five working days.

Long-running branches increase merge risk and should be avoided.

---

# Branch Scope

Each feature branch should implement:

- one backlog issue,
- one logical change,
- one pull request.

Large backlog items should be decomposed before implementation.

---

# Integration Frequency

Developers should integrate with `main` frequently.

Typical workflow:

```text
Create Branch

↓

Implement

↓

Commit

↓

Pull Latest Main

↓

Resolve Conflicts

↓

Open PR

↓

Merge
```

Frequent integration minimizes drift.

---

# Continuous Integration

Every pull request must execute:

- Type checking
- Linting
- Unit tests
- Integration tests
- Build verification
- Backlog validation

A failing pipeline blocks merging.

---

# Pull Requests

All feature branches are merged through pull requests.

Requirements:

- CI passing
- Required approvals
- Branch protection satisfied
- Acceptance criteria completed

---

# Merge Strategy

CareerOS adopts:

```text
Squash and Merge
```

Benefits:

- Clean history
- One commit per backlog issue
- Easier rollback
- Simpler release notes

---

# Branch Deletion

After merge:

```text
Feature Branch

↓

Deleted
```

Merged branches should never remain in the repository unless explicitly required.

---

# Branch Protection

The `main` branch is protected.

Protection includes:

- No force pushes
- No direct commits
- Required reviews
- Required status checks
- Up-to-date branch requirement
- Linear history (where supported)

---

# Feature Flags

When work cannot be completed in a single iteration, incomplete functionality should be isolated behind feature flags rather than long-lived branches.

Example:

```text
Merged

↓

Feature Disabled

↓

Future Enablement
```

This allows frequent integration without exposing unfinished features.

---

# Hotfixes

Urgent production fixes follow the same workflow:

```text
main

↓

hotfix branch

↓

PR

↓

Review

↓

Merge

↓

Delete
```

Hotfixes remain short-lived.

---

# Releases

Because `main` is continuously releasable:

```text
main

↓

Release Tag

↓

Deployment
```

Dedicated release branches are generally unnecessary.

They may be introduced only for exceptional operational reasons.

---

# AI-Assisted Development

AI assistants benefit from:

- small scopes,
- deterministic branches,
- isolated context,
- predictable merges.

The Backlog CLI generates feature branches directly from CBS issue metadata.

Example:

```bash
pnpm backlog:start APP-001
```

---

# Conflict Resolution

Merge conflicts should be resolved:

- immediately,
- within the feature branch,
- before review begins.

Large integration merges are discouraged.

---

# Code Reviews

Small pull requests improve:

- review quality,
- review speed,
- defect detection,
- developer understanding.

Developers should prefer multiple focused PRs over one large PR.

---

# Testing Strategy

Testing occurs continuously.

## Local

- Unit tests
- Linting
- Type checking

---

## Pull Request

- CI
- Integration tests
- Build verification

---

## Main Branch

Every merged change contributes to a continuously healthy trunk.

---

# Deployment Strategy

Because `main` remains stable:

- deployments may occur frequently,
- releases remain predictable,
- rollback complexity is reduced.

Deployment cadence is independent of branching strategy.

---

# Alternatives Considered

## Git Flow

Advantages:

- Explicit release branches.

Rejected because:

- Long-lived branches.
- Delayed integration.
- Merge complexity.
- Slower feedback.

---

## GitHub Flow Without Rules

Rejected because:

- Inconsistent practices.
- Weak governance.
- Limited automation.

---

## Long-Lived Feature Branches

Rejected because:

- Merge conflicts.
- Stale implementations.
- Difficult reviews.
- Delayed testing.

---

# Consequences

## Positive

- Continuous integration.
- Smaller pull requests.
- Faster reviews.
- Reduced merge conflicts.
- Predictable releases.
- Better AI workflow.
- Simpler repository history.

---

## Negative

- Requires disciplined integration.
- Requires comprehensive CI.
- Large features must be decomposed.
- Feature flags may be needed.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- `main` is the only long-lived development branch.
- Direct commits to `main` are prohibited.
- Every implementation uses a short-lived branch.
- Every branch corresponds to a single primary CBS issue.
- Pull requests are required for all merges.
- CI must pass before merging.
- Squash merge is the default merge strategy.
- Feature branches are deleted immediately after merge.
- Long-lived feature branches are prohibited unless explicitly approved.
- Feature flags should be used instead of prolonged branching when incomplete functionality must be integrated.

Changes to the development workflow require a new ADR.

# Decision Summary

CareerOS adopts **Trunk-Based Development with short-lived feature branches**. The protected `main` branch serves as the continuously releasable trunk, while all implementation work occurs on temporary branches derived from CBS backlog issues. Changes are integrated frequently through small, reviewed pull requests with mandatory CI validation, merged using a squash strategy, and followed by immediate branch deletion. This workflow minimizes merge conflicts, accelerates feedback, supports AI-assisted development, and maintains a stable, deployable codebase.
