# ADR-049 — Documentation as Code

- **Status:** Superseded
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-019 (YAML Backlog as Source of Truth), ADR-027 (Engineering Playbook)
- **Superseded By:** ADR-050

---

# Context

CareerOS is being developed as a long-term platform rather than a short-term project.

The repository contains:

- Multiple applications
- Shared packages
- Browser Extension
- Backend API
- Infrastructure
- ADRs
- Engineering playbooks
- Product specifications
- Implementation plans
- YAML backlogs
- GitHub Issues
- CI/CD workflows

As the platform grows, documentation will become one of the largest assets in the repository.

Traditional documentation often suffers from:

- becoming outdated
- living outside the repository
- lacking version history
- lacking ownership
- not being reviewed
- becoming disconnected from implementation

To ensure documentation evolves with the software, CareerOS treats documentation as a first-class engineering artifact.

---

# Decision

CareerOS adopts a **Documentation as Code** philosophy.

Documentation is:

- version controlled
- reviewed
- tested where applicable
- updated alongside implementation
- stored within the repository
- treated as part of the production codebase

Documentation changes follow the same engineering process as source code.

---

# Guiding Principles

Documentation should be:

- Accurate
- Versioned
- Reviewable
- Searchable
- Discoverable
- Maintainable
- Close to implementation
- Easy to update

Documentation is considered incomplete if it does not reflect the current implementation.

---

```text

product/

engineering/

browser-extension/

backend/

frontend/

operations/

```

Each directory has a clearly defined purpose.

---

# Source of Truth

Every type of information has a single authoritative location.

Examples:

| Information | Source of Truth |
|-------------|-----------------|
| Architecture Decisions | ADRs |
| Product Requirements | Product Documentation |
| Implementation Plan | Implementation Documents |
| Engineering Practices | Engineering Playbook |
| API Contracts | OpenAPI / API Documentation |
| Backlog | YAML Backlog |
| Database Schema | Prisma Schema |
| UI Components | Component Documentation |

Duplicate documentation should be avoided.

---

# Version Control

All documentation lives inside Git.

Benefits include:

- history
- reviews
- diffs
- branching
- traceability

Documentation changes are committed alongside related code changes whenever possible.

---

# Documentation Reviews

Documentation is reviewed using the same Pull Request process as code.

Review should verify:

- accuracy
- completeness
- consistency
- formatting
- architectural alignment

Documentation is not exempt from peer review.

---

# Documentation Ownership

Every major documentation area has an owner.

Examples:

- Architecture
- Backend
- Browser Extension
- Infrastructure
- Product
- Security

Ownership ensures accountability for ongoing maintenance.

---

# Architecture Decision Records

All significant technical decisions require an ADR.

Examples include:

- architectural patterns
- frameworks
- infrastructure
- deployment
- security
- testing
- browser architecture

ADRs are immutable historical records.

---

# Product Documentation

Product documentation includes:

- vision
- goals
- personas
- workflows
- feature specifications
- roadmap

Product documentation explains **what** is being built.

---

# Technical Documentation

Technical documentation explains **how** the platform works.

Examples:

- API documentation
- synchronization
- parser architecture
- Browser Extension
- deployment
- monitoring

---

# Implementation Documentation

Implementation plans describe:

- phases
- milestones
- deliverables
- dependencies
- sequencing

Implementation documentation bridges planning and execution.

---

# Inline Documentation

Code should include inline documentation where appropriate.

Examples:

- exported interfaces
- public APIs
- complex algorithms
- architectural boundaries

Comments should explain *why*, not merely *what*.

---

# README Strategy

Every major directory should contain a README.

Examples:

```text
apps/

README.md

packages/

README.md

docs/

README.md

browser-extension/

README.md
```

READMEs should orient contributors and explain structure.

---

# API Documentation

API documentation should be generated from source where practical.

Documentation should remain synchronized with implementation.

Manual duplication should be minimized.

---

# Configuration Documentation

Configuration files should document:

- purpose
- expected values
- defaults
- examples

Undocumented configuration increases operational risk.

---

# Documentation Formatting

Preferred formats:

- Markdown
- Mermaid diagrams
- YAML
- OpenAPI
- PlantUML (where appropriate)

Proprietary formats should be avoided unless necessary.

---

# Diagrams

Architecture diagrams should be stored alongside documentation.

Diagrams should be text-based where practical.

Examples:

- Mermaid
- PlantUML

This improves version control and reviewability.

---

# Documentation Standards

Documentation should:

- use consistent terminology
- define acronyms
- avoid ambiguity
- include examples where helpful
- reference related documentation

Consistency improves maintainability.

---

# Documentation Lifecycle

Documentation follows the same lifecycle as code.

```text
Create

↓

Review

↓

Merge

↓

Maintain

↓

Deprecate

↓

Archive
```

Outdated documentation should be removed or archived.

---

# Documentation Debt

Missing or outdated documentation is considered technical debt.

Engineering tasks may include:

- documentation updates
- clarification
- restructuring
- removal of obsolete content

Documentation debt should be tracked like implementation debt.

---

# Automation

Automation should support documentation where practical.

Examples:

- API generation
- changelog generation
- architecture validation
- broken link detection
- Markdown linting

Automation improves consistency.

---

# CI/CD Integration

The CI pipeline should validate documentation quality.

Potential checks include:

- Markdown linting
- broken links
- formatting
- required ADR references
- documentation completeness

Documentation failures should be visible during review.

---

# Documentation and Releases

Every significant release should update:

- ADRs (if applicable)
- implementation plans
- changelog
- API documentation
- user documentation

Documentation is part of the release process.

# Security Documentation

# AI Assistant Rules

AI-assisted development must:

- update documentation when implementation changes
- preserve ADR references
- avoid undocumented architectural decisions
- maintain documentation structure
- generate examples when introducing new systems
- keep documentation synchronized with code

Implementation changes without documentation updates are considered incomplete.

# Consequences

## Positive

- Documentation evolves with the codebase
- Better onboarding for contributors
- Improved architectural consistency
- Complete historical decision records
- Easier maintenance and auditing
- Reduced knowledge loss

## Negative

- Additional documentation effort
- Longer review process
- Ongoing maintenance responsibility
- CI validation overhead

---

# Compliance

All CareerOS documentation must reside within the repository, follow the Documentation as Code philosophy, and be updated alongside related implementation changes.

Architectural decisions require ADRs, implementation changes require corresponding documentation updates, and documentation changes follow the same review process as source code.

Any deviation requires an approved Architecture Decision Record (ADR).
