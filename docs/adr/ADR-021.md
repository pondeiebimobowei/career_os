# ADR-021: GitHub Issues Generated from YAML Backlog

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS adopts a repository-first planning model where YAML backlog files are the authoritative definition of the product roadmap.

GitHub provides excellent capabilities for:

- Issue tracking
- Pull requests
- Code reviews
- Project boards
- Milestones
- Discussions
- Automation

However, GitHub Issues were not designed to be the primary planning system.

Managing issues manually introduces several problems:

- Duplicate planning effort
- Inconsistent issue descriptions
- Drift between documentation and execution
- Missing labels
- Missing milestones
- Inconsistent acceptance criteria
- Manual project maintenance

Because CareerOS already defines its backlog in structured YAML, GitHub Issues should be generated automatically rather than authored manually.

---

# Decision

CareerOS will treat **GitHub Issues as generated execution artifacts**.

The authoritative definition of every issue exists in the repository as YAML.

The Backlog CLI is responsible for projecting backlog definitions into GitHub.

Developers do not manually create implementation issues in GitHub.

---

# Goals

The synchronization process should:

- Eliminate duplicate planning.
- Ensure deterministic issue generation.
- Keep GitHub synchronized with the repository.
- Support idempotent execution.
- Minimize manual maintenance.
- Enable AI-assisted workflows.

# Synchronization

Synchronization is performed using:

```bash
pnpm backlog:sync
```

The synchronizer:

1. Loads workspace configuration.
2. Discovers enabled domains.
3. Validates backlog.
4. Reads GitHub state.
5. Creates missing artifacts.
6. Updates changed artifacts.
7. Reports results.

---

# Idempotency

Synchronization must be idempotent.

Repeated executions without backlog changes must produce no additional changes.

Example:

```text
Sync

↓

No Changes
```

Idempotency enables safe CI execution.

# Milestones

# Dependencies

Dependencies remain defined in YAML.

During synchronization, issue bodies may include references to dependent issues.

Example:

```text

APP-003
```

GitHub serves as a visualization layer rather than the authoritative dependency graph.

# Issue Updates

When backlog changes occur:

```text
YAML

↓

Synchronizer

↓

GitHub Update
```

Examples:

- Updated title
- New acceptance criteria
- Added labels
- Changed milestone

The synchronizer updates GitHub accordingly.

---

# Manual Changes

Developers should not manually modify generated issue content.

Manual edits to generated sections may be overwritten during synchronization.

GitHub comments remain unaffected.

---

# Protected Sections

Generated issue bodies may contain markers.

Example:

```markdown
<!-- Generated by Backlog CLI -->
```

Only generated sections are managed automatically.

---

# Pull Request Integration

Generated issues integrate naturally with pull requests.

Example:


The Backlog CLI can generate PR templates using issue metadata.

---

# AI Integration

AI assistants consume YAML rather than GitHub.

The Backlog CLI may expose commands such as:

```bash
pnpm backlog:next
```

to retrieve:

- Next issue
- Acceptance criteria
- Dependencies
- Related files

GitHub serves as execution metadata only.

---

# Offline Development

Planning continues without GitHub.

Developers may:

- edit backlog,
- validate,
- review,
- branch,

---

# Error Handling

Synchronization failures should:

- Preserve repository state.
- Report actionable errors.
- Retry safely.
- Never corrupt GitHub metadata.

---

# CI Integration

Continuous Integration should execute:

```bash
pnpm backlog:validate
```

before allowing synchronization.

Synchronization should only occur after successful validation.

# Alternatives Considered

## Manual GitHub Issues

Advantages:

- Familiar workflow.

Rejected because:

- Duplicate work.
- Drift.
- Inconsistent formatting.
- Difficult automation.

---

## GitHub as Planning System

Rejected because:

- Weak version control.
- Difficult reviews.
- Poor AI integration.

---

## One-Way Import

Rejected because:

- Prevents synchronization.
- Encourages divergence.

---

# Consequences

## Positive

- Repository-first planning.
- Consistent issue quality.
- Reduced manual work.
- Better automation.
- Reliable AI context.
- Deterministic execution.

---

## Negative

- Initial tooling complexity.
- Contributors must avoid editing generated content.
- Synchronizer requires maintenance.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- YAML backlog is the authoritative definition of issues.
- GitHub Issues are generated artifacts.
- Synchronization is idempotent.
- Backlog validation passes before synchronization.
- Generated sections are not manually edited.
- GitHub comments and execution state remain user-managed.
- Repository planning always takes precedence over GitHub metadata.

Architectural changes to issue synchronization require a new ADR.

# Decision Summary

CareerOS adopts **GitHub Issues as generated execution artifacts** derived from the repository-based YAML backlog. The Backlog CLI validates CBS-compliant backlog files and synchronizes them into GitHub Issues, Labels, Milestones, and related metadata. Planning is performed exclusively in the repository, while GitHub serves as the execution, collaboration, and tracking layer, ensuring a deterministic, version-controlled, and AI-friendly engineering workflow.
