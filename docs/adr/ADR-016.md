# ADR-016: Duplicate Detection Strategy

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS allows users to capture jobs from multiple recruitment platforms using the browser extension.

The same opportunity may be captured multiple times because:

- The user visits the same posting more than once.
- The job exists on multiple platforms.
- The user manually creates an application after capturing it.
- Browser synchronization is retried.
- Multiple browser sessions capture the same job.
- A job is reposted with minor content changes.

Without duplicate detection:

- Users accumulate redundant jobs.
- Applications become fragmented.
- Analytics become inaccurate.
- Notifications are duplicated.
- AI recommendations lose quality.
- Search results become cluttered.

Duplicate detection must therefore be a first-class capability of the platform.

---

# Decision

CareerOS will implement a **multi-layer duplicate detection strategy**.

Duplicate detection occurs at several stages:

1. Browser Extension
2. Synchronization Pipeline
3. Backend Services
4. Database Constraints

Each layer provides progressively stronger guarantees.

The backend remains the **authoritative source of truth**.

---

# Goals

The duplicate detection strategy should:

- Prevent accidental duplicates.
- Preserve legitimate user data.
- Avoid false positives.
- Be deterministic.
- Support future parser expansion.
- Minimize unnecessary API requests.
- Improve analytics quality.

---

# High-Level Architecture

```text
Browser Capture

↓

Local Duplicate Check

↓

Normalization

↓

API Request

↓

Backend Duplicate Detection

↓

Database Constraints

↓

Persist
```

Duplicate detection is not a single operation—it is a layered process.

---

# Duplicate Types

CareerOS recognizes several categories of duplicates.

## Exact Duplicate

Everything matches.

Examples:

- Same source URL
- Same external identifier
- Same user

These are always treated as duplicates.

---

## Equivalent Duplicate

Different representations of the same opportunity.

Examples:

```text
Google LLC

Google
```

```text
Full-time

Permanent
```

Normalization resolves these differences before comparison.

---

## Cross-Platform Duplicate

The same job appears on multiple recruitment platforms.

Example:

```text
LinkedIn

↓

Google

Software Engineer
```

```text
Greenhouse

↓

Google

Software Engineer
```

These require heuristic matching because platform identifiers differ.

---

## Synchronization Duplicate

A retry sends the same job multiple times.

Idempotent synchronization prevents duplicate records.

---

# Detection Layers

## Layer 1 — Browser Extension

The extension checks:

- Current synchronization queue.
- Recently captured jobs.
- Local cache.

If a likely duplicate exists, the user is informed before synchronization.

This layer improves UX but is not authoritative.

---

## Layer 2 — Normalized Model

Duplicate comparison uses normalized values rather than raw values.

Examples:

- Normalized URL
- Company
- Employment type
- Location

Normalization improves comparison accuracy.

---

## Layer 3 — Backend Detection

The backend performs authoritative duplicate checks.

The backend has access to:

- Existing jobs.
- Existing applications.
- Historical captures.

Only the backend can make the final decision.

---

## Layer 4 — Database Constraints

Critical uniqueness rules are enforced at the database level.

Examples include unique combinations of:

- User
- Source platform
- External identifier

Database constraints protect against race conditions.

---

# Matching Priority

Duplicate checks follow a deterministic priority order.

```text
External ID

↓

Normalized URL

↓

Platform + External ID

↓

Title + Company + Location

↓

Heuristic Matching
```

Higher-confidence matches are evaluated first.

---

# External Identifier

Preferred identifier:

```text
Platform

+

External Job ID
```

If available, this provides the highest-confidence match.

---

# URL Matching

Normalized URLs are compared after removing:

- Tracking parameters
- Marketing parameters
- Session identifiers

Example:

```text
https://jobs.example.com?id=123&utm_source=email

↓

https://jobs.example.com?id=123
```

---

# Company Matching

Company names are normalized.

Examples:

```text
Google LLC

↓

Google
```

```text
Microsoft Corporation

↓

Microsoft
```

---

# Title Matching

Job titles are normalized.

Examples:

```text
Frontend Engineer

↓

Frontend Engineer
```

Minor formatting differences are ignored.

---

# Location Matching

Locations are normalized before comparison.

Examples:

```text
Remote

↓

REMOTE
```

```text
Lagos, Nigeria

↓

Structured Location
```

---

# Heuristic Matching

If no exact match exists, heuristic matching may compare:

- Company
- Title
- Location
- Employment type

A confidence score determines whether records are likely duplicates.

Heuristics supplement exact matching but do not replace it.

---

# Synchronization Idempotency

Every synchronization request should be idempotent.

Repeated requests for the same job should not create multiple records.

The backend either:

- Creates a new record.
- Returns the existing record.

---

# User Feedback

When duplicates are detected:

Examples:

```text
Job already exists.
```

or

```text
Application already tracked.
```

Users should understand why no new record was created.

---

# Duplicate Resolution

The backend determines one of three outcomes.

## Create

No duplicate exists.

---

## Update

The record already exists and should be updated with newer metadata.

---

## Ignore

The record is already current.

---

# Applications vs Jobs

Jobs and applications are distinct entities.

Example:

```text
Job

↓

Application
```

Multiple applications should not exist for the same user and job unless explicitly supported in a future version.

---

# Browser Extension Behavior

If the extension detects a probable duplicate:

- Notify the user.
- Allow review where appropriate.
- Avoid unnecessary synchronization.

The backend still performs final validation.

---

# Analytics

Duplicate detection improves:

- Application counts.
- Capture success metrics.
- Conversion rates.
- Funnel reporting.

Analytics operate on deduplicated domain data.

---

# AI Integration

Future AI capabilities may identify:

- Similar opportunities.
- Reposted jobs.
- Related applications.
- Near duplicates.

AI suggestions remain advisory.

The backend continues to enforce deterministic rules.

# Telemetry

Operational metrics include:

- Duplicate detections.

These metrics support ongoing tuning.

# Database Model

Recommended uniqueness constraints include:

```text
User

+

Platform

+

External ID
```

Additional indexes may include:

- Normalized URL
- User
- Company

Exact schema evolves with the domain model.

---

# Error Handling

Duplicate detection failures should never:

- Create inconsistent records.
- Crash synchronization.
- Corrupt data.

If uncertainty exists, backend validation takes precedence.

# Alternatives Considered

## URL-Only Detection

Advantages:

- Simple implementation.

Rejected because:

- URLs change.
- Tracking parameters vary.
- Cross-platform duplicates remain undetected.

---

## Title-Only Matching

Rejected because:

- High false-positive rate.
- Common job titles.

---

## Client-Only Detection

Rejected because:

- Browser state is incomplete.
- Multiple devices.
- Race conditions.

---

## Backend-Only Detection

Rejected because:

- Poor user experience.
- Unnecessary network requests.

A layered strategy provides better results.

---

# Consequences

## Positive

- Cleaner user data.
- Reliable analytics.
- Better search.
- Reduced synchronization overhead.
- Improved AI readiness.
- Strong data integrity.

---

## Negative

- More comparison logic.
- Additional indexes.
- Ongoing heuristic refinement.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Duplicate detection is layered.
- The backend is the source of truth.
- Normalization precedes comparison.
- Database constraints enforce critical uniqueness.
- Synchronization is idempotent.
- Browser detection improves UX but is non-authoritative.
- Heuristic matching supplements deterministic matching.
- Duplicate outcomes are deterministic and auditable.

Changes to the duplicate detection strategy require a new ADR.

# Decision Summary

CareerOS adopts a **multi-layer Duplicate Detection Strategy** that combines browser-side checks, normalized domain comparisons, backend validation, and database constraints to prevent duplicate jobs and applications. The browser extension provides immediate user feedback, while the backend remains the authoritative source of truth, ensuring deterministic, idempotent, and reliable duplicate handling across all supported recruitment platforms.
