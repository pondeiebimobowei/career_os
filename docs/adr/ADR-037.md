# ADR-037 — Secret Management Strategy

- **Status:** Superseded
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** ADR-044

---

# Context

CareerOS consists of multiple applications deployed across multiple environments.

Current architecture includes:

- Web Application
- Backend API
- Browser Extension
- Backlog CLI
- CI/CD (GitHub Actions)
- Coolify
- PostgreSQL
- Cloudflare
- Browser Store deployment

Each component requires secrets such as:

- Database credentials
- API keys
- OAuth credentials
- JWT secrets
- Storage credentials
- Deployment tokens

Without a defined secret management strategy:

- credentials leak into Git
- environments drift
- deployments become unreliable
- secrets are rotated inconsistently
- onboarding becomes difficult
- incidents become more likely

Secret management must therefore be standardized across the entire platform.

---

# Decision

CareerOS will adopt a **centralized, environment-specific secret management strategy** based on the following principles:

1. Secrets never exist in source control.
2. Every environment owns its own secrets.
3. Applications receive secrets through environment variables.
4. Secrets are validated at startup.
5. Secret rotation must not require code changes.
6. Least-privilege access is enforced.
7. Secrets are never exposed to client applications unless intentionally public.

---

# Secret Classification

Secrets are divided into four categories.

## Level 1 — Public Configuration

Safe for client exposure.

Examples:

- Public API URLs
- Feature flags
- Public analytics IDs
- Browser Extension version
- Application name

Example:

```env
VITE_API_URL=https://api.careeros.app
```

These are not considered secrets.

---

## Level 2 — Application Secrets

Used by server applications.

Examples:

- JWT signing key
- Session secrets
- Encryption keys

Example

```env
JWT_SECRET=...
```

Only backend services may access these.

---

## Level 3 — Infrastructure Secrets

Used by infrastructure.

Examples:

- PostgreSQL password
- Redis password
- Object storage credentials
- SMTP credentials

Never exposed outside infrastructure.

---

## Level 4 — External Service Credentials

Credentials for third-party integrations.

Examples:

- GitHub token
- Cloudflare API token
- OAuth client secret
- AI API keys
- Monitoring services

Access should be scoped to only the services that require them.

---

# Environment Strategy

Every environment maintains independent secrets.

```text
Development

↓

Staging

↓

Production
```

Secrets are never copied between environments.

Each environment uses different:

- database passwords
- JWT secrets
- API keys
- OAuth credentials

---

# Storage Locations

## Local Development

Secrets stored in:

```text
.env.local
```

Ignored by Git.

Never committed.

---

## CI/CD

Secrets stored using GitHub repository or organization secrets.

Examples:

- Docker registry token
- Deployment credentials
- Coolify API token
- Cloudflare token

No secrets are hardcoded in workflows.

---

## Production

Secrets are injected by the deployment platform (Coolify).

Examples:

```text
DATABASE_URL

JWT_SECRET

SMTP_PASSWORD

OPENAI_API_KEY
```

Applications should never read secret files in production.

---

# Validation

All environment variables are validated during application startup using Zod.

Example:

```typescript
DATABASE_URL: z.string().url()

JWT_SECRET: z.string().min(32)

PORT: z.coerce.number()
```

Applications fail fast if validation fails.

---

# Repository Rules

The repository must never contain:

- passwords
- API keys
- private certificates
- OAuth secrets
- production URLs with embedded credentials

Git history should be treated as permanent.

If a secret is committed:

1. Rotate the secret immediately.
2. Remove it from Git history if practical.
3. Investigate exposure.
4. Update affected credentials.

---

# Browser Extension Rules

The Browser Extension must never contain:

- database credentials
- backend secrets
- private API keys
- JWT signing keys
- deployment tokens

Only public configuration may be bundled.

All sensitive operations occur through the backend API.

---

# Backend Rules

The backend owns all privileged credentials.

Examples:

- database
- storage
- AI providers
- email provider
- authentication providers

Clients never communicate directly with privileged services.

---

# Shared Packages

Shared packages must never embed secrets.

Instead, dependencies receive configuration through explicit injection.

Example:

```typescript
createStorageClient({
    endpoint,
    accessKey,
    secretKey
})
```

Avoid singleton modules that read environment variables at import time.

---

# Logging

Secrets must never appear in logs.

Examples to redact:

- Authorization headers
- Cookies
- Tokens
- Passwords
- API keys
- Database URLs containing credentials

Logging middleware should automatically sanitize sensitive values.

---

# Error Handling

Validation errors should never reveal secret values.

Incorrect:

```text
JWT_SECRET=abcd1234
```

Correct:

```text
JWT_SECRET is missing.
```

---

# Secret Rotation

Secrets should be replaceable without code changes.

Rotation process:

```text
Generate new secret

↓

Deploy updated environment

↓

Restart application

↓

Verify health

↓

Revoke old secret
```

No source code modifications should be required.

---

# Principle of Least Privilege

Each credential receives only the permissions it requires.

Examples:

Database user:

- read
- write

No administrative privileges.

Cloudflare token:

- DNS only

Not full account access.

GitHub token:

- repository automation

No organization administration.

---

# Naming Convention

Environment variables use uppercase snake case.

Examples:

```text
DATABASE_URL

JWT_SECRET

SESSION_SECRET

SMTP_HOST

SMTP_USERNAME

SMTP_PASSWORD

CLOUDFLARE_API_TOKEN

OPENAI_API_KEY

SENTRY_DSN
```

Names should clearly describe their purpose.

---

# Encryption

Sensitive data stored in the database should be encrypted where appropriate.

Examples:

- OAuth refresh tokens
- API tokens
- Third-party credentials

Passwords are never encrypted—they are hashed using a secure password hashing algorithm.

---

# Secrets in Tests

Tests should use dummy credentials.

Example:

```env
JWT_SECRET=test-secret

DATABASE_URL=postgres://test:test@localhost/test
```

Production credentials must never be used in automated tests.

---

# AI Assistant Rules

AI assistants must never:

- generate fake production credentials
- commit secrets
- expose secrets in pull requests
- print secrets in logs
- include secrets in documentation

If configuration is required, assistants should reference placeholder variables.

Example:

```env
OPENAI_API_KEY=<your-api-key>
```

Never include real values.

---

# Backup Policy

Secrets should not be included in application backups.

Infrastructure configuration should be backed up separately using secure administrative processes.

---

# Monitoring

Monitor for:

- missing environment variables
- expired credentials
- failed authentication
- unauthorized access attempts
- secret validation failures

Alerts should notify operators without exposing sensitive values.

---

# Consequences

## Positive

- Improved security posture
- Consistent deployments
- Easier onboarding
- Faster incident response
- Simplified secret rotation
- Environment isolation
- Reduced accidental credential exposure

## Negative

- Additional operational overhead
- Secret rotation procedures must be maintained
- Deployment environments require proper configuration
- Startup validation can prevent application boot when configuration is incomplete

---

# Compliance

All CareerOS applications, packages, deployment pipelines, automation scripts, and AI-assisted workflows must comply with this secret management strategy.

Any deviation requires an approved Architecture Decision Record (ADR).
