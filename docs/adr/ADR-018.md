# ADR-018: Analytics Model

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

One of CareerOS's core value propositions is helping users understand and improve their job search performance through actionable insights.

Users should be able to answer questions such as:

- How many jobs have I applied to?
- What is my interview rate?
- Which companies respond most often?
- Which resume performs best?
- How long does it take to receive interviews?
- Which application stage causes the highest drop-off?

Without a well-defined analytics model:

- Dashboard metrics become inconsistent.
- Different parts of the application compute different values.
- Reports lose credibility.
- AI recommendations become unreliable.
- Historical comparisons become inaccurate.

CareerOS requires a single analytics model that all components use consistently.

---

# Decision

CareerOS will adopt a **derived analytics model**.

Analytics are **calculated from domain events and canonical business data**, not maintained as manually updated counters.

The platform will use:

- Domain entities
- Activity history
- Pipeline events

as the authoritative sources for all metrics.

---

# Goals

The analytics model should:

- Produce deterministic metrics.
- Avoid duplicated business logic.
- Enable historical reporting.
- Support dashboards.
- Power AI recommendations.
- Scale with future features.
- Remain auditable.

---

# Principles

Analytics are:

- Derived
- Deterministic
- Reproducible
- Read-only
- Event-driven

Analytics never become the source of truth.

- Description

# Dashboard Model

Dashboard widgets consume analytics rather than raw domain data.

Example:

```text
Dashboard

↓

Analytics Service

↓

Applications
```

The dashboard never computes business metrics independently.

---

# Refresh Strategy

Analytics are calculated:

- On demand for MVP.
- Cached where beneficial.
- Materialized in future versions if required.

Premature optimization is avoided.

---

# Historical Reporting

Analytics preserve historical correctness.

Example:

```text
Applications

January

↓

Applications

February
```

Historical reports are reproducible because source events are immutable.

---

# Activity History Integration

Activity History provides:

- Daily activity
- Weekly activity
- User engagement

Activity events remain distinct from application metrics.

---

# Browser Extension Metrics

Metrics include:

- Jobs captured
- Successful captures
- Failed captures

# AI Integration

Future AI capabilities may analyze analytics to:

- Recommend application goals.
- Detect pipeline bottlenecks.
- Suggest resume improvements.
- Estimate interview probability.
- Recommend follow-up timing.

AI consumes analytics but does not generate authoritative metrics.

---

# Telemetry vs Analytics

Telemetry measures platform operation.

Examples:

- API latency
- Extension failures
- Parser errors

Analytics measure user outcomes.

Examples:

- Applications
- Interviews
- Offers

These concerns remain separate.

---

# API Design

Analytics endpoints expose aggregated data.

Example:

```json
{
  "applications": 84,
  "interviews": 11,
  "offers": 2,
  "interviewRate": 13.1
}
```

The API does not expose internal calculation details.

# Database Considerations

Analytics query:

- Applications
- Pipeline events
- Activity history
- Tasks
- Companies
- Resumes

Future optimization may introduce:

- Materialized views
- Aggregation tables

The canonical business tables remain authoritative.

Queries should:

- Use indexed fields.
- Minimize joins.
- Avoid duplicated calculations.

Caching is introduced only when required by measured performance.

# Alternatives Considered

## Stored Counters

Advantages:

- Fast queries.

Rejected because:

- Synchronization issues.
- Difficult corrections.
- Inconsistent state.

---

## Dashboard-Only Calculations

Rejected because:

- Duplicated logic.
- Multiple implementations.
- Inconsistent metrics.

---

## Client-Side Analytics

Rejected because:

- Performance issues.
- Security concerns.
- Inconsistent calculations.

---

# Consequences

## Positive

- Single source of truth.
- Deterministic metrics.
- Better reporting.
- Reliable AI foundation.
- Easier testing.
- Historical reproducibility.

---

## Negative

- Slightly more expensive queries.
- Additional aggregation layer.
- Requires disciplined metric definitions.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Analytics derive from canonical domain data.
- Pipeline events drive workflow metrics.
- Activity history drives engagement metrics.
- Dashboards consume analytics services only.
- Metrics have documented formulas.
- Analytics never become the source of truth.
- Metric definitions are version-controlled.

Changes to metric definitions require review and may require a new ADR if they alter business meaning.

# Decision Summary

CareerOS adopts a **derived Analytics Model** in which all metrics are calculated from canonical domain entities, immutable pipeline events, and activity history rather than stored counters. This approach provides deterministic, auditable, and historically accurate analytics that power dashboards, reporting, and future AI capabilities while ensuring a single, consistent definition for every business metric.
