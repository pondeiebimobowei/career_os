# ADR-041 — Browser Extension Architecture

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** ADR-008 (Browser Extension as First-Class Product), ADR-013 (Browser Extension)
- **Superseded By:** None

---

# Context

The Browser Extension is the primary data acquisition component of CareerOS.

Unlike traditional job application trackers that rely on manual data entry, CareerOS automatically captures job application information directly from supported recruitment platforms.

The extension is responsible for:

- Detecting supported recruitment platforms
- Extracting structured job application data
- Normalizing extracted data
- Validating application records
- Preventing duplicate imports
- Synchronizing with the CareerOS backend
- Providing immediate user feedback

It operates independently of the Web Application and Backend API while integrating closely with both.

As support expands to additional applicant tracking systems (ATS) and job boards, the extension architecture must remain modular, extensible, testable, and resilient to changes in third-party websites.

---

# Decision

The CareerOS Browser Extension will adopt a **layered, plugin-oriented architecture** composed of independent modules with clearly defined responsibilities.

The architecture is organized into the following layers:

1. Browser Runtime Layer
2. Platform Detection Layer
3. Parser Framework
4. Normalization Pipeline
5. Validation Layer
6. Synchronization Engine
7. User Interface Layer
8. Shared Domain Layer

Each layer communicates through explicit interfaces and shared domain contracts.

The architecture should provide:

- Platform independence
- Parser isolation
- High testability

# Layer 1 — Browser Runtime

The Browser Runtime manages interaction with browser APIs.

Responsibilities include:

- lifecycle events
- storage
- alarms
- tabs
- messaging
- permissions
- service worker execution

Business logic should not exist in this layer.

---

# Layer 2 — Platform Detection

Platform detection identifies the current website.

Supported examples include:

- LinkedIn
- Greenhouse
- Lever
- Workday

Each detector returns a normalized platform identifier.

Example:

```text
linkedin

greenhouse

lever

workday
```

Detectors must never parse application data.

---

# Layer 3 — Parser Framework

The parser framework delegates extraction to platform-specific parser implementations.

Responsibilities:

- parser registration
- parser discovery
- parser execution
- parser versioning

Each parser is isolated from every other parser.

---

# Parser Interface

Every parser implements the same contract.

Example:

```typescript
interface Parser {
    canParse(url: URL): boolean;

    parse(document: Document): ParsedApplication;
}
```

Uniform interfaces simplify testing and future expansion.

---

# Supported Parser Modules

Current modules:

```text
linkedin/

greenhouse/

lever/

workday/
```

Future parsers can be added without modifying existing implementations.

---

# Layer 4 — Normalization Pipeline

Parsers extract raw platform-specific data.

The normalization pipeline converts it into the CareerOS domain model.

Responsibilities:

- field mapping
- data cleaning
- canonical formatting
- default values
- metadata generation

Normalization is parser-independent.

---

# Canonical Domain Model

Every parser outputs the same domain model.

Example:

```text
JobApplication

Company

Location

EmploymentType

ApplicationStatus

SalaryRange
```

This enables downstream systems to remain platform-agnostic.

---

# Layer 5 — Validation

Before synchronization, imported records are validated.

Validation verifies:

- required fields
- supported values
- field formats
- schema integrity

Validation uses shared Zod schemas defined in shared packages.

---

# Layer 6 — Duplicate Detection

Before synchronization:

Imported records are compared against existing applications.

Matching strategies include:

- external application ID
- ATS application ID
- company
- position
- application date

Duplicate detection prevents redundant records.

---

# Layer 7 — Synchronization Engine

Synchronization communicates with the Backend API.

Responsibilities:

- authentication
- upload
- retries
- offline queue
- conflict handling
- synchronization state

Synchronization logic is isolated from parsing.

---

# Offline Queue

When offline:

```text
Import

↓

Queue

↓

Retry

↓

Synchronization

↓

Success
```

Users should never lose imported applications because of temporary network failures.

---

# Messaging Layer

Internal communication uses typed message contracts.

Examples:

```text
Content Script

↓

Background

↓

Popup

↓

Options
```

Direct coupling between components should be avoided.

---

# Storage Layer

Extension storage manages:

- authentication tokens
- cached imports
- synchronization queue
- settings
- feature flags

Persistent state should remain minimal.

---

# Popup Architecture

The popup provides:

- import status
- synchronization status
- recent imports
- authentication state
- quick actions

The popup should never perform parsing itself.

---

# Options Page

Configuration includes:

- account connection
- synchronization preferences
- supported platforms
- diagnostics
- developer mode

Settings should synchronize through shared configuration models.

---

# Shared Domain Layer

The Browser Extension shares domain models with the Backend and Web Application.

Shared packages include:

- contracts
- validation
- types
- utilities

This prevents duplication across applications.

---

# Error Handling

Failures should be categorized.

Examples:

- unsupported platform
- parser failure
- validation failure
- synchronization failure
- authentication failure

Errors should include actionable user feedback where appropriate.

---

# Performance

Target performance:

| Operation | Target |
|-----------|---------|
| Platform detection | < 50 ms |
| Parsing | < 500 ms |
| Normalization | < 100 ms |
| Validation | < 50 ms |
| Synchronization | < 2 s |
| Popup startup | < 300 ms |

Performance should remain predictable across supported platforms.

---

# Security

The extension must never contain:

- database credentials
- backend secrets
- JWT signing keys
- third-party API secrets

All privileged operations occur through the Backend API.

Permissions should follow the principle of least privilege.

---

# Testing Strategy

Testing includes:

## Unit Tests

- detectors
- parsers
- normalizers
- validators
- duplicate detection

---

## Fixture Tests

Every parser should be validated using stored HTML fixtures.

Fixture updates accompany parser changes.

---

## Integration Tests

Verify:

- synchronization
- authentication
- messaging
- storage

---

## End-to-End Tests

Validate complete import workflows using supported recruitment platforms.

---

# Extensibility

Adding a new platform should require:

1. New detector
2. New parser
3. Fixture tests
4. Registration

Existing parsers should remain unchanged.

This minimizes regression risk.

---

# AI Assistant Rules

AI-assisted development must:

- preserve parser isolation
- avoid parser-specific logic outside parser modules
- maintain shared domain models
- avoid direct DOM dependencies outside parsers
- update fixture tests when parser logic changes

Architectural consistency takes precedence over implementation convenience.

---

# Consequences

## Positive

- Clear separation of responsibilities
- Easy addition of new recruitment platforms
- High testability
- Reusable normalization pipeline
- Stable synchronization layer
- Consistent domain model across applications

## Negative

- Increased architectural complexity
- More modules to maintain
- Additional abstraction layers
- Slightly higher initial implementation effort

---

# Compliance

All Browser Extension features, parsers, synchronization components, storage modules, and future platform integrations must conform to this architecture.

Any deviation requires an approved Architecture Decision Record (ADR).
