# ADR-040 — Backup & Disaster Recovery Strategy

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS manages valuable user data that must not be lost.

Examples include:

- User accounts
- Job applications
- Resume metadata
- Resume files
- Activity history
- Analytics snapshots
- Settings
- Browser synchronization state
- Configuration

Although production infrastructure is designed for reliability, failures can still occur.

Examples:

- Database corruption
- Accidental deletion
- Infrastructure failure
- Deployment errors
- Cloud provider outages
- Storage failures
- Human error
- Security incidents

CareerOS therefore requires a comprehensive backup and disaster recovery strategy to minimize data loss and service downtime.

---

# Decision

CareerOS will implement an automated backup and disaster recovery strategy based on the following principles:

1. Automated backups
2. Verified recovery procedures
3. Multiple backup generations
4. Off-host storage
5. Regular recovery testing
6. Defined recovery objectives
7. Infrastructure reproducibility

Backups are only considered successful if they can be restored.

---

# Recovery Objectives

The platform defines the following targets.

| Objective | Target |
|-----------|--------|
| Recovery Point Objective (RPO) | ≤ 1 hour |
| Recovery Time Objective (RTO) | ≤ 4 hours |
| Backup Verification | Every backup cycle |
| Disaster Recovery Test | Quarterly |

These values may be revised as the platform scales.

---

# Backup Architecture

```text
Applications

↓

PostgreSQL

Resume Storage

Configuration

↓

Backup Jobs

↓

Encrypted Archives

↓

Off-Host Storage

↓

Recovery Procedures

↓

Production Restoration
```

Backups must never reside solely on the production server.

---

# Assets to Protect

## Database

Backup:

- users
- applications
- resumes
- metadata
- analytics
- activity history
- settings

Database backups are the highest priority.

---

## Resume Files

Backup:

- uploaded PDFs
- DOCX files
- generated assets

Metadata and files must remain synchronized.

---

## Configuration

Backup:

- deployment configuration
- infrastructure configuration
- Docker Compose files
- reverse proxy configuration

Infrastructure should be reproducible.

---

## Secrets

Application secrets are **not** included in standard backups.

Secrets are managed independently according to ADR-037.

---

## Source Code

Git repositories are **not** backed up as part of application backups.

GitHub remains the authoritative source.

---

# Backup Types

## Full Backup

Contains complete datasets.

Performed:

- weekly

---

## Incremental Backup

Contains changes since previous backup.

Performed:

- hourly

---

## Snapshot

Infrastructure snapshots may be used for rapid recovery.

Snapshots supplement—not replace—application backups.

---

# Database Strategy

Use logical PostgreSQL backups.

Backup includes:

- schema
- data
- indexes
- constraints
- migrations

Database version compatibility should be maintained.

---

# Resume Storage Strategy

Uploaded files should be backed up separately from the database.

Benefits:

- independent restoration
- reduced backup size
- storage flexibility

Checksums should verify integrity.

---

# Backup Schedule

Recommended schedule:

| Frequency | Backup Type |
|------------|-------------|
| Hourly | Incremental database |
| Daily | Full database |
| Daily | Resume storage |
| Weekly | Full infrastructure snapshot |
| Monthly | Long-term archive |

Schedules should be automated.

---

# Retention Policy

Recommended retention:

| Backup | Retention |
|---------|-----------|
| Hourly | 48 hours |
| Daily | 30 days |
| Weekly | 12 weeks |
| Monthly | 12 months |

Expired backups should be removed automatically.

---

# Encryption

All backups must be encrypted.

Encryption applies:

- in transit
- at rest

Backup archives should never be stored unencrypted.

---

# Storage Strategy

Backups should exist in at least two independent locations.

Example:

```text
Production Server

↓

Backup Server

↓

Cloud Object Storage
```

Single-location backups are not acceptable.

---

# Integrity Verification

Every backup should be verified.

Verification includes:

- archive readability
- checksum validation
- database consistency
- file integrity

Silent backup corruption must be detected early.

---

# Recovery Testing

Backups should be restored regularly in a non-production environment.

Verify:

- database restoration
- resume restoration
- configuration restoration
- application startup
- migration compatibility

Recovery testing is mandatory.

---

# Disaster Recovery Scenarios

The strategy must address:

## Database corruption

Restore latest verified backup.

---

## Accidental deletion

Restore affected records or latest backup.

---

## Server failure

Provision replacement infrastructure and restore backups.

---

## Storage corruption

Restore file backups.

---

## Deployment failure

Rollback deployment and restore if necessary.

---

## Regional outage

Restore into alternate infrastructure if required.

---

# Recovery Process

```text
Incident

↓

Assess Scope

↓

Select Backup

↓

Provision Infrastructure

↓

Restore Database

↓

Restore Files

↓

Verify Integrity

↓

Application Validation

↓

Resume Service
```

Recovery procedures should be documented and rehearsed.

---

# Monitoring

Monitor:

- backup completion
- backup duration
- backup size
- failed backups
- storage capacity
- recovery verification

Backup failures should generate alerts immediately.

---

# Logging

Log:

- backup start
- backup completion
- verification
- restoration
- failures

Logs should include timestamps and backup identifiers.

---

# Automation

Backups should require no manual intervention.

Automation includes:

- scheduling
- verification
- cleanup
- notifications

Manual backups remain available for exceptional circumstances.

---

# Version Compatibility

Backups should remain compatible with supported PostgreSQL versions.

Database upgrades should include backup validation before migration.

---

# Security

Access to backups should be restricted.

Only authorized operators may:

- create
- download
- restore
- delete

Backup storage should follow the principle of least privilege.

---

# Compliance

Recovery procedures should maintain:

- data integrity
- auditability
- traceability

Recovery events should be logged.

---

# Testing

The following should be tested regularly:

- backup creation
- backup verification
- restore speed
- restore accuracy
- disaster recovery documentation

Testing is considered part of production readiness.

---

# AI Assistant Rules

AI-assisted development must:

- preserve backup workflows
- avoid bypassing backup validation
- never expose backup credentials
- document infrastructure changes affecting recovery

Changes to backup architecture require architectural review.

---

# Incident Documentation

Every restoration event should document:

- incident
- recovery start
- recovery completion
- backup used
- data loss (if any)
- lessons learned

Documentation supports continuous improvement.

---

# Consequences

## Positive

- Reduced risk of permanent data loss
- Faster disaster recovery
- Improved operational confidence
- Better compliance with production practices
- Predictable recovery procedures
- Safer infrastructure changes

## Negative

- Additional storage costs
- Operational maintenance
- Periodic recovery testing effort
- Backup infrastructure management

---

# Compliance

All CareerOS production environments, databases, storage systems, and operational procedures must comply with this backup and disaster recovery strategy.

Backups are not considered valid unless they have been successfully verified through restoration testing.

Any deviation requires an approved Architecture Decision Record (ADR).
