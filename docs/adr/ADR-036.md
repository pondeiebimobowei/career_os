# ADR-036: Continuous Integration and Continuous Deployment (CI/CD)

- **Status:** Superseded
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** ADR-046, ADR-047

---

# Context

CareerOS follows a repository-first engineering workflow with:

- YAML-backed planning
- GitHub Issues
- GitHub Projects
- Trunk-Based Development
- AI-assisted engineering
- Automated testing
- Docker deployments

To keep the `main` branch continuously releasable, every code change must pass a consistent and automated validation pipeline before deployment.

Without CI/CD the project risks:

- broken builds,
- inconsistent releases,
- regressions,
- invalid backlog state,
- undocumented changes,
- deployment failures.

CareerOS therefore requires a standardized CI/CD pipeline.

---

# Decision

CareerOS adopts a fully automated **Continuous Integration and Continuous Deployment (CI/CD)** workflow.

Every pull request is validated automatically.

Every successful merge to `main` produces a deployable artifact.

Production deployments are automated through the deployment platform after all quality gates have passed.

---

# Goals

The CI/CD pipeline should:

- keep `main` deployable,
- detect regressions early,
- automate repetitive engineering work,
- provide rapid developer feedback,
- ensure deterministic builds,
- support safe deployments,
- integrate naturally with AI-assisted development.

---

# Pipeline Overview

```text
Developer

↓

Feature Branch

↓

Pull Request

↓

Continuous Integration

↓

Review

↓

Merge

↓

Continuous Deployment

↓

Production
```

Every stage is automated where practical.

---

# Continuous Integration

CI validates every pull request before merge.

The pipeline executes in a clean environment.

No cached local state should be required for a successful build.

---

# Continuous Deployment

CD begins only after:

- merge to `main`,
- successful CI,
- successful image build,
- successful health verification.

Only validated artifacts are deployed.

---

# Repository Events

CI executes on:

- pull requests,
- pushes to protected branches,
- release workflows,
- manually triggered workflows where appropriate.

CD executes from trusted branches only.

---

# CI Pipeline Stages

The standard pipeline is:

```text
Checkout Repository

↓

Install Dependencies

↓

Restore Cache

↓

Type Check

↓

Lint

↓

Unit Tests

↓

Integration Tests

↓

Backlog Validation

↓

Build

↓

Package Artifacts
```

Every stage must succeed before the next stage begins.

---

# Source Validation

The pipeline validates:

- repository integrity,
- dependency installation,
- lockfile consistency,
- workspace configuration.

Builds should fail early when repository state is invalid.

---

# Type Checking

Every TypeScript project executes:

```bash
pnpm check-types
```

Type errors block merging.

---

# Linting

Static analysis validates:

- formatting,
- coding standards,
- unused code,
- common defects.

Lint violations block merging.

---

# Unit Testing

All unit tests execute during CI.

Tests should remain:

- deterministic,
- isolated,
- repeatable.

---

# Integration Testing

Integration tests verify:

- repositories,
- APIs,
- parser pipeline,
- synchronization,
- shared packages.

Infrastructure dependencies should be provisioned automatically when required.

---

# Browser Extension Validation

Extension builds verify:

- compilation,
- parser tests,
- messaging,
- packaging.

Extension regressions block merging.

---

# Backlog Validation

The repository backlog is validated using:

```bash
pnpm backlog:validate
```

Validation includes:

- schema integrity,
- dependency graph,
- duplicate IDs,
- milestone consistency,
- feature relationships.

Planning integrity is enforced automatically.

---

# Documentation Validation

Documentation generation may include:

```bash
pnpm backlog:docs
```

Generated documentation should remain synchronized with repository planning artifacts.

---

# Build Verification

Production builds verify that applications compile successfully.

Examples:

- Backend
- Web
- Browser Extension
- CLI

Compilation failures block merging.

---

# Artifact Generation

Successful builds produce artifacts such as:

- Docker images,
- browser extension packages,
- release bundles,
- generated documentation.

Artifacts should be reproducible.

---

# Dependency Caching

Package manager caches should be restored where possible to improve pipeline performance.

Caching must never compromise deterministic builds.

---

# Security Checks

CI may include automated checks for:

- dependency vulnerabilities,
- secret detection,
- license compliance,
- container image scanning.

Security findings should be triaged according to severity.

---

# Branch Protection

Protected branches require:

- passing CI,
- required reviews,
- up-to-date branches,
- resolved conversations.

Branch protection enforces repository governance.

---

# Pull Request Checks

Every pull request should report:

- build status,
- test results,
- coverage (where applicable),
- backlog validation,
- deployment readiness.

Reviewers should not manually reproduce standard CI checks.

---

# Deployment Pipeline

Continuous deployment performs:

```text
Build Image

↓

Publish Image

↓

Deploy

↓

Health Check

↓

Traffic Switch
```

Deployment should fail automatically if health checks fail.

---

# Environment Promotion

Deployments follow environment progression:

```text
Development

↓

Staging

↓

Production
```

Promotion should occur only after successful validation.

---

# Rollback

Rollback procedures should support:

- previous Docker images,
- previous releases,
- infrastructure rollback,
- database migration recovery where applicable.

Rollback procedures should be documented and tested.

---

# Notifications

Pipeline results should be visible through:

- GitHub Checks,
- Pull Requests,
- deployment history.

Developers should receive timely feedback on failures.

---

# AI-Assisted Development

AI-generated code is subject to the same CI requirements as human-written code.

AI should:

- generate passing tests,
- preserve build stability,
- avoid introducing CI failures,
- update affected documentation where necessary.

Automation treats all contributions equally.

---

# Failure Handling

Pipeline failures should:

- stop execution,
- report actionable errors,
- preserve logs,
- avoid partial deployments.

Failures should be reproducible locally whenever practical.

---

# Monitoring

Deployment monitoring should verify:

- application health,
- deployment success,
- startup completion,
- runtime stability.

Successful deployment is confirmed only after health verification.

---

# Continuous Improvement

The CI/CD pipeline should evolve through:

- new automation,
- improved caching,
- faster execution,
- stronger validation,
- updated tooling.

Major workflow changes require a new ADR.

---

# Alternatives Considered

## Manual Deployment

Rejected because:

- inconsistent,
- error-prone,
- difficult to audit.

---

## Manual Testing Before Merge

Rejected because:

- slow,
- unreliable,
- difficult to scale.

---

## Partial Automation

Rejected because:

- inconsistent developer experience,
- increased operational risk.

---

# Consequences

## Positive

- Reliable releases.
- Faster feedback.
- Continuous validation.
- Better developer productivity.
- Higher deployment confidence.
- Improved AI-assisted workflows.

---

## Negative

- CI infrastructure maintenance.
- Pipeline execution time.
- Additional operational tooling.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every pull request passes CI before merging.
- `main` remains continuously deployable.
- Type checking, linting, testing, and backlog validation are mandatory.
- Production artifacts are generated through CI.
- Deployments occur only from trusted branches.
- Failed pipelines block deployment.
- AI-generated code follows identical CI requirements.
- Significant CI/CD workflow changes require a new ADR.

# Decision Summary

CareerOS adopts a fully automated **Continuous Integration and Continuous Deployment (CI/CD)** workflow in which every pull request undergoes comprehensive validation—including type checking, linting, automated testing, backlog validation, and build verification—before it can be merged. Successful merges to the protected `main` branch automatically produce deployable artifacts and trigger deployment through the standardized deployment platform. This pipeline ensures that the repository remains continuously releasable, minimizes operational risk, and provides fast, reliable feedback for both human and AI-assisted development.
