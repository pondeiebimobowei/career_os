# ADR-042 — Synchronization Engine Architecture

- **Status:** Accepted
- **Date:** 2026-08-06
- **Decision Makers:** CareerOS Engineering
- **Supersedes:** None
- **Superseded By:** None

---

# Context

The Synchronization Engine is responsible for reliably transferring data between the Browser Extension and the CareerOS Backend API.

It is one of the most critical components in the platform because every imported job application, resume association, activity event, and synchronization status update flows through it.

The synchronization process must tolerate:

- Temporary network failures
- Backend downtime
- Browser restarts
- Duplicate submissions
- Partial synchronization
- Authentication expiration
- API version changes

The Browser Extension must continue functioning even when synchronization cannot occur immediately.

Synchronization is therefore designed as a resilient, offline-first subsystem rather than a simple HTTP client.

---

# Decision

CareerOS will implement the Synchronization Engine as an **event-driven, queue-based, offline-first architecture**.

The engine consists of the following layers:

1. Event Producer
2. Synchronization Queue
3. Queue Persistence
4. Synchronization Processor
5. Retry Manager
6. Conflict Resolution
7. Status Tracking
8. Backend API Client

Synchronization is asynchronous and resilient by default.

---

# Architecture Overview

```text
Parser

↓

Normalized Application

↓

Validation

↓

Synchronization Event

↓

Persistent Queue

↓

Sync Processor

↓

Authentication

↓

Backend API

↓

Acknowledgement

↓

Queue Cleanup
```

Synchronization never blocks the user interface.

---

# Design Goals

The engine should provide:

- Reliable delivery
- Offline support
- Idempotency
- Automatic retries
- Ordered processing
- Conflict handling
- Observable state
- Extensibility

---

# Event-Driven Architecture

Every synchronization begins as an event.

Examples:

```text
ApplicationImported

ResumeUploaded

ApplicationUpdated

ApplicationDeleted

SettingsChanged
```

Events are immutable once created.

---

# Synchronization Queue

Events are written to a persistent queue before any network request occurs.

Benefits:

- offline capability
- crash recovery
- retry support
- predictable processing

The queue is the source of truth for pending synchronization work.

---

# Queue Storage

The queue is stored using browser-managed persistent storage.

Requirements:

- survives browser restart
- survives service worker restart
- supports ordered retrieval
- supports updates to processing state

Queue data must be durable until acknowledged by the backend.

---

# Queue Item Structure

Each queued item includes:

```text
Queue ID

Event Type

Payload

Created Timestamp

Retry Count

Status

Correlation ID

Version
```

The payload must conform to shared API contracts.

---

# Queue States

Each synchronization item progresses through defined states.

```text
Queued

↓

Validating

↓

Authenticating

↓

Sending

↓

Waiting

↓

Succeeded
```

or

```text
Queued

↓

Sending

↓

Failed

↓

Retry Scheduled

↓

Queued
```

Failed items remain in the queue until retry limits are reached or manual intervention is required.

---

# Processing Model

The Synchronization Processor consumes queue items sequentially by default.

Reasons:

- predictable ordering
- simplified conflict resolution
- easier debugging

Parallel processing may be introduced later for independent event types.

---

# Trigger Sources

Synchronization may begin when:

- an item is added to the queue
- browser startup
- service worker startup
- network connectivity returns
- user initiates manual sync
- scheduled background synchronization executes

The processor should avoid duplicate concurrent executions.

---

# Offline-First Behavior

If the backend is unreachable:

```text
Create Event

↓

Persist Queue

↓

Notify User

↓

Retry Later
```

The user should never lose imported data because of temporary connectivity issues.

---

# Authentication

Before sending queued events:

1. Verify authentication state.
2. Refresh tokens if required.
3. Retry authentication failures where appropriate.
4. Pause synchronization until authentication succeeds.

Synchronization must not proceed with invalid credentials.

---

# API Communication

The Backend API is the authoritative destination for synchronized data.

Requests should:

- use shared contracts
- include correlation IDs
- include application version
- include extension version

Every successful request returns an acknowledgement.

---

# Idempotency

Synchronization requests must be idempotent.

Each event includes a unique identifier.

Example:

```text
event_01JABCDE123XYZ
```

If the same event is received multiple times, the backend processes it only once.

This protects against duplicate submissions during retries.

---

# Retry Strategy

Failures are classified before retrying.

Retryable examples:

- network failure
- timeout
- HTTP 503
- HTTP 429

Non-retryable examples:

- invalid payload
- unauthorized after refresh
- validation failure

Only retryable failures re-enter the queue.

---

# Exponential Backoff

Retry delays increase progressively.

Example:

```text
Attempt 1

Immediate

↓

Attempt 2

30 seconds

↓

Attempt 3

2 minutes

↓

Attempt 4

10 minutes

↓

Attempt 5

30 minutes
```

Backoff reduces unnecessary load during outages.

---

# Retry Limits

Synchronization attempts are capped.

Example:

| Event Type | Maximum Retries |
|------------|-----------------|
| Application Import | 10 |
| Resume Upload | 8 |
| Analytics Event | 5 |
| Settings Sync | 5 |

After the limit is reached, the item enters a failed state for user review.

---

# Conflict Resolution

Conflicts occur when local and server state differ.

Examples:

- duplicate applications
- deleted records
- stale updates

The backend remains the source of truth.

Resolution strategies include:

- merge
- replace
- reject
- user intervention

Conflict policies are defined by individual API endpoints.

---

# Ordering Guarantees

Events are processed in creation order unless dependencies require otherwise.

Example:

```text
Resume Uploaded

↓

Application Imported

↓

Application Updated
```

Dependent events must preserve order.

---

# Status Tracking

Each queue item records:

```text
Queued

Processing

Succeeded

Failed

Retrying

Cancelled
```

Users can inspect synchronization progress through the extension UI.

---

# User Feedback

The Browser Extension should communicate synchronization state.

Examples:

- Syncing…
- Waiting for connection
- Retry scheduled
- Synchronization complete
- Manual action required

Messages should be informative without exposing implementation details.

---

# Queue Maintenance

Successful events are removed after acknowledgement.

Failed events exceeding retry limits may be retained temporarily for diagnostics before cleanup.

Queue cleanup should not remove unresolved work.

---

# Versioning

Every synchronization payload includes:

- API version
- schema version
- extension version

Version metadata enables backward compatibility and troubleshooting.

---

# Observability

The engine emits:

- structured logs
- metrics
- correlation IDs
- synchronization duration
- retry counts
- queue depth

Operational metrics support production monitoring.

---

# Error Handling

Errors are categorized as:

- authentication
- network
- validation
- conflict
- server
- unknown

Unexpected failures should be reported to the centralized error tracking system.

---

# Security

The Synchronization Engine must never:

- store secrets in queue payloads
- expose authentication tokens
- transmit unencrypted sensitive data
- bypass backend authorization

All communication uses HTTPS.

---

# Testing Strategy

The Synchronization Engine requires:

## Unit Tests

- queue operations
- retry logic
- backoff calculations
- state transitions

---

## Integration Tests

- API communication
- authentication
- queue persistence
- conflict handling

---

## End-to-End Tests

Validate complete synchronization workflows under:

- online conditions
- offline conditions
- authentication expiration
- browser restart
- backend failure
- duplicate submission

---

# Extensibility

Future synchronization features may include:

- batch synchronization
- background sync APIs
- multi-device synchronization
- selective synchronization
- encrypted local queue

The architecture should accommodate these without redesign.

---

# AI Assistant Rules

AI-assisted development must:

- preserve queue durability
- maintain idempotency
- avoid bypassing validation
- preserve retry semantics
- maintain correlation IDs
- update synchronization tests when behavior changes

Changes affecting synchronization reliability require architectural review.

---

# Consequences

## Positive

- Reliable data synchronization
- Offline-first user experience
- Automatic recovery from transient failures
- Reduced duplicate submissions
- Predictable synchronization behavior
- Clear operational visibility

## Negative

- Increased implementation complexity
- Persistent queue management overhead
- Additional storage requirements
- More comprehensive testing required

---

# Compliance

All Browser Extension synchronization features, backend synchronization endpoints, queue management components, and future synchronization workflows must comply with this architecture.

Any deviation requires an approved Architecture Decision Record (ADR).
