# ADR-033: Testing Strategy

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a long-lived software platform consisting of:

- Backend APIs
- Web applications
- Browser extensions
- Shared packages
- CLI tooling
- AI-assisted engineering workflows

The platform is expected to evolve continuously while maintaining a releasable `main` branch.

Without a consistent testing strategy, the project risks:

- regressions,
- unstable releases,
- difficult refactoring,
- architecture drift,
- reduced developer confidence,
- unreliable AI-generated code.

Testing must therefore be treated as an integral part of engineering rather than a final verification step.

---

# Decision

CareerOS adopts a **layered testing strategy** that emphasizes fast feedback, deterministic execution, and confidence through automated testing.

Testing is mandatory for production code and forms part of the definition of done for every backlog item.

---

# Goals

The testing strategy should:

- detect regressions early,
- support continuous integration,
- enable safe refactoring,
- validate business behavior,
- improve deployment confidence,
- provide rapid developer feedback,
- support AI-assisted development.

---

# Testing Philosophy

Testing follows the principle:

> Test behavior, not implementation.

Tests should verify observable outcomes rather than internal implementation details.

The test suite should provide confidence that the software behaves correctly under expected and unexpected conditions.

---

# Testing Pyramid

CareerOS adopts the testing pyramid.

```text
           E2E
      Integration
        Unit Tests
```

The majority of tests should be unit tests.

Integration tests should verify interactions.

End-to-end tests should validate critical user journeys.

---

# Test Levels

## Unit Tests

Unit tests validate isolated business logic.

Characteristics:

- fast,
- deterministic,
- independent,
- no external infrastructure.

Examples:

- domain services,
- utility functions,
- parsers,
- validators,
- business rules.

---

## Integration Tests

Integration tests validate collaboration between components.

Examples:

- API + database,
- repositories,
- service interactions,
- parser pipeline,
- browser storage,
- authentication flow.

Integration tests verify system boundaries.

---

## End-to-End Tests

End-to-end tests validate complete user workflows.

Examples:

- applying for a job,
- browser extension import,
- resume upload,
- dashboard analytics,
- synchronization flow.

E2E tests provide confidence that the complete system functions correctly.

---

# Layer Responsibilities

Each architectural layer has different testing priorities.

| Layer | Primary Tests |
|--------|---------------|
| Domain | Unit |
| Application | Unit + Integration |
| Infrastructure | Integration |
| Presentation | Integration + E2E |

---

# Business Logic

Critical business rules must always have automated tests.

Examples include:

- duplicate detection,
- parser normalization,
- application pipeline,
- analytics calculations,
- resume matching,
- synchronization logic.

Business logic should never rely solely on manual verification.

---

# API Testing

API endpoints should be tested for:

- successful requests,
- validation failures,
- authorization,
- authentication,
- error handling,
- edge cases.

HTTP contracts should remain stable.

---

# Browser Extension Testing

The browser extension should include tests for:

- content scripts,
- background scripts,
- parser execution,
- storage,
- message passing,
- synchronization.

Critical extension workflows should be covered by automated tests.

---

# Parser Testing

Every parser implementation should include:

- extraction tests,
- normalization tests,
- malformed input tests,
- missing field tests,
- duplicate detection tests.

Parser reliability is critical to CareerOS.

---

# Shared Packages

Shared packages require comprehensive unit tests because they are consumed by multiple applications.

Changes to shared packages should not introduce regressions across the repository.

---

# CLI Testing

The Backlog CLI should be tested for:

- YAML loading,
- validation,
- dependency resolution,
- command execution,
- GitHub synchronization,
- documentation generation.

CLI behavior should remain deterministic.

---

# Runtime Validation Tests

Zod schemas should be tested for:

- valid input,
- invalid input,
- optional fields,
- transformations,
- error reporting.

Validation is considered part of application behavior.

---

# Database Testing

Repository implementations should be tested using integration tests.

Tests should verify:

- persistence,
- retrieval,
- constraints,
- transactions,
- migrations.

Business rules remain outside repository tests.

---

# Mocking Strategy

Mock only external dependencies.

Examples:

- HTTP services,
- email providers,
- browser APIs,
- third-party APIs,
- external storage.

Avoid mocking business logic.

Over-mocking reduces test confidence.

---

# Test Data

Test data should be:

- deterministic,
- minimal,
- readable,
- reusable.

Fixtures should represent realistic scenarios without unnecessary complexity.

---

# Test Naming

Tests should describe behavior.

Preferred style:

```text
should create application successfully
```

or

```text
returns validation error for invalid resume
```

Avoid vague test names.

---

# Code Coverage

Coverage is a supporting metric rather than a goal.

High coverage does not guarantee correctness.

Priority is given to testing critical business behavior.

Coverage targets may be established but should never encourage meaningless tests.

---

# Continuous Integration

Every pull request executes:

- Type checking
- Linting
- Unit tests
- Integration tests
- Build verification
- Backlog validation

Failing tests block merging.

---

# AI-Assisted Development

AI-generated code must include appropriate automated tests.

AI should:

- generate unit tests,
- update existing tests,
- preserve test readability,
- avoid brittle assertions.

Generated tests are reviewed alongside implementation.

---

# Performance Testing

Performance tests may be introduced for:

- parser throughput,
- synchronization,
- analytics,
- large datasets.

Performance optimization should be based on measurement.

---

# Security Testing

Critical security workflows should include tests covering:

- authentication,
- authorization,
- input validation,
- permission enforcement.

Security testing complements code review rather than replacing it.

---

# Manual Testing

Manual testing remains valuable for:

- exploratory testing,
- UX evaluation,
- accessibility review,
- visual verification.

Manual testing does not replace automated testing.

---

# Test Maintenance

Tests are part of the production codebase.

When behavior changes:

- implementation,
- documentation,
- tests

should evolve together.

Broken tests should be fixed rather than removed without justification.

---

# Definition of Done

A backlog item is considered complete only when:

- implementation is finished,
- acceptance criteria pass,
- automated tests pass,
- CI succeeds,
- documentation is updated,
- review is approved.

Testing is part of completion—not an optional activity.

---

# Alternatives Considered

## Manual Testing Only

Rejected because:

- poor scalability,
- unreliable regression detection,
- slow feedback.

---

## End-to-End Heavy Testing

Rejected because:

- slow execution,
- difficult maintenance,
- limited debugging value.

---

## Unit Tests Only

Rejected because:

- integration failures remain undetected,
- infrastructure behavior is unverified.

---

# Consequences

## Positive

- Faster feedback.
- Safer refactoring.
- Improved release confidence.
- Better AI-generated code quality.
- Reduced regressions.
- Higher engineering confidence.

---

## Negative

- Additional maintenance effort.
- Increased CI execution time.
- Test infrastructure requires ongoing investment.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Production code includes appropriate automated tests.
- Business logic is covered by unit tests.
- Integration points are verified through integration tests.
- Critical user journeys are covered by end-to-end tests where appropriate.
- Pull requests must pass all required tests before merging.
- AI-generated code includes corresponding tests.
- Tests evolve alongside implementation.
- Failing tests are addressed before merge.

Changes to the testing strategy require a new ADR.

# Decision Summary

CareerOS adopts a **layered testing strategy** based on the testing pyramid, with a strong emphasis on unit tests, supported by integration tests and targeted end-to-end tests for critical workflows. Automated testing is a mandatory part of the development lifecycle, integrated into continuous integration and required for every production change. Tests focus on observable behavior, evolve alongside implementation, and provide the confidence necessary for safe refactoring, continuous delivery, and AI-assisted software development.
