# ADR-003: Layered Architecture

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a long-lived software platform that includes multiple applications, shared packages, browser extensions, APIs, and automation tooling.

As the system grows, business logic must remain independent of frameworks, databases, UI libraries, and infrastructure. Without clear architectural boundaries, concerns become tightly coupled, making the platform difficult to maintain, test, extend, and refactor.

The architecture must:

- Scale with increasing product complexity
- Encourage separation of concerns
- Support independent testing
- Minimize coupling
- Maximize cohesion
- Allow infrastructure to evolve without affecting business logic
- Enable AI-assisted development with predictable project structure

---

# Decision

CareerOS will adopt a **Layered Architecture** across all applications.

Each application will organize its code into clearly defined layers with strict dependency rules.

Dependencies must always flow **from outer layers toward inner layers**.

Inner layers must never depend on outer layers.

---

# Architectural Principles

The architecture follows these principles:

- Separation of concerns
- Dependency inversion
- Single responsibility
- High cohesion
- Low coupling
- Framework independence
- Testability
- Explicit boundaries

---

# Layer Overview

CareerOS applications use four primary layers.

```text
Presentation
      │
      ▼
Application
      │
      ▼
Domain
      │
      ▼
Infrastructure
```

The **Domain Layer** is the core of the system.

Everything else exists to support it.

---

# Layer Responsibilities

## Presentation Layer

The Presentation Layer handles user interaction.

Responsibilities include:

- UI components
- Pages
- Routing
- Forms
- User events
- Display logic
- Client-side navigation
- Input collection

The Presentation Layer must **not** contain business rules.

### Examples

- React Components
- Layouts
- Dialogs
- Browser Extension UI
- Navigation
- Form Components

---

## Application Layer

The Application Layer coordinates use cases.

Responsibilities include:

- Application services
- Commands
- Queries
- Workflow orchestration
- Authorization checks
- Transaction boundaries
- Calling repositories
- Calling external services

The Application Layer defines *how* business operations are executed.

It does **not** define business rules.

### Examples

- CreateApplicationService
- SyncJobService
- UpdateProfileService
- LoginUseCase

---

## Domain Layer

The Domain Layer contains the business model.

It is the most important layer.

Responsibilities include:

- Entities
- Value Objects
- Business Rules
- Domain Services
- Domain Events
- Repository Interfaces
- Invariants

The Domain Layer has **no knowledge** of:

- React
- NestJS
- Prisma
- PostgreSQL
- Browser APIs
- HTTP
- Docker

The Domain Layer should be pure TypeScript.

### Examples

- Application
- Company
- Job
- Task
- Resume
- PipelineStage
- Domain Validation
- Business Policies

---

## Infrastructure Layer

The Infrastructure Layer contains implementation details.

Responsibilities include:

- Database
- ORM
- HTTP
- File Storage
- Browser APIs
- Authentication Providers
- External APIs
- Logging
- Monitoring

Infrastructure implements interfaces defined by the Domain Layer.

### Examples

- Prisma repositories
- Passport JWT Guards & Auth Adapters
- REST controllers
- Browser storage
- API clients
- Docker configuration

---

# Dependency Direction

Dependencies must always flow inward.

```text
Presentation
      │
      ▼
Application
      │
      ▼
Domain
```

Infrastructure also depends on Domain.

```text
Infrastructure
      │
      ▼
Domain
```

The Domain Layer depends on nothing.

---

# Dependency Rules

## Allowed

```text
Presentation
        ▼
Application

Application
        ▼
Domain

Infrastructure
        ▼
Domain
```

---

## Not Allowed

```text
Domain
      ▼
Prisma

Domain
      ▼
React

Domain
      ▼
HTTP

Application
      ▼
React

Application
      ▼
Prisma Models
```

---

# Repository Pattern

Repositories are defined in the Domain Layer.

Example

```text
Domain

ApplicationRepository
```

Implemented in Infrastructure.

```text
Infrastructure

PrismaApplicationRepository
```

Application services depend on interfaces, not implementations.

---

# Business Rules

Business rules belong exclusively in the Domain Layer.

Examples include:

- Valid application state transitions
- Duplicate detection rules
- Resume constraints
- Task completion rules
- Company uniqueness
- Validation invariants

Business rules must never live inside:

- React components
- Controllers
- Database models
- API routes

---

# Validation

Validation occurs at multiple layers.

## Presentation

Basic UX validation.

Examples:

- Required fields
- Character limits
- Immediate feedback

---

## Application

Request validation.

Examples:

- Authorization
- Input parsing
- Use case validation

---

## Domain

Business validation.

Examples:

- State transitions
- Domain invariants
- Business constraints

---

## Infrastructure

Persistence validation.

Examples:

- Database constraints
- Network errors
- Storage failures

---

# Error Handling

Errors are translated as they move outward.

```text
Database Error
        ▼
Infrastructure Error
        ▼
Application Error
        ▼
Presentation Error
```

The Domain Layer exposes domain-specific errors.

Examples:

- DuplicateApplicationError
- InvalidPipelineTransitionError
- ResumeAlreadyAttachedError

---

# Shared Packages

Shared packages should follow the same layered philosophy.

For example:

```text
packages/

ui/
validation/
types/
utils/
api-client/
```

Each package should have a clearly defined responsibility.

---

# Browser Extension

The Browser Extension follows the same architecture.

```text
Popup UI

      ▼

Capture Application Service

      ▼

Parser Domain

      ▼

Chrome APIs
```

Parser logic belongs to the Domain Layer.

Browser APIs belong to Infrastructure.

---

# Backend API

Example request flow.

```text

      ▼

Controller

      ▼

      ▼

Domain

      ▼

Repository Interface

      ▼

Prisma Repository

      ▼
```

# Frontend Example

```text
      ▼

      ▼
```

The React component never contains business rules.

# Alternatives Considered

## MVC

Advantages:

- Familiar
- Simple

Rejected because:

- Encourages mixing business logic into controllers.
- Does not scale well for complex domains.

---

## Feature-only Organization

Advantages:

- Easy navigation

Rejected because:

- Features still require architectural boundaries internally.

CareerOS combines **feature-based organization** with **layered architecture**.

---

## Direct ORM Access

Advantages:

- Less code initially

Rejected because:

- Couples business logic to persistence.
- Harder testing.
- Difficult future migrations.

---

# Consequences

## Positive

- Business logic is framework-independent.
- Infrastructure can evolve independently.
- Easier testing.
- Better maintainability.
- Clear architectural boundaries.
- Consistent project structure.
- Improved long-term scalability.

---

## Negative

- More files.
- Additional abstraction.
- Slightly steeper learning curve.

These trade-offs are acceptable for a long-lived platform.

---

# Compliance

The following rules are mandatory.

- Domain never imports infrastructure.
- Domain never imports React.
- Domain never imports Prisma.
- Domain never imports browser APIs.
- Business rules belong only in the Domain Layer.
- Application layer orchestrates workflows.
- Infrastructure implements interfaces.
- Presentation renders data and captures user input.
- Dependencies always point inward.

Violations require architectural review.

# Decision Summary

CareerOS adopts a **Layered Architecture** consisting of **Presentation**, **Application**, **Domain**, and **Infrastructure** layers. Business logic resides exclusively in the Domain Layer, application workflows are coordinated by the Application Layer, user interactions are handled by the Presentation Layer, and implementation details such as databases, APIs, browser APIs, and external services are isolated within the Infrastructure Layer. Dependencies always point inward, ensuring a maintainable, testable, and framework-independent architecture.
