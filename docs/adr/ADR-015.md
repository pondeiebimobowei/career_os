# ADR-015: Parser Normalization Pipeline

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS aggregates job opportunities from multiple recruitment platforms through the browser extension.

Each platform exposes job information differently.

Examples include:

| Platform | Example Employment Type |
|----------|--------------------------|
| LinkedIn | Full-time |
| Greenhouse | Full Time |
| Lever | Full-time Employee |
| Workday | Regular |
| Ashby | Permanent |

Likewise, fields such as:

- Location
- Salary
- Remote status
- Department
- Company name
- Seniority
- Employment type

all vary in format and terminology.

Without normalization:

- The database becomes inconsistent.
- Filters produce unreliable results.
- Analytics become inaccurate.
- Search quality decreases.
- Duplicate detection becomes unreliable.
- AI features receive inconsistent input.

A standardized normalization pipeline is required before captured data enters the CareerOS domain model.

---

# Decision

CareerOS will process every captured job through a **Parser Normalization Pipeline** before validation and synchronization.

The pipeline transforms platform-specific values into standardized CareerOS domain values.

Normalization occurs **inside the browser extension** before data is sent to the backend.

---

# Goals

The normalization pipeline should:

- Produce consistent data.
- Remove platform-specific terminology.
- Improve search.
- Improve filtering.
- Improve analytics.
- Simplify backend logic.
- Improve duplicate detection.
- Provide deterministic behavior.

---

# High-Level Pipeline

```text
Raw HTML

↓

Parser

↓

Raw Job Data

↓

Normalization Pipeline

↓

Canonical Job Model

↓

Validation

↓

Synchronization

↓

CareerOS API
```

The backend should only receive normalized domain objects.

---

# Pipeline Stages

The normalization pipeline consists of several sequential stages.

```text
Extraction

↓

Cleaning

↓

Normalization

↓

Enrichment

↓

Validation

↓

Synchronization
```

Each stage has a single responsibility.

---

# Stage 1 — Extraction

The parser extracts raw values directly from the DOM.

Example:

```text
Employment Type

"Full-time Employee"
```

No transformations occur during extraction beyond locating and reading data.

---

# Stage 2 — Cleaning

Cleaning removes presentation artifacts.

Examples:

- Leading whitespace
- Trailing whitespace
- Duplicate spaces
- HTML entities
- Invisible characters
- Empty strings

Example:

```text
"  Senior Frontend Engineer  "

↓

"Senior Frontend Engineer"
```

---

# Stage 3 — Normalization

Normalization converts raw values into standardized CareerOS values.

Example:

```text
Full-time

↓

FULL_TIME
```

Another example:

```text
Hybrid Remote

↓

HYBRID
```

The normalized representation is stored throughout the system.


---

# URL Normalization

URLs are normalized by:

- Removing unnecessary query parameters.
- Standardizing protocol.
- Resolving redirects where appropriate.
- Removing tracking identifiers.

Example:

```text
https://jobs.example.com?id=123&utm_source=abc

↓

https://jobs.example.com?id=123
```

This improves duplicate detection.

---

# Salary Normalization

If salary information is available:

Examples:

```text
$100k–$120k

↓

Minimum

Maximum

Currency
```

Normalized representation:

```text
Minimum

Maximum

Currency

Period
```

The original salary string may also be retained.

---

# Description Normalization

Description processing includes:

- HTML removal
- Whitespace cleanup
- Unicode normalization
- Paragraph preservation

The goal is consistent rendering across the application.

---

# Identifier Generation

Each captured job receives:

- Source platform
- Source identifier
- Normalized identifier

These identifiers assist duplicate detection and synchronization.

---

# Enrichment

Optional enrichment may include:

- Platform metadata
- Capture timestamp
- Parser version
- Language detection

Enrichment never modifies the semantic meaning of extracted data.

---

# Validation

After normalization, the canonical model is validated using shared Zod schemas.

Required fields include:

- Title
- Company
- Source URL

Validation failures prevent synchronization.

---

# Canonical Job Model

After normalization every parser produces the same model.

Example:

```text
Title

Company

Location

Employment Type

Remote Type

Description

Source URL

External ID

Platform

Captured At
```

This becomes the only representation used by the backend.

---

# Duplicate Detection

Duplicate detection relies on normalized values rather than raw values.

Examples include:

- Normalized URL
- Company
- External ID
- Title

Normalization improves duplicate accuracy across platforms.

---

# Error Handling

If normalization fails:

- The error is logged.
- The user receives feedback where appropriate.
- Synchronization is aborted.

Invalid normalized objects are never transmitted to the backend.

---

# Telemetry

Normalization metrics include:

- Parse duration
- Normalization duration
- Validation failures
- Unknown employment types
- Unknown workplace types
- Unsupported fields

Telemetry supports parser maintenance and quality improvements.

---

# Extensibility

Adding support for a new normalized field requires:

1. Update canonical model.
2. Extend normalization pipeline.
3. Update validation schema.
4. Update parser implementations.
5. Add regression tests.

# Alternatives Considered

## Store Raw Values

Advantages:

- Simple implementation.

Rejected because:

- Poor analytics.
- Weak filtering.
- Inconsistent search.
- Duplicate issues.

---

## Backend Normalization

Rejected because:

- Duplicates parser knowledge.
- Increased API complexity.
- Harder browser feedback.
- More network overhead.

---

## Per-Platform Models

Rejected because:

- Breaks shared contracts.
- Complicates backend logic.
- Difficult reporting.

---

# Consequences

## Positive

- Consistent data.
- Reliable analytics.
- Improved filtering.
- Better duplicate detection.
- Simplified backend.
- Strong foundation for AI features.

---

## Negative

- Additional browser-side processing.
- Ongoing maintenance of normalization rules.
- Requires regression testing as platforms evolve.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Every captured job passes through the normalization pipeline.
- Normalization occurs before validation.
- Validation occurs before synchronization.
- The backend receives only canonical job models.
- Shared schemas define normalized values.
- Unsupported values default to predefined `UNKNOWN` enumerations where applicable.
- Raw platform-specific values are not used for business logic after normalization.

Changes to the normalization pipeline require a new ADR.

# Decision Summary

CareerOS adopts a **Parser Normalization Pipeline** that transforms platform-specific job data into a canonical CareerOS job model before validation and synchronization. The pipeline performs extraction, cleaning, normalization, enrichment, and validation within the browser extension, ensuring that all downstream systems operate on consistent, high-quality, machine-readable data regardless of the originating recruitment platform.
