# ADR-008: Browser Extension as a First-Class Product

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is not simply a web application for tracking job applications.

One of its primary value propositions is reducing the manual effort involved in recording and organizing job opportunities across different recruitment platforms.

Most users discover jobs while browsing websites such as:

- LinkedIn
- Greenhouse
- Lever
- Workday
- Ashby
- SmartRecruiters
- Company career pages

Without an integrated capture mechanism, users would need to:

1. Copy the job URL.
2. Open CareerOS.
3. Create a company.
4. Create a job.
5. Create an application.
6. Enter metadata manually.

This workflow creates friction and discourages consistent usage.

A browser extension enables CareerOS to capture structured job data directly from supported websites, dramatically reducing manual effort.

Because job capture is a core capability—not an auxiliary convenience—the browser extension must be treated as a primary product rather than an add-on.

---

# Decision

CareerOS will treat the **Browser Extension as a first-class product** within the platform.

The extension will:

- Live in the same monorepo as the web application and backend.
- Follow the same engineering standards and architectural principles.
- Share domain models, validation schemas, and API contracts.
- Be planned, tested, documented, and released independently.
- Receive equal consideration in product planning and backlog management.

The browser extension is an independent application, not merely a utility.

---

# Goals

The browser extension should:

- Reduce manual data entry.
- Capture structured job information.
- Integrate seamlessly with CareerOS.
- Provide a consistent user experience.
- Reuse shared business logic.
- Support multiple Applicant Tracking Systems (ATS).
- Scale as new job platforms emerge.
- Be maintainable over the long term.

---

# Product Responsibilities

The browser extension is responsible for:

- Detecting supported job pages.
- Extracting structured job information.
- Authenticating the user.
- Displaying capture UI.
- Allowing user edits before saving.
- Preventing duplicate captures.
- Synchronizing data with the CareerOS API.
- Reporting capture failures.
- Collecting telemetry.

The extension is **not** responsible for:

- Core business logic.
- Long-term data persistence.
- Reporting and analytics.
- Complex application workflows.

Those remain the responsibility of the backend and web application.

# Authentication

The extension authenticates directly against the CareerOS REST API using JWT Bearer Tokens.

Workflow:

```text
User
  │
  ▼
POST /api/v1/auth/login
  │
  ▼
CareerOS NestJS API
  │
  ▼
JWT Access & Refresh Tokens
  │
  ▼
Extension Secure Storage (chrome.storage.local)
```

The extension includes the JWT Access Token in `Authorization: Bearer <jwt_token>` headers for all API requests.

---

# API Integration

The extension communicates with the same REST API used by the web application.

Benefits include:

- Consistent validation
- Shared authorization
- Unified business logic
- Reduced maintenance

No extension-specific backend should exist unless absolutely necessary.

# Offline Behavior

The extension should tolerate temporary connectivity failures.

Examples:

- Retry failed synchronization.
- Preserve unsynchronized captures temporarily.
- Notify users of synchronization status.

Long-term offline-first support is considered future work.

---

# User Experience

The extension should:

- Detect supported pages automatically.
- Minimize required clicks.
- Require minimal manual editing.
- Provide immediate feedback.
- Display clear error messages.
- Respect browser accessibility guidelines.

Capture should feel nearly effortless.

---

# Versioning

The browser extension has its own release lifecycle.

Versioning should follow Semantic Versioning.

Extension releases should remain compatible with supported API versions.

---

# Testing

The extension requires dedicated testing.

Test categories include:

- Unit tests
- Parser tests
- UI tests
- Browser integration tests
- Cross-browser compatibility tests
- End-to-end synchronization tests

Parser behavior should be validated using representative HTML fixtures.

---

# Security

The extension must:

- Request the minimum required permissions.
- Avoid unnecessary host permissions.
- Store sensitive data securely.
- Never expose authentication tokens.
- Validate all API communication.

Security considerations are documented separately.

---

# Telemetry

The extension should collect operational telemetry, including:

- Capture attempts
- Successful captures
- Failed captures
- Parser selection
- Synchronization duration
- Error categories

Personally identifiable information (PII) must not be collected unnecessarily.

# Alternatives Considered

## Manual Job Entry Only

Advantages:

- Simpler implementation

Rejected because:

- High user friction.
- Poor user retention.
- Significant manual effort.

---

## Bookmarklet

Advantages:

- Easier distribution

Rejected because:

- Limited capabilities.
- Poor browser integration.
- Inferior user experience.

---

## Browser Extension as a Utility

Rejected because:

- Undervalues a core user workflow.
- Leads to weaker planning and testing.
- Encourages architectural shortcuts.

---

# Consequences

## Positive

- Significantly improved user experience.
- Reduced manual data entry.
- Better user retention.
- Stronger competitive differentiation.
- Shared platform architecture.
- Consistent engineering standards.
- Independent product evolution.

---

## Negative

- Additional maintenance.
- Browser compatibility concerns.
- Ongoing parser maintenance as external websites evolve.

These trade-offs are justified by the strategic value of automated job capture.

---

# Compliance

The following rules are mandatory.

- The browser extension is treated as an independent application.
- It follows the same engineering standards as other CareerOS applications.
- Shared logic is reused through shared packages.
- Authentication uses the platform's identity provider.
- API communication uses the standard REST API.
- Each supported website has its own parser implementation.
- Dedicated testing and documentation are maintained.
- Browser permissions follow the principle of least privilege.

Changes to this architectural approach require a new ADR.

# Decision Summary

CareerOS treats the **Browser Extension as a first-class product**, not as an auxiliary tool. It is an independently planned, developed, tested, documented, and released application within the monorepo. By sharing domain models, API contracts, and engineering standards with the rest of the platform, the extension becomes a core part of the CareerOS experience, enabling fast, low-friction job capture across supported recruitment platforms.
