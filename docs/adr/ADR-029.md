# ADR-029: AI Operational Rules

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS uses AI extensively throughout the software development lifecycle.

AI assistants participate in:

- backlog execution,
- code generation,
- documentation,
- testing,
- refactoring,
- debugging,
- pull request preparation,
- code review assistance.

Unlike traditional engineering tools, AI systems make autonomous suggestions that may not always align with repository standards.

Without operational rules:

- architecture may drift,
- duplicated code may be introduced,
- engineering standards may be violated,
- documentation may become inconsistent,
- backlog discipline may weaken,
- automation may become unreliable.

CareerOS therefore requires explicit operational rules governing how AI interacts with the repository.

---

# Decision

CareerOS adopts a formal set of **AI Operational Rules**.

These rules define what AI assistants are expected to do, what they must avoid, and how they integrate into the engineering workflow.

These rules apply to every AI tool used within the project.

---

# Goals

The operational rules should:

- Preserve architectural integrity.
- Standardize AI behavior.
- Improve engineering consistency.
- Protect repository quality.
- Reduce human review effort.
- Maximize safe automation.
- Keep repository documentation authoritative.

---

# Core Principle

AI is an implementation assistant.

The repository is the authority.

Whenever AI and repository documentation disagree, the repository wins.

---

# Source of Truth Priority

AI should resolve ambiguity using the following precedence:

```text
Architecture Decision Records (ADRs)

↓

Engineering Playbook

↓

Backlog YAML (CBS)

↓

Domain Documentation

↓

Existing Source Code

↓

Developer Instructions

↓

Model Knowledge
```

AI should never override documented project decisions using generalized best practices.

---

# Repository Awareness

Before implementing changes, AI should understand:

- architecture,
- affected feature,
- related ADRs,
- backlog issue,
- dependencies,
- existing implementation.

AI should avoid making assumptions when repository context is available.

---

# Backlog Discipline

AI should only implement approved backlog work.

Implementation begins with:

```bash
pnpm backlog:next
```

or a specific backlog issue.

AI should not invent undocumented features.

---

# Architectural Compliance

AI must follow existing architecture.

AI must not:

- introduce new architectural patterns,
- reorganize project structure,
- redefine domain boundaries,
- bypass layered architecture,
- violate feature ownership,

unless explicitly instructed and documented through a new ADR.

---

# Code Generation Rules

Generated code should:

- compile,
- follow repository conventions,
- reuse existing abstractions,
- include appropriate typing,
- minimize duplication,
- remain readable.

Generated code should favor consistency over novelty.

---

# File Modification Rules

AI should:

- modify existing files where appropriate,
- avoid unnecessary file creation,
- preserve project organization.

New files should only be created when justified by the architecture or backlog.

---

# Dependency Rules

Before introducing a dependency, AI should determine whether:

- the capability already exists,
- an existing package can be reused,
- a shared package should be extended.

Adding new dependencies requires explicit justification.

---

# Testing Rules

AI should:

- add tests for new behavior,
- update tests for modified behavior,
- avoid removing tests without justification.

Tests are part of the implementation, not an optional enhancement.

---

# Documentation Rules

AI should update documentation whenever changes affect:

- architecture,
- APIs,
- workflows,
- configuration,
- engineering processes.

Documentation should remain synchronized with implementation.

---

# Git Workflow Rules

AI should follow the approved workflow:

```text
Backlog

↓

Feature Branch

↓

Implementation

↓

Commit

↓

Pull Request

↓

Review

↓

Merge
```

AI should not bypass repository workflow.

---

# Branch Rules

AI should:

- generate approved branch names,
- use short-lived branches,
- associate branches with one CBS issue.

AI should not create arbitrary branch names.

---

# Commit Rules

Commit messages should follow Conventional Commits.

Example:

```text
feat(api): add application search endpoint
```

AI should avoid vague commit messages.

---

# Pull Request Rules

AI may generate:

- titles,
- summaries,
- acceptance criteria,
- checklists,
- testing notes.

Human reviewers approve pull requests.

---

# Code Review Rules

Before proposing code, AI should check for:

- duplicated logic,
- existing utilities,
- architecture violations,
- naming inconsistencies,
- unnecessary complexity.

Generated code should require minimal review effort.

---

# Security Rules

AI should avoid introducing:

- hardcoded secrets,
- insecure defaults,
- missing authorization,
- weak validation,
- excessive permissions,
- unnecessary exposure of sensitive data.

Security-sensitive code requires additional human review.

---

# Performance Rules

AI should:

- avoid unnecessary database queries,
- reuse computed values,
- minimize redundant rendering,
- avoid premature optimization.

Performance improvements should be evidence-based.

---

# Error Handling Rules

AI should:

- propagate meaningful errors,
- avoid swallowing exceptions,
- preserve consistency,
- use existing error conventions.

Unexpected failures should remain observable.

---

# Refactoring Rules

AI should only refactor when it:

- improves readability,
- reduces duplication,
- simplifies architecture,
- preserves behavior.

Large-scale refactoring should be proposed before implementation.

---

# AI Scope

AI is encouraged to:

- generate boilerplate,
- implement backlog issues,
- write tests,
- update documentation,
- explain code,
- improve readability.

AI should avoid making product decisions independently.

---

# Human Responsibilities

Humans remain responsible for:

- architecture,
- code review,
- approvals,
- security,
- releases,
- roadmap,
- prioritization,
- production decisions.

Responsibility is never delegated to AI.

---

# Prohibited Actions

AI must not:

- merge pull requests,
- approve pull requests,
- modify protected branches directly,
- redefine ADRs,
- change backlog priorities,
- invent requirements,
- ignore acceptance criteria,
- remove tests without justification,
- introduce undocumented architectural changes.

---

# Continuous Improvement

AI operational rules should evolve through:

- retrospectives,
- tooling improvements,
- ADRs,
- engineering discussions.

Major changes require a new architectural decision.

---

# Alternatives Considered

## Unrestricted AI Usage

Rejected because:

- inconsistent outputs,
- architecture drift,
- weak governance.

---

## Human-Only Workflow

Rejected because:

- slower delivery,
- repetitive manual work,
- reduced productivity.

---

## AI-Driven Autonomous Development

Rejected because:

- insufficient accountability,
- architectural risk,
- unpredictable implementation quality.

---

# Consequences

## Positive

- Consistent AI behavior.
- Better architectural compliance.
- Higher code quality.
- Predictable repository evolution.
- Reduced review effort.
- Improved maintainability.

---

## Negative

- Requires disciplined prompts.
- Additional documentation maintenance.
- Human review remains essential.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- Repository documentation overrides AI assumptions.
- AI implements only approved backlog work.
- AI follows existing architecture and engineering standards.
- AI generates compliant branches, commits, and pull requests.
- AI updates tests and documentation alongside implementation.
- Human review is required before merging AI-generated code.
- AI must not perform protected or governance-related actions.
- Significant workflow changes require new ADRs.

Violations should be corrected before merge.

# Decision Summary

CareerOS adopts a formal set of **AI Operational Rules** that governs how AI assistants interact with the codebase and engineering workflow. AI is required to operate within repository-defined architecture, CBS-backed backlog planning, and established engineering standards. Repository documentation is the authoritative source of truth, human contributors retain responsibility for all governance and production decisions, and every AI-generated change must pass the same review, testing, and approval process as human-authored code. This ensures AI remains a safe, predictable, and effective engineering collaborator.
