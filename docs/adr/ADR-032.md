# ADR-032: Zod for Runtime Validation

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS is a TypeScript-first platform, but TypeScript provides **compile-time** type safety only.

Data entering the system from external sources cannot be trusted, including:

- HTTP requests
- Browser extension messages
- Local storage
- IndexedDB
- Environment variables
- Configuration files
- YAML backlog files
- Third-party APIs
- Database query results
- Web scraping and parser output
- AI-generated structured data

Without runtime validation, malformed or unexpected data may:

- cause runtime failures,
- corrupt application state,
- violate business rules,
- create security vulnerabilities,
- propagate invalid data throughout the system.

CareerOS requires a consistent runtime validation strategy that integrates naturally with TypeScript.

---

# Decision

CareerOS adopts **Zod** as the standard runtime validation library across the entire repository.

All external data crossing application boundaries must be validated using Zod schemas before entering the domain or application layers.

Zod schemas serve as the canonical runtime contract for external data.

---

# Goals

The validation strategy should:

- validate all external inputs,
- produce strongly typed results,
- eliminate duplicated validation logic,
- integrate with TypeScript,
- improve developer experience,
- provide meaningful validation errors,
- support schema reuse across applications.

---

# Validation Philosophy

TypeScript ensures correctness during development.

Zod ensures correctness at runtime.

Both are required.

```text
Compile Time

↓

TypeScript

↓

Runtime

↓

Zod

↓

Application
```

Neither replaces the other.

---

# Validation Boundaries

Validation occurs whenever data crosses a trust boundary.

Examples include:

```text
HTTP Request

↓

Zod

↓

Application
```

```text
Browser Message

↓

Zod

↓

Extension Logic
```

```text
Third-Party API

↓

Zod

↓

Domain
```

Unvalidated external data must never enter the application layer.

---

# Approved Validation Library

The repository standard is:

```text
Zod
```

Alternative runtime validation libraries require architectural approval.

---

# Schema Ownership

Schemas belong near the boundary where validation occurs.

Typical locations include:

```text
features/

shared/

contracts/

schemas/
```

Business rules remain separate from validation schemas.

---

# Type Inference

TypeScript types should be inferred from Zod schemas whenever possible.

Example:

```typescript
const UserSchema = z.object({
  id: z.string(),
  email: z.string().email(),
});

type User = z.infer<typeof UserSchema>;
```

Schemas become the single source of truth for external contracts.

---

# Safe Parsing

Preferred validation approach:

```typescript
schema.safeParse(data)
```

This enables predictable error handling without exceptions.

`parse()` may be used when validation failures are considered exceptional.

---

# Error Handling

Validation failures should:

- be explicit,
- return meaningful messages,
- avoid exposing internal implementation details,
- preserve application stability.

Errors should be translated into appropriate user-facing responses at the presentation layer.

---

# HTTP Validation

Incoming request components should be validated, including:

- request body,
- query parameters,
- route parameters,
- headers (when applicable).

Controllers should receive validated data only.

---

# Browser Extension Validation

Browser messaging APIs require validation for:

- runtime messages,
- storage payloads,
- background communication,
- content script communication.

Browser APIs should never receive unchecked objects.

---

# Parser Validation

Parser output is inherently untrusted.

All normalized parser results must pass Zod validation before persistence or further processing.

Examples include:

- LinkedIn parser output,
- Greenhouse jobs,
- Lever jobs,
- Workday jobs.

---

# Configuration Validation

Configuration should be validated during application startup.

Examples:

- environment variables,
- YAML configuration,
- feature flags,
- CLI options.

Applications should fail fast when configuration is invalid.

---

# Database Validation

Database constraints remain the primary mechanism for enforcing persistence rules.

Zod complements database validation by validating:

- input payloads,
- repository boundaries,
- serialized data,
- imported data.

Zod does not replace database integrity constraints.

---

# Domain Layer

Business rules belong in the domain layer.

Zod validates structure.

The domain validates behavior.

Example:

```text
Valid Email Format

↓

Zod

↓

Business Rule:
Email Must Be Verified
```

Structural validation and business validation remain separate concerns.

---

# Shared Schemas

Reusable schemas should live in shared packages.

Examples:

```text
packages/contracts

packages/shared

packages/domain
```

Avoid duplicating schemas across applications.

---

# Schema Composition

Prefer composition over duplication.

Example:

```typescript
BaseUserSchema.extend({
  role: z.string(),
});
```

Reuse existing schemas whenever practical.

---

# Transformations

Zod transformations may be used for:

- normalization,
- parsing,
- coercion,
- derived values.

Transformations should remain predictable and side-effect free.

---

# Defaults

Default values may be defined in schemas where appropriate.

Defaults should represent sensible application behavior rather than hidden business logic.

---

# AI-Assisted Development

AI-generated code should:

- reuse existing schemas,
- avoid duplicate validation,
- infer types from schemas,
- validate all external inputs,
- follow repository conventions.

AI should not invent alternative validation strategies.

---

# Testing

Schemas should be tested for:

- valid input,
- invalid input,
- edge cases,
- optional values,
- transformations.

Validation is considered application behavior and should be covered by automated tests.

---

# Continuous Integration

Schema validation is verified through:

- unit tests,
- integration tests,
- type checking.

Schema regressions should block merging.

---

# Alternatives Considered

## Manual Validation

Rejected because:

- repetitive,
- inconsistent,
- error-prone,
- difficult to maintain.

---

## Class Validator

Rejected because:

- decorator-heavy,
- weaker TypeScript inference,
- less ergonomic schema composition.

---

## Joi

Rejected because:

- weaker TypeScript integration,
- additional type duplication.

---

## Yup

Rejected because:

- less expressive for complex schemas,
- weaker inference capabilities.

---

# Consequences

## Positive

- Consistent runtime validation.
- Strong TypeScript integration.
- Reusable schemas.
- Improved developer experience.
- Better API contracts.
- Safer AI-generated code.

---

## Negative

- Additional schema maintenance.
- Minor runtime validation overhead.
- Developers must distinguish structural validation from business rules.

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- All external inputs are validated with Zod before entering the application layer.
- Zod is the repository standard for runtime validation.
- TypeScript types should be inferred from Zod schemas whenever possible.
- Validation schemas are reused rather than duplicated.
- Business rules remain separate from structural validation.
- Parser outputs, configuration, browser messages, and HTTP requests must be validated.
- AI-generated code follows the same validation strategy.
- Validation failures are handled explicitly.

Changes to the runtime validation strategy require a new ADR.

# Decision Summary

CareerOS adopts **Zod** as the standard runtime validation library across the entire repository. Every external input—including HTTP requests, browser extension messages, parser outputs, configuration, and third-party data—is validated using Zod before entering the application layer. Zod schemas serve as the canonical runtime contracts, with TypeScript types inferred directly from them to eliminate duplication and strengthen type safety. Structural validation remains distinct from domain business rules, ensuring a clear separation of concerns and a consistent, reliable validation strategy throughout the platform.
