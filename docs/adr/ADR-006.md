# ADR-006: PostgreSQL as the Primary Database

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

CareerOS manages structured, relational business data across multiple domains, including:

- Users
- Companies
- Jobs
- Applications
- Application Pipeline
- Tasks
- Notes
- Resumes
- Activity History
- Analytics
- Notifications
- Settings
- Billing (future)

These entities have well-defined relationships and require:

- Strong data integrity
- Transactional consistency
- Complex querying
- Referential integrity
- Reliable indexing
- Scalability
- Backup and recovery capabilities

The database must support the current MVP while providing a solid foundation for future growth.

---

# Decision

CareerOS will use **PostgreSQL** as its primary relational database management system (RDBMS).

All persistent application data will be stored in PostgreSQL.

Database access will be performed exclusively through the data access layer using Prisma ORM (see ADR-007).

---

# Goals

The database platform should provide:

- ACID-compliant transactions
- Strong consistency
- Excellent relational modeling
- High performance
- Robust indexing
- Reliable backup and recovery
- Mature ecosystem
- Cloud portability
- Long-term maintainability

---

# Why PostgreSQL

PostgreSQL was selected because it offers:

- Mature open-source ecosystem
- ACID compliance
- Advanced indexing
- Rich SQL support
- JSON/JSONB support
- Foreign key constraints
- Window functions
- Full-text search capabilities
- Excellent tooling
- Broad hosting support

It is widely adopted and well-suited for SaaS applications.

---

# Data Model

CareerOS primarily models relational business entities.

Example relationships:

```text
User
 ├── Companies
 ├── Jobs
 ├── Applications
 ├── Tasks
 ├── Notes
 └── Resumes

Company
 └── Jobs

Job
 └── Applications

Application
 ├── Tasks
 ├── Notes
 └── Activity History
```

These relationships benefit from relational modeling and referential integrity.

---

# Transaction Support

PostgreSQL transactions will be used whenever multiple operations must succeed or fail together.

Examples include:

- Creating an application and its initial pipeline state
- Updating an application status while recording activity history
- Deleting related entities safely
- Bulk import operations

Transactions ensure the database remains consistent.

---

# Referential Integrity

Relationships will be enforced using foreign keys.

Example:

```text
Application
    │
    ▼
Job

Application
    │
    ▼
Company

Task
    │
    ▼
Application
```

The application should rely on database constraints in addition to application-level validation.

---

# Normalization

The schema should be normalized to reduce duplication.

General guideline:

- Third Normal Form (3NF) where practical

Denormalization is permitted only when justified by measurable performance improvements.

---

# Indexing Strategy

Indexes will be created for:

- Primary keys
- Foreign keys
- Frequently queried columns
- Search fields
- Sorting fields
- Unique constraints

Examples:

- `email`
- `companyId`
- `applicationStatus`
- `createdAt`
- `updatedAt`

Indexes should be reviewed as query patterns evolve.

---

# Unique Constraints

Unique constraints enforce business rules.

Examples:

- User email
- `googleId` (OAuth2 Google identity)
- `githubId` (OAuth2 GitHub identity)
- External job identifiers (where applicable)

The database is the final authority for enforcing uniqueness.

---

# Soft Deletes

CareerOS will prefer **soft deletes** for user-owned business data.

Implementation:

```text
deletedAt TIMESTAMP NULL
```

Benefits include:

- Auditability
- Recovery
- Safer accidental deletion handling

Hard deletes are reserved for:

- Temporary data
- Expired sessions
- Cache tables
- Internal housekeeping

---

# Audit Fields

Every persistent entity should include common metadata.

Recommended fields:

```text
id

createdAt

updatedAt

deletedAt (nullable)
```

Additional audit fields may include:

- createdBy
- updatedBy

where appropriate.

---

# JSON Usage

PostgreSQL's JSONB support may be used for:

- Flexible metadata
- Parser output
- Integration payloads
- Feature flags

Business-critical relational data should not be stored as arbitrary JSON.

---

# Full-Text Search

Future search functionality may leverage PostgreSQL full-text search.

Candidate domains include:

- Companies
- Jobs
- Notes
- Resume metadata

External search engines will only be introduced if PostgreSQL search becomes insufficient.

---

# Performance

Performance optimization priorities:

- Proper indexing
- Query optimization
- Pagination
- Connection pooling
- Efficient joins
- Avoiding N+1 queries

Premature optimization should be avoided.

---

# Backups

Regular automated backups are mandatory.

Backup strategy includes:

- Daily snapshots
- Point-in-time recovery (where supported)
- Backup verification
- Restore testing

Backups must be encrypted and stored securely.

---

# Migrations

Database schema changes are managed through Prisma Migrations.

Rules:

- No manual production schema changes
- All schema updates are version controlled
- Every migration is reviewed
- Migrations are repeatable and deterministic

---

# Environment Isolation

Separate PostgreSQL databases are maintained for:

```text
Development

Testing

Staging

Production
```

Production data must never be used in development environments.

---

# Security

The database must be secured using:

- Network isolation
- Least-privilege database users
- TLS connections (where supported)
- Strong credentials
- Encrypted backups

Sensitive information should never be stored in plaintext.

---

# Scalability

PostgreSQL supports future scaling through:

- Read replicas
- Connection pooling
- Vertical scaling
- Partitioning (when necessary)

Horizontal scaling strategies may be evaluated as product usage grows.

---

# Monitoring

Operational metrics should include:

- Query performance
- Slow queries
- Connection count
- Storage usage
- Replication health
- Backup status

Alerts should be configured for abnormal conditions.

---

# Alternatives Considered

## MySQL

Advantages:

- Mature ecosystem
- Broad hosting support

Rejected because:

- PostgreSQL offers richer SQL features, stronger JSON support, and better extensibility for CareerOS's needs.

---

## SQLite

Advantages:

- Simple
- Lightweight
- Zero configuration

Rejected because:

- Not suitable for a multi-user production SaaS platform.
- Limited concurrency.

---

## MongoDB

Advantages:

- Flexible document model

Rejected because:

- CareerOS primarily manages relational business data.
- Referential integrity and transactional workflows are core requirements.

---

## Firebase Firestore

Advantages:

- Managed service
- Real-time updates

Rejected because:

- NoSQL model is not ideal for CareerOS's relational domain.
- More difficult to perform complex reporting and relational queries.
- Vendor lock-in concerns.

---

# Consequences

## Positive

- Strong data integrity
- Reliable transactions
- Excellent relational modeling
- Mature tooling
- Scalable architecture
- Broad community support
- Cloud portability
- Easy integration with Prisma

---

## Negative

- Requires SQL knowledge
- Schema changes require migrations
- More operational responsibility than fully managed NoSQL solutions

These trade-offs are acceptable.

---

# Compliance

The following rules are mandatory.

- PostgreSQL is the primary production database.
- Persistent business data resides in PostgreSQL.
- Schema changes occur only through Prisma Migrations.
- Foreign keys are enforced.
- Appropriate indexes are maintained.
- Soft deletes are preferred for user-owned data.
- Production data is isolated from non-production environments.
- Backups are automated and regularly tested.

Changes to the primary database technology require a new ADR.

# Decision Summary

CareerOS will use **PostgreSQL as its primary relational database**. It provides the transactional guarantees, relational modeling, indexing capabilities, and long-term scalability required by the platform. All persistent business data will be stored in PostgreSQL, with schema evolution managed through Prisma Migrations and access abstracted through the application's data access layer.
