# ADR-014: Parser Framework Architecture

- **Status:** Accepted
- **Date:** 2026-08-05
- **Decision Makers:** CareerOS Engineering
- **Version:** 1.0
- **Supersedes:** None
- **Superseded By:** None

---

# Context

A core capability of CareerOS is automatically capturing job information from third-party recruitment platforms through the browser extension.

Supported platforms include:

- LinkedIn
- Greenhouse
- Lever
- Workday

Future support may include:

- Ashby
- Workable
- SmartRecruiters
- BambooHR
- Teamtailor
- Company career pages

Each platform has:

- Different HTML structures
- Different URLs
- Different metadata
- Different DOM layouts
- Independent release schedules

These platforms change frequently and independently.

A tightly coupled parser implementation would require modifying unrelated code whenever a single recruitment platform changes.

A dedicated parser framework is required to isolate platform-specific logic while producing a consistent CareerOS job model.

---

# Decision

CareerOS will implement a **Parser Framework** based on the **Adapter Pattern**.

Each supported recruitment platform is implemented as an independent parser that conforms to a common parser interface.

All parsers output a shared canonical job model.

The remainder of the extension is completely unaware of which parser produced the data.

---

# Goals

The parser framework should:

- Support multiple job platforms.
- Isolate parser implementations.
- Allow independent parser updates.
- Produce consistent output.
- Simplify testing.
- Minimize coupling.
- Enable future parser additions.

---

# High-Level Architecture

```text
Current Browser Page

↓

Parser Registry

↓

Platform Detection

↓

Parser Interface

↓

LinkedIn Parser

Greenhouse Parser

Lever Parser

Workday Parser

↓

Canonical Job Model

↓

Validation

↓

Synchronization
```

---

# Parser Interface

Every parser implements the same interface.

Example responsibilities:

- Detect supported pages.
- Determine parser confidence.
- Extract structured data.
- Normalize values.
- Validate required fields.
- Return the canonical job model.

The extension interacts only with this interface.

---

# Parser Registry

The registry maintains all available parsers.

Example:

```text
Parser Registry

├── LinkedIn
├── Greenhouse
├── Lever
├── Workday
```

Responsibilities include:

- Registration
- Discovery
- Selection
- Execution

The registry prevents parser-specific logic from spreading throughout the application.

---

# Platform Detection

When a page loads:

```text
Current URL

↓

Registry

↓

Supported Parser

↓

Parser Instance
```

Detection may use:

- Hostname
- URL patterns
- DOM markers
- Metadata

The first parser reporting a successful match is selected.

---

# Canonical Job Model

Every parser returns the same output structure.

Example:

```text
Job

Title

Company

Location

Employment Type

Remote Status

Description

Source URL

External ID

Platform
```

Consumers never depend on platform-specific formats.

---

# Parser Responsibilities

Each parser owns:

- DOM traversal
- Element selection
- Data extraction
- Value normalization
- Required field validation

Parsers do not own:

- Authentication
- Synchronization
- API requests
- Storage
- UI rendering

---

# Parser Independence

Parsers must never depend on one another.

Example:

```text
LinkedIn Parser

×

Greenhouse Parser
```

Each parser is completely self-contained.

---

# Normalization

Platform-specific values are converted into standardized values.

Examples:

```text
LinkedIn

Full-time

↓

FULL_TIME
```

```text
Greenhouse

Remote

↓

REMOTE
```

Normalization occurs within the parser.

---

# Confidence Detection

A parser should expose a confidence score or detection result.

Possible outcomes:

```text
Supported

Unsupported

Partial
```

This enables graceful fallback behavior.

---

# Validation

Every parser validates the extracted model before synchronization.

Examples:

Required:

- Job title
- Company
- Source URL

Optional:

- Salary
- Benefits
- Department

Validation uses shared Zod schemas.

---

# Error Handling

Parser failures are categorized.

Examples:

- Unsupported page
- Missing selectors
- Invalid structure
- Required field missing

Failures should not crash the extension.

---

# Parser Versioning

Each parser evolves independently.

A LinkedIn update should not require changes to:

- Greenhouse
- Lever
- Workday

Parser ownership remains isolated.

---

# HTML Fixtures

Each parser owns representative HTML fixtures.

Example:

```text
fixtures/

linkedin/

greenhouse/

lever/

workday/
```

Fixtures enable deterministic testing without relying on live websites.

---

# Testing Strategy

Every parser includes:

## Unit Tests

- DOM extraction
- Value normalization
- Detection logic

---

## Fixture Tests

Input:

Saved HTML

↓

Parser

↓

Expected Job Model

---

## Regression Tests

Regression tests prevent website updates from reintroducing previously fixed bugs.

---

## Snapshot Tests

Optional snapshot tests verify extracted structures remain stable.

---

# Fallback Strategy

If no parser matches:

```text
Unsupported Page
```

The extension:

- Displays an informative message.
- Logs telemetry.
- Does not attempt synchronization.

---

# Extending the Framework

Adding a new platform requires:

1. Create parser.
2. Implement interface.
3. Register parser.
4. Add fixtures.
5. Add tests.
6. Update documentation.

No other architectural changes should be necessary.

---

# Performance

Only one parser should execute for a given page.

Avoid:

```text
LinkedIn

↓

Greenhouse

↓

Lever

↓

Workday
```

Detection should quickly identify the correct parser.

---

# Telemetry

Parser events include:

- Parser selected
- Detection success
- Detection failure
- Parse duration
- Extraction success
- Extraction failure

Telemetry supports maintenance without exposing sensitive user data.

---

# Security

Parsers:

- Read page content only.
- Do not inject business logic.
- Never execute arbitrary page scripts.
- Never transmit extracted data before validation.

---

# Alternatives Considered

## Single Large Parser

Advantages:

- Simpler initial implementation.

Rejected because:

- Poor maintainability.
- High coupling.
- Difficult testing.

---

## Parser Logic Embedded in Content Scripts

Rejected because:

- Tight browser coupling.
- Difficult reuse.
- Weak separation of concerns.

---

## Site-Specific Branches

Rejected because:

- Unsustainable.
- High maintenance.
- Duplicated infrastructure.

---

# Consequences

## Positive

- Independent parser evolution.
- Simplified testing.
- Clear ownership.
- Easy platform expansion.
- Consistent output model.
- Better maintainability.

---

## Negative

- More files.
- Slightly higher architectural complexity.
- Ongoing parser maintenance as external sites evolve.

These trade-offs are justified by the long-term maintainability of the system.

---

# Compliance

The following rules are mandatory.

- Every parser implements the common parser interface.
- Every parser returns the canonical job model.
- Parsers are independently testable.
- Platform detection occurs through the parser registry.
- Validation uses shared schemas.
- Parsers never communicate directly with the backend.
- HTML fixtures are maintained for every supported platform.
- Parser failures are handled gracefully.

Architectural changes to the parser framework require a new ADR.

# Decision Summary

CareerOS adopts a **Parser Framework Architecture** based on the Adapter Pattern. Each supported recruitment platform implements a common parser interface and independently transforms platform-specific HTML into a shared canonical job model. A parser registry manages discovery and execution, enabling scalable support for new job platforms while keeping parser logic isolated, testable, and maintainable.
